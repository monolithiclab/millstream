# Millstream web UI: design brief

Date: 2026-10-15. For: Claude Design. Source of truth for behaviour:
[the platform spec](../specs/20261014.platform-design.md), section 12.

We want a **distinctive** look and feel that is, above all, **usable and practical**: an operations tool people keep
open all day, that answers "what is happening, what is stuck, what should I do" in one glance and one click.

## 1. The product in one minute

Millstream runs **pipelines**: graphs of steps that process **items** (JSON records such as real estate listings).
Steps are code, LLM agents, or a human review. Items move between steps through named **streams**. A **run** is one
firing of a trigger (for example "every day at 06:00"); it pushes items through the graph. Everything is persisted,
so the UI can show, for any item, where it came from, what each step did, what it cost and who approved it.

It runs as a single binary on a laptop (`localhost`) or on a server, and the UI is embedded in that binary. Users
are technical, but reviewers may not be.

### Reference pipeline (use it for all mock data)

`crawl-homesite` and `crawl-classifieds` (code) → `dedupe` → `score` (LLM agent) →
`keep-good` (filter: score ≥ 70) → `rentability` (code) → `keep-profitable` (filter: margin ≥ 15 %) →
`analyst-review` (human) → `report` (PDF).

A typical day: 1,800 listings crawled, 1,240 unique, 310 shortlisted, 42 sent to review, 35 approved, 35 PDFs;
agent cost about $14; 3 dead letters (a crawler timeout, two schema errors).

## 2. Who uses it, and for what

| Person | Main jobs | Where |
| --- | --- | --- |
| **Pipeline engineer** | Build and debug pipelines: why did this item fail, what did the agent see, did my change help (replay) | Desktop, long sessions |
| **Operator** | Watch runs and nodes, unblock work: replay or discard dead letters, pause a step, roll back a revision | Desktop, often a second screen |
| **Reviewer** (analyst) | Decide items in the inbox quickly: approve, reject with a reason, edit a field then approve | Desktop, tablet, sometimes phone |
| **Lead** | Cost per step, intervention rate (how often humans step in), trends | Desktop, occasional |

## 3. Principles

1. **State first.** Every screen leads with what is running, waiting, stuck or failed. Healthy is quiet; problems
   are loud but never alarming for nothing.
2. **Every number is a door.** A count, a cost or an error rate links to the items behind it, already filtered.
3. **The next action sits next to the problem.** A dead letter shows its error with Replay and Discard beside it; a
   paused step shows Resume; a slow step shows its queue.
4. **Live, but calm.** Data streams in (about four updates per second per pipeline). Numbers update in place without
   layout shift; motion is subtle and respects `prefers-reduced-motion`. A lost connection is visible (a small
   "reconnecting" state, and a gap marker in live logs).
5. **Dense where it helps, generous where people decide.** Tables and graphs can be dense; the review inbox is
   spacious, readable and fast.
6. **Keyboard-first.** A command palette (`⌘K`), `/` to search, `j`/`k` to move, single-key review actions
   (`a` approve, `r` reject, `e` edit) with visible hints.
7. **Accessible and bilingual from day one.** WCAG 2.2 AA in both themes; colour never carries meaning alone (status
   also has a shape or icon and a label). English and French: plan for French strings about 30 % longer.
8. **Practical over clever.** No decorative charts, no dashboards for their own sake. If a visual does not answer a
   question in section 2, it goes.

## 4. Identity

**The name.** A millstream is the current that drives a mill: water channelled, steady, doing work. The metaphor is
rich and should be used with restraint: channels and flow (streams between steps), steady motion (live
throughput), grain being processed (items), the millstone (steady, heavy, reliable machinery).

**Direction we want.** Engineered, calm and confident, like a well-made instrument: precise lines, strong
typography, a restrained palette with one signature accent, and a recognisable way of drawing flow (how edges, queues
and moving items look in the graph). It should be identifiable from a cropped screenshot.

**Avoid.** Generic SaaS dashboard looks (purple gradients, glassmorphism, neon on black), cartoon water or literal
mill illustrations, rounded "bubbly" components, and charts used as decoration.

**Relationship to Monolithic Lab.** Millstream is made by Monolithic Lab, whose own brand is a dark basalt ground,
stone and bone text, a single ochre accent, and Big Shoulders Display for its wordmark. Millstream is a product, not
the consultancy: it needs **its own identity**. A quiet kinship (for example a warm mineral neutral, or a "by
Monolithic Lab" endorsement in the about screen) is welcome but not required; do not reuse the lab palette or
wordmark as-is.

**Typography.** One highly legible sans for the interface, and one monospace for identifiers, JSON, CEL expressions
and logs, both with tabular numerals. Fonts must be open-licensed and bundled (the UI runs offline on localhost; no
font CDN).

**Themes.** Light and dark, equal quality; dark is not an afterthought, many operators live in it.

## 5. Vocabulary and states to design for

| Concept | States (each needs a distinct, accessible treatment) |
| --- | --- |
| Run | `running`, `waitingReview`, `succeeded`, `completedWithErrors`, `cancelled` |
| Delivery (one item at one step) | `pending`, `leased` (running), `awaitingReview`, `done`, `filtered`, `failed` (will retry), `dead`, `cancelled` |
| Dead letter | `open`, `replayed`, `discarded`; kinds `dead` (step failed) and `unrouted` (no route matched) |
| Step | active, paused, failing, slow (insight), unschedulable (no node can run it) |
| Pipeline | active, paused, disabled |
| Node | active, draining, revoked, disconnected |
| Engine | active, standby |
| Insight | `open`, `acknowledged`, `resolved`, `muted`; kinds: slow step, failure cluster, cost, review pattern, unschedulable |
| Review sample | `open`, `decided`, `unreviewed` (an auto-approved item a person double-checks; it never blocks anything) |

## 6. Screens

Navigation: a global area (**Inbox**, **Nodes**, **Metrics**, **Logs**) and, per pipeline, **Graph**, **Runs**,
**Streams and items**, **Dead letters**, **Insights**, **Lessons**, **Revisions**. A pipeline switcher and the command
palette reach everything.

Design these first, in this order:

1. **Pipeline graph (live).** Steps as nodes, streams as edges, laid out automatically left to right (React Flow).
   Overlays: items in flight, throughput, error rate, p95 latency and queue depth per step; edge thickness by
   volume; failing steps highlighted; insight badges; filters and review steps visually distinct from code and agent
   steps. Clicking a step opens a side panel: its metrics, recent failures, queue, Pause and Resume. This is the
   signature screen.
2. **Item detail.** Payload (collapsible JSON with copy), artifacts preview (PDF, images), lineage tree upstream and
   downstream, and every attempt: status, duration, cost, error, the agent transcript (prompts, tool calls, final
   output, readable as a conversation), and live logs while it runs.
3. **Review inbox.** A queue on the left, the item on the right, rendered for a human (not raw JSON by default):
   the fields that matter, the editable fields (for example `marginPct`, `notes`) clearly marked, reason codes on
   reject, a diff of edits before confirming, keyboard shortcuts, and review samples marked as such. Must work well
   on a tablet and acceptably on a phone (375 px).
4. **Run timeline.** A Gantt per step for one run: when each step started and drained, waiting versus working
   time, what is blocking the run; the run report (critical path, slowest steps, failures by cluster, cost versus
   the median of the last 10 runs) and, while running, an ETA.
5. **Dead letters.** Grouped by error fingerprint; per group the count, the step, the first and last seen, a sample
   item; Replay or Discard one, a selection or a group, with a confirmation that states the consequence.
6. **Pipelines list.** State, active revision, last run, items today, cost today, open dead letters; Pause,
   Disable, Roll back.
7. **Nodes.** Nodes with labels, version, slots used and free, leases held, health; the active and standby
   engines; unschedulable deliveries; Drain and Revoke.
8. **Insights.** Open insights by kind and step, each with its evidence (figures, sample items) and links to the
   items; Acknowledge, Mute.
9. **Metrics explorer.** Pick a metric, group by step, action, run or label, choose a time range (uPlot); the view is
   kept in the URL so it can be shared.

Also needed: **Lessons** (per agent step: rules and examples, each linking to the review or insight it cites), **Live
logs** (a tail for a run, a step or an item, best effort, with a gap marker after reconnects), and **Revisions** (which
revision each run used).

### Page anatomy

Every screen is built by `ScreenPage`, top to bottom in five rows, each filled through a named slot:

1. **Context line** (`context`, optional): the parents' breadcrumb, `<pipeline> / <Section>` on detail screens.
2. **Title row**: the h1, the help toggle (`help`), status chips (`status`), primary actions at the right (`actions`).
3. **Summary line** (`summary`, optional): the screen's figures in one line of small text.
4. **Toolbar** (`toolbar`, optional): state tabs first, then filters, then secondary actions, in one wrapping row.
5. **Content**: cards, tables and lists with the shared loading, empty and error states.

One component per job: `HelpTip` is the `(?)` disclosure that holds every explanation (never the page body);
`Select` is the one dropdown, a native select with a drawn chevron; `Segmented` is the one state-tab control, counts in
its labels; filter fields are a label above a 34 px control, selects applying on change and text on Enter or blur.

## 7. States and edge cases

- Empty states that teach: no pipelines yet (how to run one), no runs today, inbox zero (a quiet success).
- Loading without layout shift; live reconnecting; read-only while the engine is in standby failover (about 30 s).
- Long values: item ids (`it_7f3a…`), URLs as keys, long step names, French labels.
- Scale: a stream with 50,000 items (virtualised tables, server-side filtering with CEL expressions), a graph with
  25 steps, a run with 2,000 deliveries in the timeline.
- Errors with a message up to 4 KB, shown truncated with expand and copy.
- Money in USD with cents; durations from milliseconds to days; counts with thousands separators per locale.

## 8. Technical constraints

- React and TypeScript, Vite, Tailwind CSS, React Flow (graph), uPlot (time series), react-i18next (EN and FR).
- Served from the Go binary on `localhost` or behind a reverse proxy; no external assets at runtime.
- Live data over server-sent events; the UI only changes runs, pipeline and step state, rollbacks, nodes, replays,
  dead letters, review decisions and insight states. Pipelines themselves are edited as files, not in the UI.
- Desktop-first (1280 to 1920 px wide); inbox, run status and item detail usable down to 375 px.

## 9. What we would like back

1. **Design tokens** for light and dark: colour (including the status set), type scale, spacing, radius, elevation,
   motion, as CSS custom properties ready to map to Tailwind.
2. **Component inventory** with states: status badge, step node and edge, queue indicator, run bar, data table,
   JSON viewer with diff, transcript view, live log tail, metric chart frame, side panel, command palette, toast,
   confirmation dialog, empty state.
3. **The nine key screens** of section 6 in both themes, in English, plus the inbox and item detail in French and at
   375 px.
4. **Interaction notes**: live updates, keyboard shortcuts, focus order, and how the graph shows motion without
   distracting.
5. **The identity in a sentence**, and the reasoning behind the palette and typography choices.
