# M2 agents and builtins: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Each task is test-first,
> ends with a green `make ci` and its own commits.

**Goal:** pipelines mix code and LLM agents: `filter` and `dedupe` run in the engine, `container` actions run under
Docker or Podman, agent actions run through a harness-agnostic adapter with transcripts, budgets, evals and lessons,
past items can be replayed, and the engine reports insights and run reports.

**Architecture:** builtins execute inside the engine's dispatcher as store units (no node round trip). A local
content-addressed artifact store holds action artifacts and agent transcripts. The agent adapter is a hidden
subcommand of the `millstream` binary (`millstream agent`) that speaks the action protocol and drives a harness; the
engine starts it like an exec action, inside a container when available. Harness calls go through a record/replay
layer so tests never touch the network. Replay runs, metric rollups and the insights projector extend the store and
engine.

**Tech stack:** as M1; Docker or Podman CLI for containers (`docker run -i`); `net/http` for the `api` harness; the
`claude` CLI for the `claude-code` harness; `text/template` for prompts.

**Spec:** [platform design](../specs/20261014.platform-design.md), sections 4.7, 5.7, 5.11, 6.1, 6.2, 6.4, 7, 9.2,
10.2, 11.1, 11.4, 13, 16 and 19 (M2 row).

## Global constraints

- Everything from the M1 plan's Global constraints still applies.
- Builtins are `filter`, `dedupe` and `review` (review arrives in M3); they take their parameters under `config`
  (D16).
- No network in tests: harness calls are replayed from recordings under `testdata/`; containers are exercised only
  when `docker` (or `podman`) is available, otherwise those tests are skipped with a clear message, and CI keeps a
  fast path with a fake runtime.
- Agent cost is taken from the harness when reported, else computed from token counts and the price table.
- Lessons are part of the revision hash; `check` enforces `lessons.maxTokens` (default 2,000, approximate tokens =
  characters / 4).
- Insights are deterministic: no LLM involved.

## Review focus

1. A dedupe window boundary: a key seen 30 days and 1 second ago passes again; one seen 29 days ago is filtered
   (Task 1).
2. A replay of an upstream step through `dedupe`: dedupes only within its own generation (Task 2).
3. An agent whose output fails the output schema: retryable error with the transcript kept for each attempt (Task 5).
4. A run whose agent spend reaches `budget.runUsd`: agent steps pause, nothing exceeds the budget even with
   concurrent deliveries in flight (Task 6).
5. A lessons file over the token limit: `check` fails, the adapter never truncates (Task 8).

## Tasks

### Task 1: `filter` and `dedupe` builtins in the engine

- Engine executes builtin deliveries itself: `filter` evaluates `config.expr` (CEL over item, vars, run) and either
  publishes the item unchanged on `out` or marks the delivery `filtered`; `dedupe` evaluates `config.key` (CEL string)
  and applies the Dedupe unit (spec 5.11: look up (step, generation, key); pass and set `seenAt` if absent or older
  than `window`, else `filtered` with reason `duplicate`).
- Store: `Filter` unit (delivery → filtered with reason) and `Dedupe` unit; `dedupe_keys(pipeline, step, generation,
  key, first_item, seen_at)`; failpoints for both.
- `check`: builtins no longer warn "arrives in M2" (review still does until M3).
- Tests: filter pass/drop, CEL error → non-retryable dead; dedupe window boundaries, generation scoping; crash tests
  for the two new units in the e2e suite.

### Task 2: replay runs

- `generations(pipeline, next)` counter; `millstream replay --pipeline p --step s [--since 7d] [--run id]
  [--where CEL] [--revision n]` creates a run of kind `replay`, takes a new generation in the same transaction, and
  creates deliveries of `s` for the selected input items (items on the step's `in` streams); outputs carry the replay
  run id; downstream deliveries carry the replay generation.
- Store unit `StartReplay`; items selection read-only; expired payloads fail explicitly (no retention in M2, so only
  the code path and test).
- Tests: replay creates new items with new ids, concurrent replays get distinct generations, `--where` filters,
  dedupe inside a replay scoped to its generation, crash test for the unit.

### Task 3: artifacts

- `internal/artifacts`: content-addressed local store (`.millstream/artifacts/<pipeline>/<sha256>`), `Put(r) (Ref,
  error)`, `Open(ref)`, reference counts in the `artifacts` table.
- Protocol: `emit.artifacts[{name, path}]` relative to `MILLSTREAM_WORKDIR`; the node uploads on done (path must stay
  inside the workdir — `os.Root`), item envelopes carry `{name, sha256, size, type}`; input artifacts materialised in
  the workdir before `item`. SDK: `Context.Artifact(name, path)` and `Context.InputArtifact(name) (path, error)`.
- Fixture `report` writes its text report as a real artifact.
- Tests: path traversal refused, dedupe by hash, materialisation, SDK round trip.

### Task 4: container runtime, registry actions and the lock file

- `internal/runtime/container`: runs `docker run -i --rm` (or podman) with stdio attached, the workdir mounted, env
  passed explicitly, `--read-only` except the workdir, network per manifest (`none` unless declared); same protocol and
  pool as exec (share code: a `Launcher` interface used by the exec pool).
- Action resolution: `kind: container` manifests name an `image`; registry refs `ns/name@range` map through the
  environment file's `registries` (M2: an optional `millstream.yaml` read by `run` with `registries` and `prices`)
  to `<registry>/<name>:<version>`; `millstream lock` resolves each to an exact digest (`docker image inspect` /
  `docker manifest inspect`) and writes `millstream.lock`; `run` refuses a digest mismatch.
- Tests: fake launcher in unit tests; a real container test (busybox-free: build a tiny image from the fake action
  binary with a generated Dockerfile `FROM scratch`) skipped when docker is absent; lock round trip.

### Task 5: agent adapter and harnesses

- `millstream agent` hidden subcommand (the action process for `kind: agent`): reads the manifest's
  `runtime.agent` (harness, model, prompt, tools, mcp, network, maxTurns, maxCostUsd), renders `prompt.md` with
  `text/template` (payload, config, vars, lessons as `.Lessons`, appending a "Lessons from past runs" section when the
  template does not reference them), runs the harness, extracts structured output (native structured output where
  available, else the last fenced JSON block), validates against the output schema (retryable error on mismatch),
  emits the output with metrics `tokens_in`, `tokens_out`, `cost_usd`, `model`, `turns`, `duration_ms`, and writes the
  transcript (prompts, tool calls, results, final output; secrets redacted) as an artifact.
- Harness drivers behind `Harness` interface: `claude-code` (spawns `claude -p --output-format json` with an explicit
  `--allowedTools` list and `--max-turns`), `api` (Anthropic Messages API and OpenAI-compatible chat completions over
  HTTP, with an adapter-run tool loop limited to declared tools; no tools in M2 beyond none — document).
- Record/replay: `MILLSTREAM_HARNESS_MODE=record|replay|live` with recordings keyed by a hash of (harness, model,
  rendered prompt, schema); tests run in replay.
- Sandbox: when a container runtime is available, the engine runs the adapter in a container with the network policy;
  otherwise only with `agents.allowUnsandboxed: true` in the environment file (logged at every start).
- Tests: prompt rendering and lessons appending, structured output extraction both ways, schema mismatch retry with
  transcript per attempt, cost from tokens and price table, record/replay keying, redaction in transcripts.

### Task 6: budgets

- `maxCostUsd` per delivery enforced by the adapter (stop, non-retryable). `budget.runUsd` / `budget.dayUsd`: the
  Lease unit reserves the step's `maxCostUsd` on agent deliveries; Done/Fail replace it with the reported cost; a
  lost lease keeps the reservation; when the next reservation would exceed a budget, the pipeline's agent steps are
  paused with a `budgetReached` event and the UI/CLI shows the cause; `resume` is manual.
- Tests: concurrent leases never exceed the budget; day rollover by UTC day; node death keeps the reservation.

### Task 7: evals

- `millstream eval <action dir> [--harness-mode replay]`: cases in `evals/*.yaml` (`input`, `assert: [CEL over
  output]`, optional `judge: {rubric, model}` using the `api` harness with recordings); prints a score per case; stores
  results in `eval_results`, exposed as the metric `eval_score{action,case}` with the M4 Prometheus endpoint.
- Tests: CEL assertions pass/fail, judge via recording, exit codes.

### Task 8: lessons

- Resolver loads `lessons/<step>.yaml` (or the `lessons` key path) into the action spec for agent steps; `check`
  validates the lessons schema and `lessons.maxTokens`; the adapter receives lessons via the item/hello config path
  (`hello.lessons`), never truncated.
- Tests: injection, over-limit check failure, change of lessons changes the revision hash.

### Task 9: metric rollups, insights, run reports

- `metric` messages and engine metrics recorded as events; a projector rolls them up per minute into
  `metric_rollups(pipeline, name, labels_json, minute, count, sum, min, max)`; `/metrics`-style text dump via
  `millstream metrics` (Prometheus endpoint comes with the server in M4).
- Insights projector (spec 11.1 kinds available in M2: `slowStep`, `failureCluster`, `cost`, `unschedulable`;
  `reviewPattern` arrives with review in M3): runs at run end and every `insights.every`; fingerprints, states,
  `millstream insights [list|ack|mute]`.
- Run reports: critical path, slowest steps, failures by cluster, cost, comparison with the median of the last 10
  runs; `millstream run report <id>`.
- Tests: golden insights over fixture event logs, rollup math, report golden output.

### Task 10: `init`, `test action`, conformance suite

- `millstream init pipeline|action <name> [--lang go|raw]` scaffolds a package or an action (Go SDK main + manifest +
  schemas + an example eval).
- `millstream test action <dir>`: fixture inputs in `tests/*.yaml` against golden outputs; `--conformance` runs the
  protocol conformance suite (hello/ready, item/done, keyed outputs, error mapping, shutdown, malformed input
  tolerance) against any action.
- Tests through the CLI parser; conformance passes for the SDK and the fixture actions.

### Task 11: M2 exit

- Fixture extended: an agent `score` variant (`kind: agent`, harness `api`, recordings in testdata) replacing the code
  scorer in an `m2-fixture` package, `dedupe` inserted between crawl and score.
- E2E: scoring runs with the (replayed) agent; insert `dedupe` and replay seven days of crawls (seven manual runs with
  `crawl` dates) through it; edit the lessons file, replay a day, scores change (recordings keyed on the rendered
  prompt make this deterministic).
- Crash suite extended to the new units (filter, dedupe, startReplay).
- A live smoke test (`MILLSTREAM_LIVE=1`, not in CI) runs the agent step against the real `claude` CLI if installed.
