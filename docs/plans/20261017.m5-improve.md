# M5 self-improvement: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Each task is test-first,
> ends with a green `make ci` and its own commits.

**Goal:** pipelines get better from their own history: agent steps can fall back and be audited, insights trigger an
`improve` pipeline in development, evidence moves from production to development, every change is a validated
proposal (lessons, prompt, config, topology, distill) accepted on its base revision and published safely, and the UI
gets the Improve view.

**Architecture:** the engine gains only what spec 11 assigns it: abstain and fallback, audits, the new insights,
evidence export and import, the backtest endpoint, proposal rules (states, path rules, conditional acceptance) and
publish actions. Everything that drafts is the `improve` package, an ordinary pipeline embedded in the binary that
calls the public API with a proposals-only token. Agents in tests and in the exit run through the record/replay
harness, so the whole milestone is offline and deterministic.

**Tech stack:** as M1–M4; git with hooks disabled for the publish actions; `gh` and `glab` only inside the publish
container, faked in tests.

**Spec:** [platform design](../specs/20261014.platform-design.md), sections 6.3 (abstain), 11 (all), 12.2 (Improve
view), 13 (`evidence`, `improve`, `proposals`, `backtest`), 14 (`environment`, `improve`), 15.3, 16 and 19 (M5 row).

## Global constraints

- Everything from the M1–M4 plans' Global constraints still applies, including AGENTS.md "Test suites" (default Go
  suite ≤ 500 ms; it starts M5 near the limit, so each task makes room for what it adds) and the M3 UI rules.
- The "Time and token budget" rules in `~/.claude/CLAUDE.md`: iterate with `make ci` and
  `make test-e2e PKG=…`; full suites once per task; one `/simplify` pass; short reports.
- Production deployments never run `improve` and refuse `improve.publish: apply` (D31).
- Proposed code is untrusted until accepted: it runs only in the network-less container sandbox; the publish action
  never builds or runs it and holds no other credential (D33).
- No compatibility shims before launch.

## Review focus

1. A proposal accepted while another open proposal touches the same step: the other becomes `stale` in the same
   transaction; acceptance on a moved base revision makes the proposal `stale` instead (Task 5).
2. A distill holdout leaking into training through a retry, a lesson example or the same item key: the split refuses
   it (Task 7).
3. A patch that touches a path its kind does not allow, a symlink or a mode change: refused at drafting and at
   publishing; the published patch's hash must equal the validated one (Tasks 5 and 8).
4. An evidence bundle past its expiry: import refuses it and the development engine deletes imported evidence when it
   expires; a purged key lists the bundles that held it (Task 3).
5. An audit on a step whose actions have side effects: `check` fails; audits never hold a run open (Task 1).

## Tasks

### Task 1: abstain, fallback and audits

- Protocol `abstain` message (spec 6.3) in the protocol, SDK and adapter; staged outputs discarded.
- Step key `fallback: { action, when: [abstain, error], auditRate }`; the Abstain unit hands the delivery to the
  fallback with attempts reset; envelopes record `producedBy`.
- Audits: `auditRate` samples covered items, runs the fallback with `audit: true` into the `audits` table, reserves
  budget, never retried, never part of the run; `check` requires `effects: none` on both actions.
- Metrics (coverage, fallback rate, fallback cost, audit agreement) and the `drift` insight on disagreement.

### Task 2: environments, insight triggers and the remaining insights

- `environment: production | development` enforced across commands (`serve` production, `run` development; already
  parsed in M4): production refuses `improve` and `publish: apply`.
- Trigger kind `insight` (insights at or above `improve.minSeverity`), feeding the improve package.
- Insights `waste`, `drift` (from Task 1), `distillable` (spec 11.5 criteria), and review attribution (spec 11.6:
  edited field → nearest step whose output differs from its input) feeding `reviewPattern` with proposal hints.

### Task 3: evidence export and import

- `millstream evidence export --pipeline <p> [--since] [--insight]`: bundle with open insights, a stratified sample
  (`improve.evidence.sample`), lineage inputs and outputs, review decisions without reviewer identities, transcripts,
  the production revision hash; stream `redact` pointers replaced by stable hashes; `evidence_exports` audit rows;
  `purge --key` lists bundles that held the key.
- `millstream evidence import <bundle>` into a development deployment as read-only history, refused when expired,
  deleted on expiry; backtests report divergence from the bundle's revision.

### Task 4: the backtest endpoint

- `POST /api/v1/backtests` and `millstream backtest <patch>`: apply the patch to a scratch copy, replay the changed
  steps on a stratified sample (local history or imported evidence; `improve.backtest.sample`), in a scratch store with
  `effects: external` actions stubbed, reusing recorded upstream outputs; rerun downstream steps reached by newly
  admitted items, charged to the improve budget; report before/after agreement with historical outputs and reviewer
  decisions, failure rate, cost, latency.

### Task 5: proposals

- `proposals` table and units: kinds, states (`drafting`, `validating`, `ready`, `accepted`, `rejected`, `stale`),
  patch artifact and hash, touched paths, fingerprint suppression after rejection (resurfaces when the insight's
  severity doubles), rejection reasons kept for later drafts.
- Path rules per kind (spec 11.7) at drafting and publishing; symlinks and mode changes refused.
- Validation by the engine: `check`, base-revision evals before and after (a proposal cannot redefine its own success),
  backtest; revalidation of stale proposals by rebasing.
- The Proposal acceptance unit (spec 5.11): only on the current base; marks overlapping proposals stale.
- API, CLI `proposals list|show|accept|reject`, a proposals-only token for the improve package.

### Task 6: the improve package

- `millstream/improve` embedded in the binary, run only in development when `improve.enabled` and a harness are set:
  steps `gather-evidence`, `draft` (agent, recorded in tests), `validate`, `propose`, `publish`, its own
  `improve.budget.dayUsd`, triggers: insight stream, weekly cron, manual "Propose a fix".
- Proposal drafting for `lessons`, `prompt`, `config` (autoApprove, retries), `topology` (filter upstream with the
  `maxFalseDrop` check) from the patterns of spec 11.6; `millstream improve [--insight]`;
  `millstream init pipeline --from improve`.

### Task 7: distill

- Holdout split by time and item key made before gathering evidence; no holdout item, retry or derived lesson example
  reaches the drafting agent.
- The `distill` proposal: generated Go action with the SDK, unit tests and evals, allowed to abstain; validation
  thresholds `minAgreement` 0.98, `minCoverage` 0.6, ≥ 200 covered holdout items, then evals; the patch moves the
  agent under `fallback`.

### Task 8: publish actions

- `apply` (development revision under the acceptance condition), `patch-file`, `git-pr-gh`, `git-pr-glab`: in their
  own container with only forge credentials, git with `core.hooksPath=/dev/null`, refusing any content whose hash
  differs from the validated patch; pull requests carry the validation report and a `Millstream-Proposal` trailer.
- On apply, read `Millstream-Proposal` trailers; a revision whose parent is not the validated base runs evals and a
  backtest against the previous revision and raises an insight on regression.

### Task 9: the Improve view

- Insights by kind and step with evidence; proposals with a diff viewer, rationale, evidence items and the before/after
  validation table; accept and reject (reason required); Lessons sources linked to their proposal, review or insight;
  en/fr, WCAG AA, per the canvas where it covers these screens (the canvas lacks a proposals board: follow the
  components board and record the gap).

### Task 10: M5 exit

- Evidence exported from a production deployment of the reference pipeline (the M2 fixture with review, recorded
  agents) yields, in a development deployment, an accepted `lessons` proposal and an accepted `distill` proposal whose
  code cuts agent cost with holdout agreement of at least 0.98: an e2e scenario, offline, through the CLI and API, with
  a Playwright pass through the Improve view.

## Execution notes

Milestone completed on branch `m5-improve` (2026-10-20). `make ci` green (coverage 88.5%, floor 88: the Docker and git
paths of publishing and the sandbox are covered by the e2e build only); `make test-times` 627 ms (budget 750, raised
from 500 during M5 by the user's ruling); `make test-e2e` green after two fixes; `make test-ui` (98.4% statements) and
`make test-ui-e2e` (150 + 9 + 2) green; `make test-exit` green.

**Exit.** `TestM5Exit` (`docs/m5-exit.md`): a production deployment exports evidence from two pipelines; a development
deployment with no history of its own imports it; the improve pipeline drafts a `lessons` proposal (backtest: reviewer
agreement 0.58 → 1.00 over 46 deliveries) and a `distill` proposal (holdout 270 items, 260 covered, agreement 1.000,
$0.2189 saved of $0.2272); both are accepted and applied; day 3 on the published code costs $0.0084 against $0.2273
in production (3.7%).

**Built.** Abstain, fallback and audits with the `drift` insight (T1); environments enforced, insight triggers, the
`waste` and `distillable` insights and review attribution with proposal hints (T2); evidence export and import with
keyed-hash redaction, expiry and purge listing (T3); the patch format and the backtest endpoint on a scratch store with
external effects stubbed (T4); proposals with per-kind path rules, a parsed semantic check of `pipeline.yaml`,
validation by check, base evals and backtest, acceptance on the base revision and a proposals-only token (T5); the
embedded improve package (T6); distill with an engine-fixed holdout split (T7); publish actions (`apply`, `patch-file`,
`git-pr-gh`, `git-pr-glab`) with hash checks, trailers and recovery, and the network-less sandbox for every piece of
proposed code (T8); the Improve view (T9); the exit scenario (T10).

**Rulings.**
- Proposed code runs only in the network-less sandbox, wherever it runs (evals, backtest, distill holdout); without
  Docker it is refused. Production refuses proposals, their validation and the proposals token (D31 corollary).
- Backtest pass rule: reviewed and unreviewed agreement may each drop by at most the share of reviewed deliveries that
  moved toward the reviewers' truth, plus 0.02; the failure rate may not rise; `maxFalseDrop` holds for every proposal.
- The engine fixes the distill holdout boundary; distill agreement compares output keys exactly.
- Request ids are identifiers a purge keeps and must never carry personal data.
- The improve budget, backtest jobs and holdout floors live in memory per process (ROADMAP).
- Full slow suites run once per batch of parallel work, after merging, under `caffeinate -i` (user rulings, now in
  `~/.claude/CLAUDE.md`); heavy suites queue on a machine-wide lock.

**Review.** The whole-branch review found one critical issue, proposed exec code escaping the sandbox through an
action directory no step referenced, and six important ones (unredacted insight evidence, proposals stuck validating,
a proposer-chosen holdout, a too-coarse pass rule, proposals accepted in production, publishing not recovering from a
half-finished publish); all fixed with tests. Bugs found by the exit and the final runs: imported evidence invisible
to the improve pipeline, distill agreement ignoring keys, and a node not renewing the lease of a delivery whose package
it was still fetching.

**Deferred** (ROADMAP): durable improve budget, backtest jobs and holdout floors; the 600 ms test target; a
proposal's publish state stored on its row; a decoded-bundle cache; the Improve view driven against a deployment with
real evidence in Playwright.
