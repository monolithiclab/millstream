# Convex Workflow: competitive analysis

Checked 2026-10-22. Sources are the component's page and README, its GitHub issues and pull requests, the Convex docs
(limits, pricing, regions), the Convex blog and Stack articles, npm and GitHub API figures, and this repo's spec,
decisions, roadmap and plan execution notes. Figures marked *unverified* came from secondary sources or summaries and
need a re-check before any external use. This note compares; it does not recommend changes to Millstream's scope.

## Summary

Convex Workflow (`@convex-dev/workflow`) is a **code-first durable-execution library** for apps already built on
Convex. A workflow is a TypeScript function whose steps (queries, mutations, actions, sleeps, events, child workflows)
are journalled in the Convex database and replayed deterministically after each step. It is small, pre-1.0 (0.4.10),
Apache-2.0, maintained mostly by one engineer, and widely installed inside Convex apps (about 227k npm downloads a
week, 85 GitHub stars). It inherits Convex's strengths (reactive status queries, transactions, zero infrastructure on
the cloud) and its limits (1 s mutation bodies, 8 MiB journals, 1 MB of step I/O per execution, 10 to 30 min actions,
TypeScript only, Convex only).

Millstream is a **declarative pipeline platform** for work that mixes code, LLM agents and human decisions: a YAML
graph of steps connected by persisted item streams, run by one self-hosted Go binary on SQLite or Postgres, with
review inboxes, agent budgets, evals, a live UI and a self-improvement loop built in. It is not released yet.

The two overlap on "reliable multi-step background work with retries and human waits", but they answer different
questions. Convex Workflow answers *"how do I make this function survive failures?"* inside one app. Millstream
answers *"how do I run, watch, review, cost and improve a stream of items flowing through code, agents and people?"*
as a separate system. Convex Workflow wins on developer ergonomics for Convex users and on general-purpose control
flow; Millstream wins on item-level data processing, operations, AI governance and independence from a vendor.

## What Convex Workflow is

| Aspect | Convex Workflow |
| --- | --- |
| Definition | `workflow.define({ args, returns }).handler(async (step, args) => …)` in TypeScript |
| Steps | `step.runQuery`, `runMutation`, `runAction`, `runWorkflow` (child), `sleep`, `awaitEvent`, `withOptions` |
| Parallelism | `Promise.all` over steps, capped by the Workpool's `maxParallelism` |
| Durability | Journal of step results in Convex tables; the handler re-executes from the start and replays the journal |
| Determinism | `fetch`, env vars and `crypto` blocked in the body; `Date`, `console`, `Math.random` patched (seeded) |
| Retries | Per step, exponential backoff with jitter; **actions are not retried by default** |
| Guarantees | Mutations exactly once (transactional); actions at-least-once when retried (user makes them idempotent); `onComplete` exactly once |
| Waits | `sleep` (no compute while sleeping, "workflows that last for months"); `awaitEvent` / `sendEvent` for external or human input |
| Control | `cancel` (in-flight actions still finish), `restart({ from: step })`, `cleanup` (manual; nothing is cleaned by default) |
| Status | `getStatus` (reactive when called from a query), `list`, `listByName`, `listSteps` |
| Limits | 1 MB total step input and output per execution; journal 8 MiB; workflow body bound by mutation limits (1 s of user code, 16 MiB read or written) |
| Platform | Convex cloud (4 regions, non-US +30 %) or self-hosted Convex backend (FSL-1.1, source-available) |
| Maturity | 0.4.10, pre-1.0, Apache-2.0, 52 open issues and PRs, ~65 npm versions since 2024-09 |

### Pricing and quotas that matter for workflows

- Function calls: 1M a month on Free, then $2.20 per million; 25M on Pro, then $2 per million. Each step costs several
  calls (the scheduled step, the handler's replay mutation, Workpool bookkeeping): the exact count is *unverified*.
- Action compute: 20 GB-hours on Free, 250 on Pro. Actions run at most 10 min (Node) or 30 min (Convex runtime).
- Concurrency: 8 scheduled jobs on Free, 256 on Pro; the README asks to keep total `maxParallelism` across workflows
  and workpools at or below 100 on Pro.
- Pro is $25 per member per month (*unverified* on the primary pricing page); Business has a $2,500 monthly minimum.

### Gaps the maintainers and users report

- **No versioning.** Adding, removing or reordering steps, or renaming a step function, fails every in-flight run with
  a determinism violation; the README tells users to keep a workflow's code stable for its whole life
  ([#35](https://github.com/get-convex/workflow/issues/35); versioning PR
  [#279](https://github.com/get-convex/workflow/pull/279) unreleased). A Discord user running 30-day workflows found no
  documented answer for deploys.
- **No webhook or callback primitive.** Receiving an external callback takes an HTTP action plus `sendEvent`; issue
  [#184](https://github.com/get-convex/workflow/issues/184) (the most discussed) calls it six steps of boilerplate.
- **No timeout on `awaitEvent`, no racing events** ([#177](https://github.com/get-convex/workflow/issues/177), PR
  [#224](https://github.com/get-convex/workflow/pull/224)), **no per-step rollback**
  ([#266](https://github.com/get-convex/workflow/issues/266)), slow status queries
  ([#74](https://github.com/get-convex/workflow/issues/74)).
- **No dedicated run UI, metrics or tracing**: status APIs plus the generic Convex dashboard and log streams.
- **Lock-in**: the library only runs on Convex; the self-hosted backend is FSL-1.1 (no competing use, Apache-2.0 after
  two years per version), with little scaling guidance.
- **Bus factor**: one maintainer authored most commits of both Workflow and Workpool.

Outside GitHub issues, no independent review, Hacker News or Reddit thread about the component turned up, and the
2026 durable-engine roundups we found do not mention it. Its visibility is as a Convex feature, not as a product.

## Side by side

| Concern | Convex Workflow | Millstream |
| --- | --- | --- |
| Shape of a workflow | Imperative TypeScript function, any control flow (loops, branches, recursion via child workflows) | Static YAML graph; conditions via CEL `filter` and routes; no loops (cycles are a `check` error) |
| Unit of durable work | One function invocation and its journal | One item delivery (step, item, generation) in a persisted stream |
| Data flow | Values returned between steps, 1 MB total per execution | Items in named streams, fan-out and fan-in, lineage across pipelines, artifacts in file or S3 storage |
| Languages | TypeScript only, Convex functions | Any language over the stdio JSON-lines protocol; Go SDK; `exec`, `container` and `agent` actions |
| Durability mechanism | Deterministic replay of user code | Database item log, fenced leases, publish on `done`; no user-code replay, so no determinism rules |
| Delivery semantics | Mutations exactly once; actions at-least-once if retried, not retried by default | At-least-once everywhere, idempotency from deterministic item ids and an `idempotencyKey` per delivery |
| Retries | Per step, opt-in for actions | Per step, on by default (3 attempts, 10 s to 10 min backoff); poison items end as dead letters |
| Failure handling | Workflow fails, `onComplete` gets the error; `restart({ from })` | Dead-letter streams, replay or discard with an audit trail, step replay over history (`replay --since --where`) |
| Code changes mid-run | Breaks in-flight runs | Runs pinned to a content-hash revision; rollback reactivates one |
| Long waits | `sleep`, `awaitEvent` for any event | Human `review` with timeout and escalation; no generic sleep or wait-for-event step |
| Triggers | Call a mutation (from a client, cron or HTTP action you write) | `cron` with catch-up, `manual`, `webhook` (token, idempotency key, rate limit), insight, stream import |
| Human in the loop | `awaitEvent` plus your own UI | Inboxes, editable fields, reason codes, auto-approve rules, sampled audits, keyboard UI, notifications |
| AI | Separate Agent component (threads, tools, streaming); Workflow chains its calls | Agent actions with sandbox, budgets, transcripts, record and replay, evals, lessons, fallback, distill |
| Self-improvement | None | Insights, evidence bundles, proposals validated by backtest, accept or reject by a person |
| Concurrency control | Workpool `maxParallelism` (steps), platform scheduler quotas | Step `concurrency` and `rate`, pipeline limits, budgets, placement labels, round-robin across pipelines |
| Observability | Reactive status queries, `listSteps`, Convex dashboard and logs | Events table, lineage, run timeline and report, metrics rollups and Prometheus, live SSE UI, log tail |
| Testing | `convex-test` with known edge cases | `test pipeline` with stubs, `test action` with golden outputs, `eval`, recorded agent calls, `backtest` |
| Scale-out | Managed by Convex | One active engine, one hot standby on Postgres, remote worker nodes; throughput ceiling not yet measured |
| Hosting | Convex cloud, or self-hosted Convex (FSL) | Self-hosted only: one binary, SQLite or Postgres |
| Licence | Apache-2.0 library on an FSL backend | Apache-2.0 core; commercial edition planned |
| Maturity | Pre-1.0, in production use inside Convex apps | Proof of concept, milestones M1 to M5 built, not released |

## What Convex Workflow offers that Millstream does not

1. **General-purpose control flow in code.** Loops, data-dependent branching, recursion and dynamic step counts are
   ordinary TypeScript. Millstream's static graph cannot loop, and dynamic fan-out exists only as an action emitting
   several keyed items.
2. **Durable `sleep` and `awaitEvent` for any event.** A workflow can wait days for a payment callback or a timer at
   no compute cost. Millstream's only first-class wait is a human review; a delay or an external callback means a new
   run started by a cron or webhook trigger, with the correlation left to the author.
3. **Exactly-once transactional steps.** Mutations commit with the workflow's state in one database transaction.
   Millstream is deliberately at-least-once (D9) and relies on idempotent actions.
4. **Zero operations on the cloud.** No binary, database, failover or upgrade to run. Millstream is self-hosted only.
5. **Reactive status in the app's own UI.** `getStatus` inside a Convex query pushes live progress to any client the
   app already has. Millstream exposes SSE and an HTTP API, but the app must integrate with a separate system.
6. **Same language and transaction as the application.** Steps read and write the app's own tables; no protocol,
   serialisation boundary or separate deployment.
7. **Restart from a step and child workflows.** `restart({ from })` re-runs from any step; `runWorkflow` composes
   workflows with typed return values. Millstream composes pipelines through stream imports instead, which are
   one-directional and not call-and-return.
8. **An installed base.** About 227k weekly npm downloads (Workpool about 392k) inside Convex apps, on a vendor that
   raised a $57M Series B in August 2026. Millstream has no users yet.

## Where Millstream is ahead

1. **No determinism rules and safe deploys.** Millstream never replays user code, so an action may call the network,
   read the clock or change its code freely. Runs are pinned to the content-hash revision they started on, so a
   deploy never breaks an in-flight run, and rollback is one command. This is Convex Workflow's most-reported gap.
2. **Item streams, not function calls.** Persisted streams with fan-out, fan-in, routing, dedupe, lineage across
   pipelines, artifacts by content hash, retention and GDPR purge suit data processing (sourcing, enrichment,
   scoring). Convex Workflow caps a run at 1 MB of step I/O and keeps no item-level lineage.
3. **Failure as data.** Dead letters are ordinary streams with replay, discard and an audit trail; a step can be
   replayed over weeks of history after a prompt change. Convex Workflow offers `restart` per workflow and an error
   in `onComplete`.
4. **Human review as a product, not a primitive.** Inboxes with timeouts, escalation, editable fields validated
   against schemas, reason codes, auto-approve rules with sampled audits, review metrics and a keyboard-first UI.
   Convex gives `awaitEvent`; the inbox, its UI and its metrics are left to the developer.
5. **Governed AI.** Sandboxed agents, per-delivery and per-day budgets enforced by reservation, transcripts, recorded
   agent calls for deterministic tests, evals with LLM judges, lessons, fallback with audits, and distillation of an
   agent into code behind a holdout. Convex's Agent component handles threads and tools, not cost governance or
   evaluation.
6. **Self-improvement loop.** Insights detect slow steps, failure clusters, cost and review patterns; the `improve`
   pipeline drafts proposals that the engine validates by backtest before a person accepts them. No equivalent
   exists on Convex.
7. **Operations built in.** Live graph, run timeline with critical path and ETA, metrics explorer, Prometheus
   endpoint, log tail, nodes view, all in one WCAG 2.2 AA bilingual UI. Convex Workflow relies on the generic
   dashboard and the app's own UI.
8. **Any language, any runtime.** Actions in any language over a published stdio protocol, as processes, containers
   or agents, on remote nodes with labels and slots; no 10 to 30 minute action ceiling (timeouts are per step).
9. **No vendor or licence lock-in.** One Apache-2.0 binary on SQLite or Postgres, data in the customer's own
   database, no per-call pricing. Convex Workflow only runs on Convex, whose self-hosted backend is FSL.
10. **Triggers included.** Cron with catch-up, webhooks with per-trigger tokens, idempotency keys and rate limits, and
    triggers on another pipeline's insights. Convex Workflow has none of its own; webhook callbacks are its
    most-requested feature.

## Where Millstream is weaker today

- **Not released.** No users, no published throughput ceiling, a 30-minute soak instead of the week-long run, release
  tooling written but not published.
- **Operations are the customer's.** Even with Compose and systemd files, someone runs Postgres, the standby and the
  nodes. Convex cloud runs itself.
- **Single active engine.** Coordination state (rates, sessions, backtest jobs) lives in the active engine's memory
  and resets on failover; no active-active.
- **Narrower control flow.** No loops, no durable timers, no generic external-event wait, no call-and-return
  composition.
- **SDK coverage.** Go only; Python after v1; no TypeScript SDK, which is Convex's whole audience.
- **Known gaps** listed in `ROADMAP.md`: webhook signature verification, per-destination network allowlists, the
  `api` harness without a tool loop, live streams exhausting Chrome's six connections per host.

## Positioning

The products rarely compete for the same buyer. A team already on Convex reaches for Convex Workflow because it is
there, typed and free of operations; nothing in Millstream would make it leave Convex. Millstream's buyer runs item
pipelines that mix agents and people, cares about cost, review and audit, and wants the system and its data on its
own infrastructure. For that buyer, Convex Workflow is a building block they would have to wrap with an inbox, an
operations UI, budgets, evals and a deploy story; Millstream is that wrapper, shipped.

Points worth borrowing, as ideas to weigh rather than commitments (each would need its own decision):

- **A durable wait step**: `sleep` or wait-for-callback, correlated by item, with a timeout, would cover payment and
  approval callbacks without a second pipeline. Convex's most-requested issues show the demand.
- **Reactive embedding**: a small client library or a documented SSE contract for showing a run's progress inside
  the customer's own app.
- **Restart from a step** for one run, alongside the existing step replay.
