# Agentic harnesses, from chains to code: analysis

Checked 2026-10-26 against Karthik Ramgopal, "The Evolution of Agentic Harnesses: From Chains to Graph to Code", InfoQ,
2026-10-26, part of InfoQ's *Agentic AI Architecture* series. Millstream facts come from this repo's spec, roadmap,
`internal/agent` and `docs/development/m5-exit.md`. The article describes the author's systems at LinkedIn; no figure
from it is reused here. This note compares and proposes; each proposal would need its own decision before it reaches
the spec.

## Summary

The article tells the history of the harness: the scaffolding that makes a probabilistic model reliable,
observable and fit for production. It goes through three paradigms. **Chains** are linear prompt choreography, cheap
and fragile. **Graphs** add explicit nodes and edges, retries, state, validation and human approvals, but they stay
bounded automations whose recovery paths are coded by hand. **Code harnesses** make the model write code, run it in a
sandbox, validate it and refine it in a loop. The article closes with four practices and one rule:

- treat model output as untrusted input;
- separate planning from execution;
- invest in observability;
- build for continuous improvement;
- use the least complex abstraction that solves the problem, and optimise capability per dollar.

Millstream fits this framing closely, with one twist the article lacks. Millstream is a graph harness at the level of
a stream of items: every step is durable, and code, agents and people sit in one declarative graph. A code harness
can run inside an agent step, as `claude-code` in the sandbox. The self-improvement loop then moves a step down the
article's ladder when the evidence allows: an agent becomes code (`distill`), and a review becomes a rule
(`autoApprove`) or a filter. Each move is proven on a holdout or a backtest, and each is accepted by a person. The
article tells engineers to pick the least complex abstraction once, at design time. Millstream measures which steps
could be simpler and proposes the change. That is the strongest selling point the article opens, and nothing in it
covers the move.

The article also exposes three real gaps:

- **No iterative refinement loop inside an agent delivery.** A schema mismatch is retried with the same prompt, and
  the model never sees why it failed.
- **No output assertions at run time** beyond the schema.
- **No tool loop in the `api` harness**, so a code harness works only through `claude-code`.

## What the article argues

| Paradigm | What it is | Strength | Failure mode |
| --- | --- | --- | --- |
| Chains | Linear prompts, each output feeding the next; the model as text in, text out | Fast to build, lowest latency and cost | One bad step cascades; no detection or recovery; "best effort" |
| Graphs | Nodes (model calls, tools, validations) and edges (control flow), declarative; multi-agent orchestrators, A2A, human approvals | Branching, parallelism, retries, fallbacks, state, explicit validation, inspectable plans | Human-defined workflows; growing state spaces mean recovery paths and edge cases coded by hand; brittle flow definitions; poor fit for open-ended tasks |
| Code | The model writes code, runs it in a sandbox, validates it, refines it until the checks pass | Deterministic pass or fail signal, verifiable, auditable, reproducible | Highest compute and latency from the loops |

A code harness has four parts in the article: an execution sandbox, instrumentation and logging, a validation
harness, and an iterative refinement loop. Its examples are an assistant built as a three-step chain, a recruiting
agent on a graph that adds cognitive memory as a separate agent, and an analytics agent that writes SQL and Python,
runs them on sample data, and checks the results against privacy and governance rules until they pass.

The conclusion: developers move from prompt designers to system architects. Reliability comes from integrating
probabilistic models into deterministic frameworks, with determinism where possible and controlled nondeterminism
only where needed. Over-engineering is the common failure.

### The twist: a harness that descends the ladder

The article treats the choice of paradigm as a decision made once. In a Millstream pipeline the choice is per step,
and it changes with evidence:

1. A step starts as an agent, because the rules are not known yet.
2. Reviews accumulate. Recurring edits become a `lessons` proposal, near-universal approvals an `autoApprove` rule,
   and predictable rejections a `filter` moved upstream of the expensive step.
3. Once the agent's answers are predictable (the `distillable` insight: 500 deliveries, a bounded schema, at most two
   turns, 95% reviewer agreement), `distill` proposes code. The code is checked on a holdout it never saw and keeps
   the agent as the fallback for the items it abstains on. `auditRate` keeps sampling, and the `drift` insight
   raises disagreements.

The M5 acceptance scenario runs this end to end, on synthetic listings whose answers follow a rule:

- agreement with reviewers went from 0.58 to 1.00 after a lessons proposal;
- the code covered 260 of 270 held-out items and agreed on all of them;
- the next day cost 3.7% of the agent cost.

This is the article's "capability per dollar" made mechanical, and its "determinism where possible, controlled
nondeterminism only where needed" made measurable: coverage is the share that became deterministic, and the
fallback rate is the share that still needs the model.

### What the article's critique of graphs means for Millstream

The article's main charge against graphs is that recovery paths, validation and edge cases end up coded by hand.
Millstream answers part of it. Recovery is generic: retries, dead letters, replay over history, fallback. Nothing per
pipeline handles it. Edge cases surface as insights and become proposals instead of hand edits. The other part
holds: a Millstream pipeline is a fixed graph, and an open-ended task cannot be written as one. The answer is to
keep the graph for the durable, reviewable outer flow and put the open-ended part inside one agent step running a
code harness. That needs gaps 1 and 3 closed to be convincing on any model.

## Selling points

### Documentation (this repo)

1. **An agents-in-production guide, `docs/guides/agents.md`.** The guides hold only getting started and deployment
   today. Agent practice is scattered across spec sections 7, 8, 11 and 15. A guide organised by the article's four
   practices would be the most useful page for a new author:
   - untrusted output: the schema, `abstain`, allowlists and the effects check;
   - planning apart from execution: proposals, and why agents never edit the graph;
   - observability: transcripts, metrics, lineage and redaction;
   - improvement: lessons, evals, recordings, distill and audits.

   It would also say when to pick a builtin, code, an agent or a review for a step. Add its row to `docs/README.md`.
2. **Spec section 20, prior art.** The LangGraph and CrewAI row says they "orchestrate inside one agent". A sentence
   would place Millstream at the level the article calls a graph harness, durable per item, and say that a code
   harness runs inside an agent step.
3. **README pitch.** One line would help: "each step is the cheapest that works: a rule, code, an agent or a person,
   and the platform proposes moving a step down when the evidence allows".
4. **Accuracy of the M5 figures.** `m5-exit.md` says the listings are synthetic and the agent follows a rule. Every
   reuse of 3.7% and 1.000, in docs and on the site, should say so in a few words.

## Features to consider

Ranked by value against cost. None is committed; each goes to `ROADMAP.md` or a decision first.

1. **Validation feedback within a delivery** (closes gap 1). When an answer fails the output schema, the adapter
   sends the validator's errors back to the harness as a follow-up turn, up to a small `repairTurns` limit, inside
   the same attempt, within `maxTurns` and `maxCostUsd`.
   - Each repair turn is in the transcript, and the recording key covers the conversation, so replay stays
     deterministic.
   - The existing `schema_validation_failures` metric gains a "repaired" counterpart.
   - This is the article's refinement loop at the smallest cost: today a mismatch spends a whole new attempt on an
     identical prompt.
   - Small to medium (`internal/agent`, spec section 7.1).
2. **Output assertions on agent steps** (closes most of gap 2). An `assert` list of CEL over `output`, `input` and
   `vars`, the same language as eval cases. A failure is a schema-class error: retried, and with feature 1 fed back to
   the model.
   - This keeps the AGENTS rule that thresholds belong in `filter` steps. An assertion states that the answer is
     wrong (an invariant: a score within its band, a quoted field present in the input). A filter states that a
     correct item is not wanted.
   - The rule needs writing down in the spec, or assertions will drift into thresholds.
   - Small.
3. **The `api` harness tool loop, with MCP for both harnesses** (gap 3, already in `ROADMAP.md`). Without it, a code
   harness exists only through Claude Code, and the article's pattern cannot run on an OpenAI-compatible or local
   model. A sandboxed code-execution tool would come with it: Python or SQL in the agent's container, its result
   returned as a tool result. Raise its priority to M6 or just after. Medium.
4. **Live judges on a sample.** Eval judges run only offline. A step key that scores a sample of production answers
   with the action's eval judge, recorded like audits and raising a `drift`-like insight below a threshold, would be
   the article's "secondary model" check without paying for it on every item. It reuses `internal/eval` and the audit
   machinery. Medium.
5. **Personal data masking in transcripts.** The article asks for observability "while masking sensitive data".
   Secrets are redacted; personal data in a transcript is erasable by purge but stored in clear. Reusing the evidence
   bundle's pointer list (each stream names its personal fields) to mask those values in transcripts would close it.
   Medium; it touches redaction, which recordings share.
6. **A request-and-wait trigger.** The article's examples are interactive. Millstream's webhook returns at once and
   the result arrives later. A webhook that can wait a bounded time for the run's output would cover light
   interactive uses. It sits close to the parked durable-wait idea (`20261022.convex-workflow.md`). Weigh it against
   the non-goal of serving chat traffic.

Explicitly not proposed:

- **Run-time graph changes by an agent.** They would break the revision hash, replay and the review of every
  change. Planning stays at design time.
- **Cycles.**
- **A2A or an orchestrator agent.** Multi-agent reasoning belongs inside an action.
- **Per-entity mutable memory.** It conflicts with immutable items and deterministic replay. Lessons and shared
  streams cover the cases seen so far.
