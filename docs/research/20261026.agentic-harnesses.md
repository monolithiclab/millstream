# Agentic harnesses, from chains to code: analysis

Checked 2026-10-26 against Karthik Ramgopal, "The Evolution of Agentic Harnesses: From Chains to Graph to Code", InfoQ,
2026-10-26, part of InfoQ's *Agentic AI Architecture* series. Millstream facts come from this repo's spec, roadmap,
`internal/agent` and `docs/development/m5-exit.md`. The article describes the author's systems at LinkedIn; no figure
from it is reused here. This note compares and proposes; each proposal would need its own decision before it reaches
the spec.

## Summary

The article tells the history of the harness: the scaffolding that makes a probabilistic model reliable,
observable and fit for production. It goes through three paradigms. **Chains** are linear prompt choreography, cheap
and fragile. **Graphs** add explicit nodes and edges, retries, state, validation and human approvals, but they stay
bounded automations whose recovery paths are coded by hand. **Code harnesses** make the model write code, run it in a
sandbox, validate it and refine it in a loop. The article closes with four practices and one rule:

- treat model output as untrusted input;
- separate planning from execution;
- invest in observability;
- build for continuous improvement;
- use the least complex abstraction that solves the problem, and optimise capability per dollar.

Millstream fits this framing closely, with one twist the article lacks. Millstream is a graph harness at the level of
a stream of items: every step is durable, and code, agents and people sit in one declarative graph. A code harness
can run inside an agent step, as `claude-code` in the sandbox. The self-improvement loop then moves a step down the
article's ladder when the evidence allows: an agent becomes code (`distill`), and a review becomes a rule
(`autoApprove`) or a filter. Each move is proven on a holdout or a backtest, and each is accepted by a person. The
article tells engineers to pick the least complex abstraction once, at design time. Millstream measures which steps
could be simpler and proposes the change. That is the strongest selling point the article opens, and nothing in it
covers the move.

The article also exposes three real gaps:

- **No iterative refinement loop inside an agent delivery.** A schema mismatch is retried with the same prompt, and
  the model never sees why it failed.
- **No output assertions at run time** beyond the schema.
- **No tool loop in the `api` harness**, so a code harness works only through `claude-code`.

## What the article argues

| Paradigm | What it is | Strength | Failure mode |
| --- | --- | --- | --- |
| Chains | Linear prompts, each output feeding the next; the model as text in, text out | Fast to build, lowest latency and cost | One bad step cascades; no detection or recovery; "best effort" |
| Graphs | Nodes (model calls, tools, validations) and edges (control flow), declarative; multi-agent orchestrators, A2A, human approvals | Branching, parallelism, retries, fallbacks, state, explicit validation, inspectable plans | Human-defined workflows; growing state spaces mean recovery paths and edge cases coded by hand; brittle flow definitions; poor fit for open-ended tasks |
| Code | The model writes code, runs it in a sandbox, validates it, refines it until the checks pass | Deterministic pass or fail signal, verifiable, auditable, reproducible | Highest compute and latency from the loops |

A code harness has four parts in the article: an execution sandbox, instrumentation and logging, a validation
harness, and an iterative refinement loop. Its examples are an assistant built as a three-step chain, a recruiting
agent on a graph that adds cognitive memory as a separate agent, and an analytics agent that writes SQL and Python,
runs them on sample data, and checks the results against privacy and governance rules until they pass.

The conclusion: developers move from prompt designers to system architects. Reliability comes from integrating
probabilistic models into deterministic frameworks, with determinism where possible and controlled nondeterminism
only where needed. Over-engineering is the common failure.

### The twist: a harness that descends the ladder

The article treats the choice of paradigm as a decision made once. In a Millstream pipeline the choice is per step,
and it changes with evidence:

1. A step starts as an agent, because the rules are not known yet.
2. Reviews accumulate. Recurring edits become a `lessons` proposal, near-universal approvals an `autoApprove` rule,
   and predictable rejections a `filter` moved upstream of the expensive step.
3. Once the agent's answers are predictable (the `distillable` insight: 500 deliveries, a bounded schema, at most two
   turns, 95% reviewer agreement), `distill` proposes code. The code is checked on a holdout it never saw and keeps
   the agent as the fallback for the items it abstains on. `auditRate` keeps sampling, and the `drift` insight
   raises disagreements.

The M5 acceptance scenario runs this end to end, on synthetic listings whose answers follow a rule:

- agreement with reviewers went from 0.58 to 1.00 after a lessons proposal;
- the code covered 260 of 270 held-out items and agreed on all of them;
- the next day cost 3.7% of the agent cost.

This is the article's "capability per dollar" made mechanical, and its "determinism where possible, controlled
nondeterminism only where needed" made measurable: coverage is the share that became deterministic, and the
fallback rate is the share that still needs the model.

### What the article's critique of graphs means for Millstream

The article's main charge against graphs is that recovery paths, validation and edge cases end up coded by hand.
Millstream answers part of it. Recovery is generic: retries, dead letters, replay over history, fallback. Nothing per
pipeline handles it. Edge cases surface as insights and become proposals instead of hand edits. The other part
holds: a Millstream pipeline is a fixed graph, and an open-ended task cannot be written as one. The answer is to
keep the graph for the durable, reviewable outer flow and put the open-ended part inside one agent step running a
code harness. That needs gaps 1 and 3 closed to be convincing on any model.

## Features to consider

Ranked by value against cost. None is committed; each goes to `ROADMAP.md` or a decision first.

1. **Validation feedback within a delivery** (closes gap 1). When an answer fails the output schema, the adapter
   sends the validator's errors back to the harness as a follow-up turn, up to a small `repairTurns` limit, inside
   the same attempt, within `maxTurns` and `maxCostUsd`.
   - Each repair turn is in the transcript, and the recording key covers the conversation, so replay stays
     deterministic.
   - The existing `schema_validation_failures` metric gains a "repaired" counterpart.
   - This is the article's refinement loop at the smallest cost: today a mismatch spends a whole new attempt on an
     identical prompt.
   - Small to medium (`internal/agent`, spec section 7.1).
2. **Output assertions on agent steps** (closes most of gap 2). An `assert` list of CEL over `output`, `input` and
   `vars`, the same language as eval cases. A failure is a schema-class error: retried, and with feature 1 fed back to
   the model.
   - This keeps the AGENTS rule that thresholds belong in `filter` steps. An assertion states that the answer is
     wrong (an invariant: a score within its band, a quoted field present in the input). A filter states that a
     correct item is not wanted.
   - The rule needs writing down in the spec, or assertions will drift into thresholds.
   - Small.
3. **The `api` harness tool loop, with MCP for both harnesses** (gap 3, already in `ROADMAP.md`). Without it, a code
   harness exists only through Claude Code, and the article's pattern cannot run on an OpenAI-compatible or local
   model. A sandboxed code-execution tool would come with it: Python or SQL in the agent's container, its result
   returned as a tool result. Raise its priority to M6 or just after. Medium.
4. **Live judges on a sample.** Eval judges run only offline. A step key that scores a sample of production answers
   with the action's eval judge, recorded like audits and raising a `drift`-like insight below a threshold, would be
   the article's "secondary model" check without paying for it on every item. It reuses `internal/eval` and the audit
   machinery. Medium.
5. **Personal data masking in transcripts.** The article asks for observability "while masking sensitive data".
   Secrets are redacted; personal data in a transcript is erasable by purge but stored in clear. Reusing the evidence
   bundle's pointer list (each stream names its personal fields) to mask those values in transcripts would close it.
   Medium; it touches redaction, which recordings share.
6. **A request-and-wait trigger.** The article's examples are interactive. Millstream's webhook returns at once and
   the result arrives later. A webhook that can wait a bounded time for the run's output would cover light
   interactive uses. It sits close to the parked durable-wait idea (`20261022.convex-workflow.md`). Weigh it against
   the non-goal of serving chat traffic.

Four further patterns are left out on purpose; the next section says why.

## What not to build, and why

Four patterns from the article would fight Millstream's design. They share one root. Millstream's guarantees rest
on knowing, before a run starts, what can happen to an item:
- which steps it can reach;
- which schemas it must match;
- which effects it can cause;
- what each step may spend.

Then every past item can be run again on the same terms. Each pattern below moves part of that knowledge into a
model's reasoning, at run time, where the engine cannot see it. Each also has a form that keeps the guarantees.

### Run-time graph changes by an agent

**The pattern.** A planner model reads the item and decides which steps run next, inserts a step, or rewrites the
plan as it goes. This is the "plan and execute" agent, with the plan applied by the framework at run time.

**What it breaks.**
- *The revision.* A pipeline has no version field: its revision is the content hash of the package (section 4.2), and
  every run is pinned to the revision it started on. If an agent can change the graph mid-run, the revision no
  longer describes what ran. `replay --step` over last month's items would not re-run the same pipeline, and a
  rollback would not restore the previous behaviour.
- *`check`.* It proves things about the whole graph before anything runs (section 4.8):
  - producers and consumers have compatible schemas;
  - no cycle exists;
  - every agent step on a budgeted pipeline sets `maxCostUsd`;
  - no agent output reaches an `effects: external` step without a review.

  A graph decided at run time cannot be checked in advance. The effects warning matters most here. Agents read
  crawled pages and documents (section 15.4), and today a prompt injection can at worst produce a bad answer, which
  the schema, a filter or a review catches. If the agent could add a step, the same injection could add an action
  that sends an email or writes to a CRM.
- *Measurement.* Insights, backtests, review attribution, cost per step and the `distillable` test all aggregate
  over deliveries of one step of one revision. When each item takes its own path, there is no stable step to
  measure, compare or replace with code.

**What to do instead.** Bound the agent's freedom to what the graph declared:
- *Choose among declared paths.* The agent answers a category, and route objects in `out` send the item to one of the
  branches the engineer wrote. The model decides; the set of possible paths is still known to `check`.
- *Plan inside the step.* Open-ended work (searching, writing and running code, iterating) happens inside one agent
  delivery: Claude Code with its declared tools, within `maxTurns` and `maxCostUsd`. Its final answer still passes
  the output schema.
- *Plan the pipeline as a proposal.* Changes to the graph itself are `topology` proposals: drafted by the `improve`
  agent, backtested on past items, accepted by a person, released as a new revision. This is the article's
  "separate planning from execution", at the time scale where a plan can be checked.

### Cycles

**The pattern.** A step's output flows back to an earlier step: re-score after enrichment until the score settles,
regenerate until a validator passes, send an item back to the writer when a reviewer rejects it.

**What it breaks.**
- *Termination.* Item ids are `hash(step, stream, input item, generation, key)` (section 5.2), so each pass of a
  loop makes a new item and nothing bounds how many. A run is settled when all its deliveries end. With a cycle,
  whether a run ends depends on what the models answer, and `run --once`, run outcomes and run budgets lose their
  footing.
- *Cost.* Budgets reserve per delivery, and a loop turns a per-item limit into a per-pass limit. An item that never
  converges spends until the day budget pauses the whole pipeline.
- *Lineage.* An item that passed the same step three times has that step three times in its ancestry. Review
  attribution names "the nearest step whose output differs from its input" (section 11.6), and stops being a clear
  answer. Insights mix first passes with fifth passes.
- *The checks.* Schema compatibility, the effects warning and the order of steps are all statements about an acyclic
  graph. `check` refuses cycles within a pipeline and across pipelines through imported streams for this reason.

**What to do instead.**
- *Bound the loop inside a delivery*, where a turn limit and a cost limit already hold. An agent's turns are that
  loop, and the validation feedback proposed above (feature 1) is the "regenerate until valid" case, done safely.
- *Unroll a fixed number of passes* as named steps (`score`, `enrich`, `rescore`): acyclic, each measured on its own.
- *Let a person correct* instead of sending back: `editable` fields on the review, with the edit becoming evidence
  for a `lessons` proposal.
- *Re-run deliberately*: retries for transient failures, dead-letter replay after a fix, `replay --step` over history
  after a prompt change. Each re-run is a recorded decision, never a loop.

### An orchestrator agent, or A2A between agents

**The pattern.** A top-level agent receives the task and delegates parts to specialist agents, through an
agent-to-agent protocol such as A2A, deciding who works on what and when.

**What it breaks.**
- *Scheduling and limits.* The engine already orchestrates: leases, retries, `concurrency`, `rate`, placement on
  nodes, and budget reservation before each agent delivery. An orchestrator agent moves those decisions into a
  model, where the engine cannot reserve, retry or pause them. It is the hand-coded coordination the article
  criticises in graphs, now written in a prompt.
- *Accounting.* `maxCostUsd`, run and day budgets, transcripts and the cost metrics hold because every model call of
  a step goes through the adapter (D4). Calls made by agents the orchestrator reached elsewhere escape them,
  unless each reports back.
- *Allowlists.* A step's tools, MCP servers and network are declared in its manifest. A delegate with its own tools
  is a capability the manifest never listed.

**What to do instead.**
- *Agents are steps, and streams connect them.* That is a multi-agent architecture with a deterministic orchestrator.
  Each agent has its own schema, budget, transcript, evals and lessons, and the boundaries between agents are
  checked contracts.
- *Multi-agent reasoning stays inside a step.* A LangGraph graph, a CrewAI crew or Claude Code's subagents run within
  one action, report their cost through `metric` messages, and answer through the output schema.
- *Across teams, use shared streams* (section 4.12): one pipeline imports another's stream, under a contract `check`
  verifies.
- *A2A at the edges stays open.* An action that calls an external A2A agent, or a trigger that accepts A2A tasks, is
  an ordinary action or trigger. It needs no engine change, and could be a stock action later.

### Per-entity mutable memory

**The pattern.** Agents read and write a memory per customer, seller or listing across runs ("this seller always
inflates surfaces"), as the article's cognitive memory agent does for personalisation.

**What it breaks.**
- *Determinism.* Today a delivery's input is its item, its config, the run's variables and the step's lessons from
  the run's revision (section 11.4). All of them are fixed or versioned, and recordings are keyed by the rendered
  prompt. A memory that changes between runs makes the same item give a different prompt tomorrow: replay, recorded
  tests and evals stop reproducing.
- *At-least-once delivery.* A delivery can run twice (D9): a crash after the memory write and before `done`, or a lost
  lease. Outputs publish on `done` (D20) precisely so that a failed attempt leaves no trace, and a memory write is a
  trace. Two deliveries of the same key in parallel race on it too.
- *Validation.* Backtests replay past items. With memory, a past item would be scored with knowledge written after
  it. The `distill` holdout splits by entity and by time so that the drafting agent never sees a holdout item, and a
  shared memory is a channel for exactly that leak.
- *Erasure.* A purge follows lineage to erase every copy of an item (section 15.6). A memory derived from many items
  has no lineage to follow.

**What to do instead.**
- *Lessons are the memory that fits:* procedural, per step, learned from every item's reviews, reviewed as a
  proposal, versioned with the revision.
- *State as items.* "What is known about this seller" can be a stream, produced by a step and read by others, keyed
  and retained like any data; `dedupe` with a key and a window answers "seen before".
- *An explicit external store* remains possible. An action that reads or writes its own database declares it, with
  `effects: external` for writes, and the trade-off is the author's, in plain sight.
- *If a real need appears*, the shape that would fit is a read-only lookup pinned to the run: the latest approved
  item for a key as of the run's start, recorded with the delivery so that replay reads the same value. That would
  be a design of its own, with a decision.
