# M6, the open-source release: design

## Why

M1 to M5 built the engine, agents, review, the server and the self-improvement loop. The pre-release review of
2026-11-16 found that a newcomer cannot reach any of it quickly: no installable binary, no published SDK, Go as the
only SDK language, no stock actions beyond three builtins, no measured capacity, and reference documentation that
lives inside a 2,800-line design spec. M6 makes Millstream installable, measurable and documented, and closes the one
gap in the improvement loop a user would notice first: nobody can tell whether an applied proposal helped.

This document refines the M6 row of the platform spec (`20261014.platform-design.md`, section 19). Where the two
disagree, this document wins and the platform spec is updated in the same commit as the code.

## Goals

1. **Install in one command.** Release binaries for darwin and linux (amd64, arm64) with the web UI embedded, a
   container image on GHCR, a Homebrew formula, all signed; the Go SDK tagged so actions need no `replace`.
2. **Stock actions** that cover the first steps a newcomer writes by hand today: fetch over HTTP, write to a file,
   post to a webhook (including chat incoming webhooks).
3. **A Python SDK**, so the second-largest audience writes actions without hand-rolling the protocol.
4. **A published capacity**: the throughput ceiling and engine memory on the section 16 benchmark workload, measured
   in CI and in the docs.
5. **Signature verification** of registry actions on pull.
6. **The full protocol specification** and **a documentation site** built from `docs/`.
7. **Measure after release**: every applied proposal gets its realised effect recorded beside its prediction.

## Non-goals

- No new runtime, store or harness. No Kubernetes, OpenTelemetry, OIDC or RBAC (later milestones and editions).
- No TypeScript SDK in M6: Python first, TypeScript once a user asks.
- No durable sleep or wait-for-callback step (ROADMAP, Agents): the docs say plainly that Millstream is an item
  stream, not a durable function runtime, and point to where that matters.
- No auto-applying of proposals: measuring after release is its prerequisite, not its start.

## Design

### 1. Release

- **Trigger.** A `v*` tag push runs the release workflow; a tag is pushed only when the owner asks (AGENTS.md).
  The workflow runs `make ci`, the full `make test-e2e` and the UI suites first, then `goreleaser release`.
- **Binaries.** GoReleaser builds `millstream` for darwin/linux × amd64/arm64 after `make ui` (in its pinned
  container), so the embedded UI is the real build, never the placeholder. A test in the release workflow starts the
  binary and checks `/` serves the built `index.html`.
- **Image.** `Dockerfile.release` pushed to `ghcr.io/monolithiclab/millstream`, tagged with the version and `latest`.
- **Signing.** cosign keyless signing of the checksums file and the image (the `.goreleaser.yaml` sections exist and
  are skipped by snapshots today).
- **Homebrew.** A formula in `monolithiclab/homebrew-tap`, written by GoReleaser.
- **Go SDK.** The nested module is tagged `sdk/go/v0.1.0` in the same release. The scaffold's `go.mod.tmpl` requires
  that version and drops its replace comment; the getting-started guide drops `MILLSTREAM_REPO` and both
  `go mod edit -replace` steps.
- **Dependabot** for the `docker` ecosystem, so pinned digests refresh by pull request.
- The ROADMAP "Deployment (icebox)" release and SDK items move here and leave the ROADMAP.

### 2. Stock actions

Stock actions are built into the binary, like the agent adapter (`millstream agent`) and the improve actions: the
reference `millstream/<name>` resolves to the running binary's hidden `millstream action <name>` subcommand. They
therefore run on any node, including the distroless image, with no registry, no Docker and no build. This replaces
the platform spec's plan of OCI-published stock actions (section 4.7, D-entry in `docs/decisions.md` to be recorded
with the code).

| Action | Config | Behaviour |
| --- | --- | --- |
| `millstream/http-fetch` | `url` (CEL over `item`, `vars`), `method` (default `GET`), `headers`, `timeoutSec`, `maxBytes` (default 8 MiB) | One output per item: `{url, status, headers, body}`, `body` as text when the content type is text or JSON, else stored as an artifact. A 5xx or a network error is retryable; a 4xx is an output (routing decides). Declares its network in its manifest. |
| `millstream/sink-file` | `path` (a template over `run` and `vars`), `format` (`jsonl` default, `json`) | Appends each item's payload to the file, one file per run by default; emits nothing. Writes are fsynced before `done`, so a retry after a crash may duplicate a line, never lose one (at-least-once, D9). |
| `millstream/sink-webhook` | `url`, `secret` (a secret name, sent as a bearer token), `body` (optional template; default the payload as JSON) | POSTs each item; a 2xx is done, a 429 or 5xx retryable, any other status non-retryable. With `body`, the same action posts to Slack, Teams or Mattermost incoming webhooks, so there is no separate notification action. |

Templates use the existing CEL interpolation (spec section 4.4). Each action passes `test action --conformance` and
has golden tests in its package.

### 3. Python SDK

- One file, `sdk/python/millstream.py`, standard library only, Python 3.10+. API: `millstream.map(fn)`,
  `millstream.map_keyed(fn)`, a `Context` with `config`, `vars`, `metric(name, value)`, `artifact(name, path)` and
  `abstain(reason)`, mirroring the Go SDK's names in Python style.
- `millstream init action --lang python` replaces `--lang raw`: it scaffolds a Python action with the SDK file copied
  in beside `main.py` (vendored, no package index, no network). PyPI publication waits for a user asking.
- Tests: the SDK's own unit tests run in a pinned Python container (no host toolchain, as D35 for the UI); the
  e2e suite runs `test action --conformance` against the scaffolded action.
- Spec section 6.6 changes from "Python SDK after v1" to this.

### 4. Capacity

- `make bench` runs the section 16 workload (20 pipelines × five one-in-one-out code steps, 2 KB payloads, 50 ms
  actions, one SSE client per pipeline, retention and projections running) against SQLite and Postgres, and reports
  the sustained items per second at which queue depth stays bounded, p95 end-to-end latency and the engine's peak RSS.
- CI runs a short version and fails when peak RSS exceeds 150 MB (spec 6.5); the full run is a milestone-close gate,
  like the soak test.
- The figures, the machine they were measured on and the command go into `docs/guides/deployment.md` under
  "Capacity", which is the published ceiling of D26. Postgres index tuning (ROADMAP) is done from this profile.

### 5. Signature verification

- `registries.<namespace>` takes an object: `{ repository: <prefix>, identity: <regexp>, issuer: <url> }`. With
  `identity` set, the node verifies the pinned digest's signature before running it by calling the operator's
  `cosign verify` (a host binary, as Docker and git are), keyless against the given identity and issuer.
- A pull of a namespace with `identity` set fails the delivery non-retryably when cosign is missing or verification
  fails; `check` warns when a package uses such a namespace and cosign is not on the `PATH`.
- Stock actions need no signature: they are the binary itself, whose release is signed.

### 6. Protocol specification and documentation site

- `docs/reference/action-protocol.md` becomes the normative specification of protocol 1: every rule in MUST/SHOULD
  form, numbered, and each numbered rule names the conformance check that tests it (the conformance suite reports
  rule numbers).
- Reference pages extracted from the platform spec: the pipeline file (section 4), the environment file (generated
  from `init environment`, as the CLI reference is generated from the commands). The platform spec keeps the design
  and points to them.
- The site is built from `docs/` by gomddoc (the lab's own generator), deployed to GitHub Pages by the release
  workflow. Guides first (quickstart, getting started, agents in production, deployment), then reference, then
  development. A page "When Millstream is the wrong tool" draws on spec section 20 and the Convex analysis.

### 7. Measure after release

- When a proposal is recorded applied (`proposalApplied`), the engine notes the revision and the time. Once the
  pipeline has settled `improve.measure.runs` runs on that revision (default 5) or seven days have passed, the
  insights projector computes, over the same number of settled runs before and after: the figures of the insight the
  proposal answered, the cost per approved item, the intervention rate (reviews decided by a person per item), and for
  `distill` the share of items the code covered.
- The result is stored on the proposal as `outcome` (before, after, predicted by its backtest, and a verdict:
  `met`, `missed` or `inconclusive` when either side has fewer than `improve.measure.minItems` items), served by
  `GET /proposals/{id}` and shown in the Improve view.
- A `missed` outcome opens an insight of a new kind, `missedEffect`, for people; the improve pipeline does not
  trigger on it (it never feeds itself).

## Testing

- Release: a snapshot build in `make test-image` checks the embedded UI and the version string; the workflow's
  signing and publishing steps are exercised only by a real tag.
- Stock actions: golden tests per action (httptest servers, temp directories), conformance in e2e, one reference
  pipeline variant writing its approved items with `sink-file` in the e2e suite.
- Python SDK: unit tests in a container; conformance in e2e.
- Capacity: `make bench` itself; the CI RSS check.
- Signature verification: a fake `cosign` on the `PATH` in e2e (accepts, refuses, missing).
- Measure after release: storetest cases for the outcome record; an insights golden test over a fixture where an
  applied `lessons` proposal meets its prediction and one where it misses.
- Docs: the existing link checks over the site build; every command in the quickstart run for real.

## Exit criterion

On a machine with only Homebrew: `brew install monolithiclab/tap/millstream`, then the quickstart
(`docs/guides/quickstart.md`) reaches an approved review in under ten minutes; the `v0.1.0` artifacts verify with
cosign; `docs/guides/deployment.md` publishes the measured ceiling and RSS; the documentation site is live.

## Order

1. Release pipeline and SDK tag (unblocks the quickstart on a clean machine).
2. Stock actions, then the Python SDK (both reuse the conformance suite).
3. Protocol specification and docs site.
4. Capacity benchmark.
5. Signature verification.
6. Measure after release.

Each is a task of the M6 plan (`docs/plans/`), written when M6 starts.
