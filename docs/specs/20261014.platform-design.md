# Millstream: platform design

Date: 2026-10-14. Status: draft for review. Name chosen in
[the naming note](../research/20261014.naming.md), pending a trademark search.

Millstream is a pipeline platform for processing work that mixes code, LLM agents and human decisions. A pipeline is
a graph of actions connected by persisted streams of items. It runs on a laptop with one binary, and unchanged on a
server. Every pipeline is instrumented by default.

Decisions referenced as `Dn` are recorded in [`docs/decisions.md`](../decisions.md). Features parked for after v1
are in [`ROADMAP.md`](../../ROADMAP.md).

## 1. Purpose

### 1.1 The problem

Most of the automation a forward-deployed engineering (FDE) team builds for a customer has the same shape: a chain
of `input → action → output` steps, where one step's output is the next step's input. Some steps are plain code
(crawl, compute, render), some are LLM agents (classify, score, extract, write), and some need a human to approve.

Built ad hoc, each project re-implements scheduling, fan-out, retries, error collection, cost tracking and a way to
see what happened. The result can't be reused at the next customer, and nobody can answer "how many listings did we
score yesterday, what did it cost, and which ones failed?" without reading logs.

### 1.2 What Millstream is

- **A standard way to define pipelines:** a declarative file describing triggers, streams and steps, validated
  before it runs.
- **A standard action contract:** any program that speaks a small JSON-lines protocol is an action, whatever its
  language, and agents are actions like any other.
- **A durable, observable runtime:** every item is persisted, every state change is an event, and metrics, lineage
  and a live view come for free.
- **One engine from laptop to server:** the same pipeline package runs with SQLite on a laptop, and on Postgres with
  an active engine, a hot standby and nodes on other hosts.
- **Many pipelines per instance:** each pipeline is a package with its own actions, agents, lessons, assets, secrets,
  limits and lifecycle, and a pipeline can read another pipeline's streams.
- **Pipelines that learn:** insights on slow steps, failures, cost and reviews; validated proposals (lessons, prompt
  changes, filters, tuning, code that replaces an agent), drafted in development from production evidence, for a
  person to accept.

It is used by engineers to build and run customer pipelines on customer infrastructure. The engine is open source;
a commercial layer adds what larger organisations pay for (section 17).

### 1.3 Reference example

The running example in this spec, and the end-to-end acceptance test of the platform:

1. Every day, crawl new real estate listings matching a set of filters, from several sources.
2. Score each listing.
3. For each listing scoring above a threshold, compute rentability: fees, renovation work, resale margin.
4. For each listing whose margin clears a threshold, have an analyst approve it.
5. Generate a PDF report for each approved listing.

Later, a deduplication step is inserted between crawling and scoring without touching the other steps.

### 1.4 Success criteria

- The reference pipeline runs end to end on a laptop with `millstream run`, with no service to install.
- Killing the active engine, the standby or any node at any point loses no item and publishes no output twice
  downstream (section 5.11).
- Several pipelines share one instance, and a backlog in one never starves another.
- Inserting a step is a change of a few lines in the pipeline file, and past items can be replayed through it.
- For any pipeline, the UI answers: what is running now, how many items went through each step, what failed and
  why, what each agent step cost, and how often a human intervened.
- On the reference pipeline, evidence from production yields accepted proposals that lower the intervention rate
  and the agent cost without lowering agreement with reviewers.
- A second pipeline imports the reference pipeline's approved listings without changing it.
- The same package runs on a laptop and on a server; only the environment file differs.

## 2. Scope

### 2.1 Goals for v1

- Declarative pipeline file with variables, secrets and CEL expressions; static validation.
- Durable item log with at-least-once delivery and idempotent item identity.
- Action runtimes: local executable, container, LLM agent (harness-agnostic), human review, builtins.
- Cron, manual and webhook triggers.
- Retries, dead letters, replay, pause, resume and cancel.
- Metrics, lineage and a live view built in; Prometheus export.
- Self-improvement: insights, run reports, evidence export, validated proposals, step lessons, and agent steps
  replaced by code with an agent fallback.
- Streams shared between the pipelines of an instance.
- A web UI with a live pipeline graph, run timelines, item browsing, live logs, metrics and a review inbox.
- Many isolated pipelines per instance, each deployed as a package.
- An active engine with a hot standby on Postgres, and pull-based nodes on other hosts.
- Laptop and server (VPS) deployments, with a measured and published throughput ceiling.

### 2.2 Non-goals for v1

- A graphical pipeline editor. The pipeline file in git is the source of truth (D7).
- Multi-tenant SaaS. Each customer gets their own deployment (D6).
- Exactly-once side effects on external systems. Millstream passes an idempotency key; the external system enforces it.
- Sub-second stream processing, and a contractual throughput figure: v1 publishes the ceiling it measures on a
  documented benchmark (D26); agent steps need far less.
- An active-active control plane, with several engines dispatching at once (D22).
- Kubernetes as a runtime: nodes that launch action pods, and a Helm chart.
- Auto-applying proposals: every proposal is accepted by a person.
- Run-wide aggregation (a step that waits for all of a run's items).
- Sharing streams across instances, sharding across stores, and federation of instances.

## 3. Core concepts

| Concept | Definition |
| --- | --- |
| **Item** | The unit of work: a JSON payload and an envelope (section 5.2). Binaries are stored as artifacts and referenced, never inlined. |
| **Stream** | A named, persisted, typed channel of items. Steps read from and write to streams; they never reference each other. |
| **Action** | A reusable, versioned implementation described by a manifest: input, output and config schemas, a kind and a runtime. |
| **Step** | One use of an action in a pipeline: its input streams, outputs, config and execution policy. |
| **Trigger** | What starts a run: `cron`, `manual`, `webhook` or `insight`; a stream imported from another pipeline also starts runs (section 4.12). A trigger `x` publishes one item per run to the stream `trigger.x`, which steps read like any other stream (section 4.6). |
| **Run** | One firing of a trigger, or one replay. Every item belongs to exactly one run. |
| **Pipeline** | One file declaring variables, secrets, triggers, streams and steps, deployed in a **package** with its local actions, lessons and assets (section 4.9). |
| **Engine** | The control-plane process: API, UI, scheduling and dispatch. One is active per deployment; a standby takes over if it dies (section 5.9). |
| **Node** | A process that pulls deliveries and runs actions; one is embedded in the engine on a laptop (section 5.10). |
| **Action process** | The child process (or container) a node starts to run an action. |

Because steps only know streams, the graph is defined by which steps write to and read from each stream:

- Several steps reading one stream each receive every item (fan-out).
- Several steps writing one stream merge their outputs (fan-in of producers, for example several crawlers).
- Inserting a step means pointing it at an existing stream and re-pointing one consumer to its output.

## 4. The pipeline file

### 4.1 Example

```yaml
pipeline: property-sourcing
description: Daily sourcing of renovation opportunities

vars:
  city: Lyon
  maxPrice: 400000
  minScore: 70
  minMarginPct: 15

secrets: [homesiteToken]

triggers:
  daily: { cron: "0 6 * * *", tz: Europe/Paris }

streams:
  listings.raw: { retention: 90d, redact: [/seller/phone] }

steps:
  crawl-homesite:
    action: lab/crawl-homesite@1.2
    in: trigger.daily
    out: listings.raw
    config:
      filters: { city: "${vars.city}", maxPrice: "${vars.maxPrice}" }
      token: "${secrets.homesiteToken}"
  crawl-classifieds:
    action: lab/crawl-classifieds@0.9
    in: trigger.daily
    out: listings.raw
    config:
      filters: { city: "${vars.city}", maxPrice: "${vars.maxPrice}" }

  dedupe:
    action: dedupe
    in: listings.raw
    out: listings.unique
    config: { key: "item.addressNorm + ':' + string(item.surfaceM2)", window: 30d }

  score:
    action: lab/score-listing@2
    in: listings.unique
    out: listings.scored
    concurrency: 8
  keep-good:
    action: filter
    in: listings.scored
    out: listings.shortlist
    config: { expr: "item.score >= vars.minScore" }

  rentability:
    action: ./actions/rentability
    in: listings.shortlist
    out: listings.priced
  keep-profitable:
    action: filter
    in: listings.priced
    out: listings.selected
    config: { expr: "item.marginPct >= vars.minMarginPct" }

  analyst-review:
    action: review
    in: listings.selected
    out: listings.approved
    config: { inbox: analysts, timeout: 72h, onTimeout: reject, editable: [/marginPct, /notes] }

  report:
    action: lab/pdf-report@1
    in: listings.approved
    out: reports.pdf

budget:
  runUsd: 25
```

### 4.2 Top-level keys

| Key | Required | Meaning |
| --- | --- | --- |
| `pipeline` | yes | Identifier, unique in a deployment: lowercase letters, digits and `-`. |
| `description` | no | Shown in the UI. |
| `vars` | no | Named values usable in config interpolation and in CEL (section 4.4). |
| `secrets` | no | Names of the secrets the pipeline uses (section 4.5). |
| `triggers` | yes, unless the pipeline imports a stream | Map of trigger name to trigger definition (section 4.6). A pipeline that imports a stream may have none: its imports open its runs (section 4.12). |
| `streams` | no | Per-stream settings: `schema` override, `retention` (how long its items keep their payloads and artifacts, unlimited by default; section 9.3), `redact` (JSON pointers whose values evidence bundles hash, section 11.2); or an import of another pipeline's stream, `{pipeline, stream}` with an optional `retention` of its copies (section 4.12). Streams are otherwise declared implicitly by use. |
| `steps` | yes | Map of step name to step definition (section 4.3). |
| `budget` | no | Cost guards: `runUsd`, `dayUsd` (section 7.5). |
| `limits` | no | `concurrency`: the most deliveries of this pipeline in flight across all nodes (section 4.10). |
| `placement` | no | `labels` nodes must have; a step's own `placement` overrides it (section 5.10). |
| `insights` | no | `enabled` (default true), `every` (default `15m`), `disable` (a list of kinds) (section 11.1); `check` refuses other keys and unknown kinds. Deployment-wide defaults from the environment file are not read yet. |
| `improve` | no | `enabled`, `budget`, `minSeverity`, `publish`, `backtest`, `distill`, `filter`, `evidence` (sections 11.2 and 11.3). Used in development deployments; defaults come from the environment file. |

A pipeline has no version field. The engine stores each distinct package content as a **revision** (its SHA-256,
plus the git commit when the package is in a clean git tree; section 4.9), and every run records the revision it
used.

### 4.3 Step keys

| Key | Default | Meaning |
| --- | --- | --- |
| `action` | required | An action reference (section 6.2) or a builtin name. |
| `in` | required | Stream name or list of stream names, including trigger streams (`trigger.<name>`; section 4.6). |
| `out` | — | Where outputs go, in one of three shapes (see below). Omitted only for terminal steps. The step graph is computed from `in` and `out` alone. |
| `dlq` | `<step>.dlq` | The step's dead-letter stream (section 5.6). |
| `config` | `{}` | Validated against the action's config schema. Builtins take all their parameters here. |
| `concurrency` | `1` | Maximum deliveries of this step in flight. |
| `rate` | none | Maximum deliveries of this step started per period, for example `10/min`. |
| `placement` | pipeline's | `labels` nodes must have, for example `{ gpu: "true" }`. |
| `retry` | `{maxAttempts: 3, backoff: 10s, maxBackoff: 10m}` | Exponential backoff with jitter for retryable errors. |
| `timeout` | `10m` | Per delivery. On timeout the action process is killed and the error is retryable. |
| `paused` | `false` | Starts the step paused. |
| `fallback` | none | `action`, `when` (`abstain`, `error`), `auditRate`: a second action for the deliveries the first one abstains on or fails (section 11.5). |
| `lessons` | `lessons/<step>.yaml` if present | Agent steps: the step's lessons file (section 11.4). |

**Outputs and routing** (D15). `out` takes exactly one of three shapes, for every step, builtin or not:

```yaml
out: listings.raw                               # one stream
out: [listings.raw, listings.audit]             # every output goes to each stream
out:                                            # route objects: first match wins
  - { when: "item.city == 'Lyon'", out: listings.lyon }
  - { when: "item.city == 'Paris'", out: listings.paris }
  - { when: "true", out: listings.other }       # an explicit catch-all, if wanted
```

- Route objects are evaluated in order when outputs are published, at `done`; each output goes to the first route
  whose `when` holds. `when` is CEL over the output `item`, `vars` and `run`.
- An output that matches no route goes to the step's `dlq` (`<step>.dlq` unless set) as an `unrouted` dead letter
  (section 5.6), so a gap in the routes is visible and replayable, never a silent loss. A step that wants every output
  routed ends its list with a catch-all, `{ when: "true", out: … }`.
- A list holds either stream names or route objects, never both.
- A `when` that fails to evaluate is deterministic, so the delivery fails without retry.

### 4.4 Variables and CEL

Expressions use [CEL](https://cel.dev) (D8): typed, side-effect free, bounded in cost, and with a mature Go
implementation.

- **Variables** are declared under `vars` with their default values, which also give their types. A deployment overrides
  a value with an environment variable named `MILLSTREAM_VAR_<NAME>`, the name in upper snake case: `minScore` reads
  `MILLSTREAM_VAR_MIN_SCORE`. The same variable applies to every pipeline that declares that name, so a value shared by
  several pipelines is set once. Values are resolved in this order, highest first: `--var name=value` on the command
  line, the environment variable, then the pipeline default. A value is parsed as JSON unless the default is a string,
  and must match the default's type; a default of `null` makes the variable required, so the run fails before any
  delivery if it is unset.
- The engine reads these variables at the start of each run, and the resolved set and where each value came from are
  stored on the run, so a run and its dead-letter replays keep their values; a replay run resolves them again.
  `millstream vars <pipeline>` prints each variable with its value, its source and its environment variable name.
- **Config interpolation.** A string in `config` may contain `${expr}`. The expression is CEL evaluated once when
  the run starts, over `vars`, `run` and `secrets`. A string made of a single `${expr}` takes the expression's type
  (`"${vars.maxPrice}"` is an integer); otherwise the result is spliced into the string.
- **Item expressions.** Builtins (`filter`, `dedupe`) and route objects in `out` evaluate CEL per item over `item`,
  `vars` and `run`; `envelope` gives `id`, `key`, `ts` and `attempt`.
- Action config never depends on `item`: the same config applies to every item of a run.
- Every expression is compiled and type-checked by `millstream check`. Evaluation has a cost limit; exceeding it fails
  the item as non-retryable.

| Name | Type | Available in |
| --- | --- | --- |
| `vars` | map | interpolation, item expressions |
| `run` | `{id, trigger, startedAt, revision}` | interpolation, item expressions |
| `secrets` | map | interpolation only |
| `item` | the payload | item expressions only |
| `envelope` | `{id, key, ts, attempt, step}` | item expressions only |

### 4.5 Secrets

A pipeline lists only the **names** of the secrets it uses (`secrets: [homesiteToken]`). Where each value comes from is
deployment knowledge, so the environment file maps each pipeline's names to sources, `{ env: NAME }` or
`{ file: path }`, and that mapping is also the grant: a pipeline can resolve only the names mapped for it, and
`check` fails on an unmapped name. Without an environment file (`millstream run` on a laptop), a name resolves from
the environment variable `MILLSTREAM_SECRET_<NAME>`, following the rule for variables (`homesiteToken` reads
`MILLSTREAM_SECRET_HOMESITE_TOKEN`). Secrets:

- are only usable in config interpolation and as a review step's `notify` webhook (section 8), never in item
  expressions;
- are passed only to steps whose config references them;
- are redacted from logs, events, stored config and the UI, by value as well as by name: each occurrence of a
  value becomes `[redacted:<name>]`. Values shorter than 4 characters are not redacted, since replacing them
  everywhere would garble logs without protecting anything. In M1 the engine builds the redactor from the values it
  resolves at dispatch and hands it to the node with the delivery: the action's stderr, the node's and engine's logs,
  the error stored on a failed delivery (and so its dead letter), and the names and labels of the metrics an action
  reports are redacted. Redaction matches the literal secret value in decoded strings only: an encoded form of it
  (base64, URL-encoded) is not recognised.

### 4.6 Triggers

| Kind | Definition | Run input |
| --- | --- | --- |
| `cron` | `{cron: "<5-field spec>", tz: <IANA zone>, catchup: latest \| all \| none}` | `{trigger, scheduledAt}` |
| `manual` | `{manual: {}}`, optional `inputSchema` | The input given by `millstream trigger` or the UI, validated |
| `webhook` | `{webhook: {rate: 60/min}, inputSchema}`, served at `POST /hooks/<pipeline>/<trigger>` | The request body, validated; authenticated by the trigger's token |
| `insight` | `{insight: {minSeverity: warning, kinds: [...]}}`, both optional | The insight: `{pipeline, insightId, kind, scope, severity, evidence}`; fires for each insight of another pipeline that opens, reopens or escalates (section 11.1) |

Firing a trigger creates a run and one **trigger item**. Its envelope has `step` and `stream` set to
`trigger.<name>`, no parents, generation 0, and `key` set to the scheduled time (cron), the request id (manual,
webhook; a webhook may pass its own in an `Idempotency-Key` header), or the insight's id and the sequence number of
the event that opened or escalated it (insight). Its id is
`hash("trigger", name, key)`, so a cron trigger that fires twice for the same scheduled time, for example after a
restart, creates one run, not two.

The trigger item is published to the trigger's stream, `trigger.<name>`, and steps receive it by reading that
stream with `in` (D14). Trigger streams are roots: only their trigger writes to them, and each item on them starts a
run, while items on every other stream belong to an existing run. The `trigger.` prefix is reserved, and a trigger's
`inputSchema` is the schema of its stream. A step may read trigger streams and ordinary streams together, for
example `in: [trigger.rescore, listings.unique]`.

**Webhook triggers.** `apply` gives each webhook trigger without a token a new one: 32 random bytes, URL-safe base64
after `mswh_`, shown once in its output (and in the API's answer), never again. The store keeps only its SHA-256, in
`trigger_tokens` (section 9.1); applying the package again keeps it, so callers never break, and so does a rollback.
`millstream trigger token <pipeline> <trigger> --rotate` (or the API, or the UI) replaces it and shows the new one
once; the old one stops working at once. An apply interrupted between its revision and its tokens leaves the trigger
without one, answering every request `401`, until the apply is run again or the token rotated.

A request is `POST /hooks/<pipeline>/<trigger>`, outside `/api/v1` and its browser guards (section 12.1): no Host or
Origin check, no `auth.token`, no session cookie. The trigger's token authenticates it, as `Authorization: Bearer
<token>` or, for a sender that cannot set a header, the `token` query parameter (proxies log URLs: prefer the header),
compared by its SHA-256 in constant time; a token is never logged. A request without the right token is `401`,
whatever the pipeline or trigger, so it learns nothing of them. The body is JSON (`Content-Type: application/json`,
`415` otherwise), at most 1 MiB (`413`), and must match the trigger's `inputSchema` (`400`); a manual firing's input
is held to the same schema. `Idempotency-Key`, 1 to 128 printable ASCII characters without spaces, is the request id
and so the run's trigger key (never personal data, section 15.6): a request sent again with it answers `200` with
the run it fired, else a new run answers `202` with its id (`{pipeline, runId, created}`). The run is recorded with
trigger source `webhook`. Each
trigger takes at most its `rate` (`<count>/<s|min|h|day>`, `60/min` by default), from a bucket that starts
full and refills continuously, held in the active engine's memory; a request over it is `429` with `Retry-After`, as
is every request from an address past ten failed token checks in a minute (section 12.1). A paused pipeline's
webhook fires (its deliveries wait), a disabled one's is a `409 conflict`, a trigger the active revision does not have
as a webhook trigger `404`, and a standby engine answers `503` naming the active engine (section 5.9), as it does
every action.

**Insight triggers.** After each pass of the insights projector (section 11.1), the engine reads the
`insightOpened` and `insightEscalated` events recorded since its last pass (on its first, those of the last 24
hours) and fires each insight trigger whose `kinds` (every kind without) hold the insight's kind and whose
`minSeverity` (else the environment file's `improve.minSeverity`, else `warning`) the insight's severity reaches,
for insights of every other pipeline: a pipeline's own insights never fire its triggers. A muted insight fires
nothing. The run, recorded with trigger source `insight`, is keyed by the insight and its event, so an engine that
reads an event again (after a restart, or a standby taking over) finds the run instead of firing another, and an
insight that reopens or escalates later fires again. An insight trigger takes no `inputSchema`: its stream carries
insights. This is how the `improve` pipeline starts (section 11.3).

Firings missed while no engine was running are handled by the trigger's `catchup`: `latest` (default)
fires the most recent missed time once, `all` fires each missed time, `none` records them as skipped firings. Any
trigger can also be fired by hand (`millstream trigger`, the UI): firing a cron trigger by hand opens a run recorded
as manual, keyed by its request id, and does not affect catch-up, which resumes after the last scheduled time the
trigger fired or skipped.

### 4.7 Builtins

Builtins are the steps that need the engine's own state (D16); everything with a side effect is an action.

| Builtin | Config | Behaviour |
| --- | --- | --- |
| `filter` | `expr` | Emits the item unchanged when `expr` is true; otherwise marks the delivery `filtered`. |
| `dedupe` | `key`, `window` | Emits the item unless an item with the same key passed this step, in the same generation, within `window`; otherwise `filtered` with reason `duplicate` (section 5.11). |
| `review` | section 8 | Parks the item until a human decides (the Park unit), or passes it at once when `autoApprove` holds. |

Builtins never reach a node. The dispatcher leases their deliveries in the same Lease unit as a node's pull, under
that node's lease, and completes each in the engine before the pull returns: `filter` evaluates `expr` over `item`,
`envelope`, `vars` and `run` and passes the item on through the Done unit (same key and payload, so routing
applies) or applies the Filter unit with reason `exprFalse`; `dedupe` evaluates `key` and applies the Dedupe unit
(section 5.11); `review` evaluates `autoApprove` and applies the Park unit (section 8). An expression that fails to
compile or evaluate for an item ends the delivery dead with class `expr`,
since it is deterministic. A builtin's `config` is not interpolated: its strings are CEL expressions and a duration,
validated by `check`. Without `window`, a key holds back its duplicates for ever. A pull leases again while its
builtins complete, to fill the node's free slots (at most the slots a remote node registered with), but returns
what it holds once a third of the lease has passed, or a remote node's wait: the leases it took for the node are
renewed only once the node holds them, and a backlog of builtins must not let them expire.

Every builtin takes its parameters under `config`, like any action, and its outputs in `out`. Routing is not a
builtin: any step routes through route objects in `out` (section 4.3). Writing items out to a file or a webhook is
done by stock actions published by the project (`millstream/sink-file`, `millstream/sink-webhook`), resolved like any
registry action.

Thresholds live in `filter` steps, not inside actions, so one scoring action serves every customer and every
threshold is visible in the pipeline file.

### 4.8 Validation

`millstream check` runs before every `run`, `serve` reload and `apply`, and fails on:

- unknown actions, triggers or streams, or steps without `in`;
- an `out` list mixing stream names and route objects, or a `when` that does not compile;
- a step whose `out` is a `trigger.*` stream, or a stream named with the reserved `trigger.` prefix that matches no
  trigger;
- a secret name the environment does not map for the pipeline;
- cycles in the step graph, or between pipelines through imported streams; an import of a stream that does not
  exist; a step whose `out` names an imported stream; a producer revision that removes an imported stream or breaks an
  importer's contract (section 4.12), unless `--force` is given;
- a fallback with `auditRate` where either action does not declare `effects: none`;
- streams that are read but never written; `out` streams that nobody reads are a warning only;
- config that does not match the action's config schema, after interpolation types are inferred;
- CEL expressions that do not compile or type-check;
- **schema incompatibility** between producers and consumers, within the subset of section 4.11; parts of a schema
  outside the subset are listed as not statically checked, and every item is also validated against the consumer's
  input schema at runtime (section 5.5);
- an agent step that can reach a step whose action declares `effects: external` without a `review` step that has no
  `autoApprove` in between (warning, advisory only; section 15.4).

`millstream check a/ b/` also checks the packages against each other (imports, contracts, cycles; section 4.12): an
import from a pipeline that is not among them is a warning that it is not checked. `apply` checks the packages
applied against every other pipeline of the instance.

`millstream graph` prints the resolved graph as Mermaid or DOT.

### 4.9 Packages

A pipeline is deployed as a **package**: a directory holding the pipeline file and everything it uses (D13).

```text
property-sourcing/
  pipeline.yaml      the pipeline file
  actions/           local actions
  lessons/           per-step lessons (section 11.4)
  evals/             pipeline-level eval cases
  assets/            static files for actions: templates, reference data, shared prompt fragments
  millstream.lock
```

- A **revision** is the SHA-256 of the package's content, so a change to a local action, a lesson or an asset is a
  new revision, exactly like a change to `pipeline.yaml`.
- **Local actions are never built by Millstream.** A local action is either an `exec` action whose binary or script
  is in the package (per platform under `bin/<os>-<arch>/` when it is compiled), or a `container` action whose
  manifest names an image built by the user's own toolchain; `millstream lock` pins that image by digest, like a
  registry action.
- An environment file (`millstream.yaml`, section 14) at the root of the package directory is not part of the
  package: it describes where the package runs.
- `millstream apply <dir>` uploads the package as a content-addressed bundle. Nodes fetch it by hash and cache it
  (section 5.10); assets are materialised read-only under `MILLSTREAM_ASSETS` for every action of the pipeline.
- `millstream run <dir>` runs a package locally; a lone pipeline file is a package of one file.

### 4.10 Isolation between pipelines

An instance runs several pipelines of one organisation (D6), each isolated from the others:

| Concern | Mechanism |
| --- | --- |
| Data | The pipeline id scopes streams, items, deliveries, runs, events, metrics, insights, proposals, inboxes and budgets. Artifacts are stored under a per-pipeline prefix. A pipeline that imports another's stream gets its own copies of its items (section 4.12) |
| Secrets | A pipeline resolves only the secret names the environment file maps for it (section 4.5) |
| Capacity | `limits.concurrency` caps a pipeline's deliveries in flight across all nodes, and the dispatcher serves pipelines with ready deliveries in round-robin, so one pipeline's backlog never starves another: by name, each lease carrying on after the pipeline served last, whichever node asks; a pipeline at its limit, or whose steps are at their `concurrency` or out of `rate`, sits its turns out without handing them to the next |
| Placement | `placement.labels` on the pipeline or a step restricts its deliveries to nodes with those labels (section 5.10) |
| Lifecycle | Each pipeline is applied, paused, disabled, rolled back to an earlier revision or deleted on its own |
| Access | One token for every pipeline in the open-source edition; RBAC per pipeline in the commercial edition |

### 4.11 Schema compatibility

`check` proves that producers and consumers fit within a defined subset of JSON Schema 2020-12, says exactly where it
cannot, and leaves the rest to runtime validation (section 5.5) (D17).

- **Supported:** `type` (one type, or one type and `null`), `properties`, `required`, `items` as a single schema,
  `enum`, `const`, `allOf` (merged before checking), and `$ref` to the schema's own `$defs` (resolved, recursion
  allowed).
- **Rule.** For every property the consumer requires, every producer must declare it **and require it**; the
  producer's types must be a subset of the consumer's (`integer` counts as `number`, and `null` only where the
  consumer allows it); a producer's `enum` or `const` must be a subset of the consumer's `enum`; arrays and objects
  are checked recursively. Extra producer properties are allowed.
- **Not provable:** an unconstrained producer value against a consumer `enum` is a warning, not an error.
- **Outside the subset:** `anyOf`, `oneOf`, `not`, `if`/`then`/`else`, `patternProperties` and `dependentSchemas` mark
  that subtree **not statically checked**; `check` lists each one as a warning. `format`, `pattern` and numeric or
  length bounds are enforced at runtime only.
- **Refused:** a `$ref` to anything outside the schema document, which would make `check` depend on the network and
  revisions irreproducible.
- Schemas generated by the Go SDK stay inside the subset, so the common path is fully checked.

### 4.12 Shared streams

A pipeline reads another pipeline's stream by declaring it under `streams`, under a name of its own (D19). Steps then
read that name with `in` like any stream. Declaring the stream is all it takes: within an instance, which belongs to one
organisation (D6), every stream can be imported, and the producer does not change.

```yaml
# deal-flow (consumer)
streams:
  approved: { pipeline: property-sourcing, stream: listings.approved }
steps:
  notify-buyers:
    action: lab/notify-buyers@1
    in: approved
```

- **Imported streams are roots,** like trigger streams: only the import writes to them (`check` refuses a step whose
  `out` names one), and items on them start runs. A pipeline that imports a stream needs no trigger. Any stream of the
  producer can be imported, its trigger and dead-letter streams included, and so can a stream the producer itself
  imports: copies flow down a chain of imports.
- **Contract.** The producer's output schema for the stream is the contract: the consumer's steps reading it, directly
  or through builtins, are checked against it with the rule of section 4.11, across the two packages (and along a
  chain, against the first producer's schema).
- **Runs.** Items a producer run publishes on the stream open **one run in each importing pipeline**, keyed by the
  producer run (`hash("import", stream name, producer run id)`, the stream named as the consumer names it). That
  consumer run, of kind `import` (its trigger the stream, its trigger key the producer run), receives every item the
  producer run publishes on the stream, and stays open until the producer run settles, since more items may still
  arrive: `running`, or `waitingReview` while it has nothing left of its own and the producer run waits only on
  reviews. It settles in the transaction that settles the producer run, or later, with its own last delivery.
- **Items.** The consumer gets its own copy of each item, published to the imported stream in the same transaction as
  the producer's item (section 5.11). The copy's id is `hash("import", stream name, producer item id)` and its parent
  is the producer's item, so lineage crosses pipelines while data, retention and erasure stay per pipeline (the import
  declaration's `retention` applies to the copies). The copy
  keeps the item's key, payload and artifact references; the first time a node opens such an artifact, the engine
  copies its file into the consumer's artifacts (section 9.2). Only an item the producer newly inserts is copied: a
  retry that republishes it under the first-commit rule (section 5.2) copies nothing again, and an import declared
  later receives none of the items published before it (back-fill them, below).
- **Each pipeline stays its own.** The consumer run is pinned to the consumer's revision active when it opens, charged
  to the consumer's budget, and its failures go to the consumer's dead letters. Its variables are those resolved when
  that revision was applied, as a firing resolves them, since the run opens inside the producer's Done, where no
  environment is read: applying a pipeline that imports a stream fails when its variables or secrets do not resolve.
  The streams a pipeline imports are always its active revision's: a rollback brings back that revision's imports
  and the variables it was applied with.
  A consumer run opened for a producer run of generation 0 takes generation 0; one opened for a replay run takes the
  consumer's next generation, so its outputs and dedupe keys are its own. A paused or disabled consumer still
  receives items, as pending deliveries. Cancelling a producer run stops new items; consumer runs already open finish
  with what they received. A consumer run cancelled receives nothing more.
- **Replay.** A producer replay run publishes like any run, so importers get a new consumer run for it. A dead-letter
  replay that reopens a producer run reopens its consumer runs too, and a copy published into a consumer run that had
  settled reopens it. A pipeline that starts importing a stream back-fills from the producer's retained history:
  `millstream replay --stream approved --pipeline deal-flow --since 7d` opens a consumer replay run, in a new
  generation, over the producer items on the stream whose payload has not expired (narrowed by `--since` and
  `--where`; `--run` is refused): each is copied under the id the import gives it, or found when the consumer
  already holds it, and delivered to every step reading the stream.
- **Validation across pipelines.** `check` and `apply` look at every pipeline of the instance. They refuse an import
  of a pipeline or stream that does not exist, a producer revision that removes an imported stream or breaks an
  importer's contract, unless `--force` is given, and they refuse cycles between pipelines. A finding a producer
  revision causes while its importer is unchanged is reported on the producer, a warning under `--force`; a finding
  of an importer's own revision (its new import, its new contract) is always an error. Should a cycle reach the
  store all the same, a copy never re-enters a pipeline it came through in the same transaction.

## 5. Execution model

### 5.1 Overview

The **control plane** is one active engine, optionally with a standby (section 5.9): a scheduler (triggers), a
dispatcher (deliveries), the review inbox, the HTTP API and the metrics projections, all over one **log store**
(section 9). Actions run on **nodes** that pull deliveries (section 5.10); on a laptop one node is embedded in the
engine. Nodes and action processes are stateless and disposable; the log store is the only state (D2).

### 5.2 Item identity and envelope

Every key and every multi-word value that Millstream defines is lowerCamelCase (D18): in JSON (the item envelope, the
action protocol of section 6.3, the HTTP API, event payloads) and in YAML (the pipeline file, action manifests, the
environment file, lessons), for example `runId`, `autoApprove`, `maxCostUsd`, `awaitingReview`. Acronyms are written
as words. Other names keep their own conventions: metric names follow Prometheus (`tokens_in`), log-store tables and
columns follow SQL (`staged_outputs`), CLI flags are kebab-case, environment variables are upper snake case, and names
chosen by users (pipelines, steps, streams, triggers, vars, payload fields) follow their own grammar; the examples use
camelCase for vars and payload fields.

```json
{
  "id": "it_7f3a…",
  "key": "https://www.homesite.example/annonces/123",
  "runId": "run_2026-10-14T06:00Z_daily",
  "stream": "listings.raw",
  "step": "crawl-homesite",
  "parents": ["it_19c2…"],
  "generation": 0,
  "ts": "2026-10-14T06:00:12.481Z",
  "payload": { "...": "..." },
  "artifacts": [{ "name": "photo-1.jpg", "sha256": "…", "size": 183402, "type": "image/jpeg" }]
}
```

Item ids are deterministic (D9):

```text
id = hash(producing_step, out_stream, input_item_id, generation, key ?? output_index)
```

- **Outputs publish on `done`** (D20). An action's outputs are staged with the attempt and published, routed and
  delivered downstream in the transaction that records `done`. An attempt that fails, loses its lease, ends dead or
  is cancelled publishes nothing, and its staged outputs are discarded.
- **Keys.** A delivery with a single output may omit `key`. A delivery with more than one output must key every one
  of them, since `output_index` is only stable for a single output, and the keys must be distinct, since two outputs
  under one key would share an id; the engine checks this at `done` and fails the delivery as a non-retryable
  key-rule error otherwise. A crawler keys by listing URL; the Go SDK enforces the rule.
- **Items are immutable and the first commit wins.** A retried delivery republishes its outputs under the same ids.
  An output whose id already exists with the same payload hash is a no-op. With a different payload, the existing item
  is kept, the new payload is discarded and a `nondeterministicOutput` event is recorded, counted per step.
  Downstream steps therefore see each output once even though the action ran twice.
- **Generation.** Every run has a generation: 0 for runs started by a trigger, and a value taken from a per-pipeline
  counter for each replay run (section 5.7). Every delivery and output of a run carries it, so a replay produces new
  items rather than colliding with earlier ones.
- A long crawl that should feed downstream steps early splits its work into several deliveries (one per source or per
  page of results), since each delivery publishes when it is done.

### 5.3 Deliveries

A **delivery** is one (step, input item, generation) triple, owned by one run. It is created when an item is
published to a stream the step reads (including a copy on an imported stream, section 4.12), or by a replay
(section 5.7).

```text
pending → leased → done
                 → filtered           (builtin decided not to pass it on)
                 → awaitingReview     → done | filtered
                 → failed → pending   (retryable, attempts left, after backoff)
                          → dead      (non-retryable, or attempts exhausted)
dead → pending                        (dead-letter replay, retry budget restarted)
pending | failed | leased | awaitingReview → cancelled   (run cancelled, or its item purged)
```

- **Leases.** A leased delivery has an owner node, a fencing token and an expiry, renewed by the node's heartbeat.
  When a node or the engine disappears, its leases expire, and messages carrying a stale fencing token are refused
  (section 5.10). An expired lease consumes its attempt, like a retryable failure of class `leaseExpired`: the
  delivery returns to `pending` after backoff while attempts remain, and ends `dead` with its dead letter once they
  are exhausted, so an item that kills every node it lands on stops. Lease duration defaults to 60 seconds.
- **Ordering.** Deliveries of one step are dispatched oldest first. No ordering is guaranteed across steps or across
  concurrent deliveries.
- **Pause.** A paused step keeps receiving deliveries in `pending` and dispatches none.
- **Cancellation.** Cancelling a run moves its pending, retry-waiting and awaiting-review deliveries to `cancelled`,
  and discards its open dead letters (section 5.6): a cancelled run is never replayed.
  A leased delivery is not interrupted, but when it ends its outputs are discarded, it is recorded as `cancelled`
  with its cost, and it creates no further work. Outputs published before the cancellation, and their external
  effects, are not undone.

### 5.4 Runs

A run is **settled** when every delivery it owns is in a terminal state (`done`, `filtered`, `dead`, `cancelled`) and,
for a run opened by an imported stream and not cancelled, the producer run is settled too (section 4.12). Fallback
audits are records, not deliveries, so they never hold a run open (section 11.5). Run states:

| State | Meaning |
| --- | --- |
| `running` | Some deliveries are pending, leased or waiting to retry. |
| `waitingReview` | Only deliveries in `awaitingReview` remain. |
| `succeeded` | Settled with no open or discarded dead letter. |
| `completedWithErrors` | Settled with at least one dead letter (section 5.6) still open, or discarded. |
| `cancelled` | Cancelled by a user (section 5.3). |

A dead-letter replay returns a settled run to `running` until it settles again.

### 5.5 Errors

| Class | Source | Handling |
| --- | --- | --- |
| Retryable | `{"type":"error","retryable":true}`, action process crash, timeout, a protocol violation (malformed line, unknown message type; the process is killed), agent output failing schema validation | Retry with backoff, then dead |
| Non-retryable | `retryable: false`, input failing the step's input schema, CEL cost limit exceeded, a key-rule violation (several outputs, not all keyed or with a key repeated), an item too large for a protocol line | Dead immediately |
| Config | Interpolation failure at run start, missing secret | The run fails before any delivery; recorded as a run error |

The engine checks a delivery when it dispatches it, before any process starts: an item failing the action's input
schema is dead with class `inputSchema`, and a config that fails to interpolate, misses a secret or fails the
action's config schema is dead with class `config`. In M1 config errors surface this way, on each delivery, rather
than failing the run up front.

Every error is stored on its delivery as the attempt number, the error class and a message truncated to 4 KB.
The details stay where they already are, found by the delivery's keys: the logs kept by the host (section 10.3) and,
for agents, the transcript artifact (section 7.2). Nothing is copied.

### 5.6 Dead letters

A step's dead-letter stream is its `dlq` key, `<step>.dlq` by default. It is an ordinary stream: several steps may
share one, and a step may read it, for example to alert. A dead letter is a new item on that stream:

- **Kinds.** `dead`: the input item of a delivery that ended dead. `unrouted`: an output that matched no route object
  (section 4.3); its delivery still completes and its other outputs are published.
- **Item.** Its id is `hash("dlq", dlq stream, origin delivery id, output id or "", failure sequence)`, where the
  failure sequence counts the origin delivery's earlier dead letters, so each failure is a new item that readers of
  the stream see; its payload is
  `{kind, originStep, originDelivery, error, item}`, where `item` is the dead input or the unrouted output; its parent
  is that item; it belongs to the origin run.
- **State.** The `dead_letters` table holds each dead letter's state: `open`, `replayed` or `discarded`. A run's
  outcome counts its open and discarded dead letters (section 5.4).
- **Replay** (`millstream replay --from dlq --run <id>`) reopens the origin run. A `dead` letter moves its delivery
  back to `pending` with its retry budget restarted: its attempts are numbered on from the dead one, never reused
  (attempt artifacts such as transcripts are kept by number), and `retry.maxAttempts` counts from the replay (the
  delivery's `attempt_base`). Nothing was published by the dead attempt, so its outputs keep their ids.
  An `unrouted` letter re-evaluates the routes on the stored output and publishes it. Replay uses the run's revision,
  or the active one with `--migrate`, which records the revision change on the run; fixing a route usually needs it.
  The dead letter becomes `replayed` and stays so; a new failure creates a new dead letter, under the next failure
  sequence.
- **Discard** (`millstream dlq discard`) marks dead letters `discarded`: the loss is accepted and recorded.
  Cancelling a run discards its open dead letters too, since a cancelled run cannot be replayed.

### 5.7 Revisions, replay and topology changes

- **Runs are pinned to their revision** (D21). A run executes entirely on the revision it started with: graph, action
  digests, config, vars and lessons. Applying or rolling back a revision affects runs started afterwards; in-flight
  runs finish on their own revision, so a run waiting three days on a review keeps its prompt, and a step removed by
  the new revision still completes for the runs that started before it.
- **Replay** creates a run of kind `replay` that owns new deliveries for a selection of items on a step:
  `millstream replay --step score --since 7d`, `--run <id>`, `--where '<CEL>'`. It runs on the active revision (or
  `--revision`) and takes a new generation in the same transaction, so its outputs and its dedupe keys are its own.
  Two concurrent replays are two runs with distinct generations. This is how a newly inserted `dedupe` step is
  back-filled, how last week's listings are re-scored with a new prompt, and how a lessons change is checked.
  - **Selection.** The items on the step's input streams in the replay's revision, from every generation, narrowed by
    `--since` (published within the duration), `--run` (one run's items) and `--where` (CEL over `item`, `envelope`,
    `vars` and `run`, evaluated by the engine before the run starts). Items are immutable, so the selection is read
    outside the transaction; a selection with no item is refused.
  - **Run.** Its id is `run_replay_<request id>` (`--request-id`, generated when absent), so a replay retried after
    a crash returns the run it already started instead of starting another. It has no trigger, its trigger key is
    the request id, and its variables are resolved when it starts, as for a firing. Its deliveries, outputs and
    everything downstream carry its generation, and its outputs belong to it.
- **Migrating a run** (`replay --from dlq --migrate`, section 5.6) is refused while a live delivery of the run
  (pending, leased or awaiting review) belongs to a step the active revision does not have: that delivery would be
  left with no step to run. Let the run settle, or keep the step, first. A delivery whose step is missing from its
  run's revision all the same ends `dead` on the default `<step>.dlq` when it reports.
- Replaying an item whose payload is gone (expired or erased, section 9.3) fails explicitly; it is never replayed from
  a tombstone. A back-fill leaves such items out.

### 5.8 Backpressure

The log store absorbs bursts: a slow step builds a queue, visible as queue depth and oldest-pending age, and never
slows its producers. Throughput is bounded by step `concurrency` and `rate`, the pipeline's `limits`, and the
capacity of the nodes that match its placement.

### 5.9 Active engine and standby

One engine is active per deployment (D22). On Postgres, a second `millstream serve` on the same store runs as a **hot
standby**.

- **Leadership.** At start-up an engine opens a dedicated connection and takes a Postgres session advisory lock for
  the deployment. The holder is the active engine; a standby blocks on the lock. That connection is also the engine's
  only write connection, so an engine without the lock cannot write: there is never a second writer, whatever the
  clocks or the network do. An engine whose write connection fails stops dispatching at once and steps down: its
  embedded node abandons its deliveries without reporting them, and the process stands by again rather than exiting.
  When the active engine dies or loses its database session, Postgres releases the lock; the standby takes it,
  rebuilds its in-memory state from the store and starts dispatching, typically within 30 seconds. While it waits, a
  standby serves the reads and the UI from a read-only connection (section 12.1).
- **Watching the write connection.** With `engine.keepalive` k and `engine.lockCheck` c (5 seconds each by default,
  section 14): TCP keepalives every k after k idle on both ends (the server's through the session's
  `tcp_keepalives_*` settings) and a TCP user timeout of 3k; the idle writer pings every c, and a ping unanswered for
  2k, or a batch for 3k, loses the session; the server ends a session silent for c + 2k (`idle_session_timeout`),
  which a healthy engine's pings never allow. So an engine whose process dies releases the lock at once (its socket
  closes), and one whose host or network dies, even behind a proxy that keeps its TCP connection open, steps down
  and has its lock released within c + 2k, 15 seconds by default. The failover tests measure, with c = 0.5 s and
  k = 1 s: about 2.5 s from a network cut to the step-down and to the standby's lock; a few milliseconds from a
  killed process or an ended session to the standby's lock; and its first dispatch then waits for the dead engine's
  leases to expire (section 16).
- **Identity.** Each engine has an id (its host name and a random suffix) and, on taking the lock, records itself in
  the `leadership` table under the lock with the next **epoch**; the write session's `application_name` names it, so
  any engine lists who leads and who waits (`/api/v1/nodes`). Nodes following the active engine learn its id and
  address from a standby's refusal, and its epoch at registration (section 5.10).
- **Single writer** (D23). The active engine applies every state change through one writer loop that batches
  operations into transactions (group commit). Each atomic unit of section 5.11 is applied whole within a batch, and
  the writer assigns event sequence numbers in commit order. Reads (API, UI, projections) use a separate connection
  pool. SQLite uses the same writer loop. On SQLite, CLI commands that change state (`trigger`, `cancel`, `replay`,
  `dlq discard`, `pause`, `resume`) write from their own process, through their own writer loop, under SQLite's file
  locking, while a `millstream run` may be writing: each unit is still one transaction, and the database serialises
  the writers. On Postgres they go through the active engine's API (`--server`, section 13), or, with `--direct`,
  take the leadership lock themselves while no engine runs; commands that only read use a read-only connection
  without the lock.
- **Coordination in memory.** Step `concurrency` and `rate`, pipeline `limits` and the round-robin across pipelines
  (section 4.10) are enforced in the active engine's memory, for its embedded node and remote nodes alike: leases
  are taken one pull at a time, under the engine's lock, against the deliveries it holds in flight. Budgets reserve
  before they spend: leasing an agent delivery writes a reservation of its `maxCostUsd` (that of its action in its
  run's revision) on the delivery, counted against the run and day budgets, and completion replaces it with the
  reported cost (the sum of the attempt's `cost_usd` metrics). A delivery whose node dies keeps its reservation
  as spent, and so does an attempt the runtime loses (a crash, a timeout) when it reported less, so unreported
  spend is charged in full; retries, fallbacks, audits and backtests reserve the same way, so a budget is
  never exceeded. The check is part of the Lease unit, so concurrent leases cannot pass it together; the engine
  only names the agent steps and their reservations. Reservation is what makes concurrent leases safe, so an agent
  step of a pipeline that sets `budget.runUsd` or `budget.dayUsd` must set `maxCostUsd`: `check` refuses one that
  does not, and the engine fails its deliveries at dispatch as `config` errors rather than run them unreserved.
- **Takeover.** The new active engine rebuilds slots and reservations from leased deliveries, and starts each step's
  rate empty, its first token one interval in, so a failover never causes a burst. Each term of leadership runs a
  new engine: its leases in flight, rate buckets, cron schedules (resumed from the store's last firings, with their
  catch-up rules), revision caches and review timeouts start from the store, and budgets are the store's
  reservations. Background work (cron scheduling, the insights
  projector, rollups, retention) runs as loops in the active engine. Triggers fire once across a failover, because
  run and trigger item ids are deterministic and unique in the store (section 4.6).
- **Nodes during a failover** keep running their deliveries, reconnect to the new active engine (a standby answers
  `503` with the active engine's address until it takes over) and renew their leases. The 60-second lease outlasts a
  normal failover, so in-flight work is not redone.
- **Postgres availability** is the database's job: a managed service or a replicated setup. Millstream reconnects
  after a database failover. SQLite has no standby; on a laptop or a single VPS, systemd or Docker restarts the
  engine, which resumes from the store.
- **Throughput** (D26). v1 publishes the ceiling it measures on the benchmark workload of section 16, kept as a
  regression baseline in CI, rather than committing to a figure. Nodes lease deliveries in batches and the writer
  group-commits; the pipeline id is the leading key of every table, so pipelines can later be sharded across stores.

### 5.10 Nodes

Actions run on **nodes** (D24): `millstream node --join <url>` on a VM, a GPU machine or an on-premises server, with
the deployment's node token in `MILLSTREAM_NODE_TOKEN`. On a laptop, `millstream run` embeds one node that pulls over
an in-memory transport, so the same dispatcher, leases and protocol run everywhere; the embedded node allows `exec`
(section 15.3).

- **Registration.** A node registers its id, version, labels and capacity per runtime: `exec` (only with
  `--allow-exec`), `container` (Docker or Podman), and the agent harnesses it has. It keeps one long-lived HTTP/2
  connection to the active engine and follows it across a failover (section 5.9).
- **Pull.** A node with free slots asks for deliveries matching its labels. The engine leases them from the store,
  following placement, limits and the round-robin across pipelines, and sends each with its payload, resolved config
  (secrets included), signed URLs for input artifacts, and the package hash. The node runs the action with the stdio
  protocol of section 6.3, so actions do not change. Nodes never connect to the store.
- **Failure.** A heartbeat every 5 seconds renews all of a node's leases. A dead node's leases expire after
  `lease.duration` (60 seconds) and its deliveries return to `pending` for other nodes, each expiry consuming an
  attempt (section 5.3). Every lease carries a **fencing token**: a node cut off and later reconnected has its
  `done` and `error` refused, so a stale owner can never complete a delivery that was handed to another node. When
  the active engine fails over, nodes reconnect to the new one and resend buffered messages; deterministic ids and
  fencing make that safe.
- **Draining.** `millstream node drain` or SIGTERM stops pulling, lets in-flight deliveries finish within a timeout
  and releases the node, for rolling upgrades.
- **Data on nodes.** Packages are fetched by hash and cached. Artifacts move directly to and from the S3-compatible
  store through signed URLs; with a local artifact directory, the engine proxies them. Secrets stay in memory and in
  the delivery's tmpfs working directory, never on disk.
- **Placement.** A delivery no node can take (no matching label or runtime) is shown as **unschedulable** and raises
  an insight, rather than waiting silently.

**The protocol** (M4). Remote nodes speak JSON under `/node/v1` (section 12.1): HTTPS, HTTP/2 when the engine serves
`tls`, or plain HTTP to a loopback engine only. Every request carries the node token as a bearer token, compared in
constant time, and names the node, which must have registered with the engine serving it.

- `register` sends the node's id (kept in its state directory, so it outlives restarts), the protocol version
  (another is refused), its version, labels (`--labels k=v,…`), slots and runtimes: `exec` only with `--allow-exec`
  (a node without it refuses exec processes itself, unsandboxed agents included), `container` when the runtime the
  environment file names is installed, and `agent:<harness>` for each harness it can run (`api` whenever it runs the
  adapter at all, `claude-code` in the sandbox or with `claude` on its PATH).
- `pull` is a long poll, and the engine leases within what is left of its wait, so it answers before the node's request
  times out; the node heartbeats beside it, on its own schedule. The engine leases with the Lease unit it uses for its
  embedded node, leaving out the steps whose placement the node does not match: the runtime the step's action needs
  (none for a builtin, which runs in the engine whatever node leased it) and the step's labels, else its pipeline's. A
  registered node never takes a delivery it cannot run; `run`'s embedded node, a laptop's only node, takes every
  delivery. A delivery the engine leased is always resolved into an assignment or failed, even when the pulling request
  is cancelled meanwhile.
- Each assignment carries the lease, the item message, the step's timeout, the secrets resolved for it (kept in the
  node's memory) and the action as the engine resolved it: identity, digest, the package's hash, the config
  interpolated for the run, and for an agent the secret names and the model's prices. The node fetches the package by
  hash into its cache (`packages/<hash>`, written whole or not at all) and resolves the action again there, so that
  an exec action's `bin/<os>-<arch>` program is the node's platform's. A delivery that cannot run on the node (its
  package cannot be cached, an agent without a sandbox) is failed at once with its class.
- `heartbeat` renews every lease the node holds, and runs while it holds none too: it is how the engine knows the
  node is alive (its last heartbeat is stored). `done` and `error` are resent until the engine answers, across a
  reconnection or a failover; an answer refusing them as stale drops the result on the node. The engine accepts
  `done`, `error` and `leave` with `{"accepted": true}`, and the node takes nothing else for an acceptance, an
  empty answer included. A request the engine cannot answer now (its term ended mid-request, its store closed,
  read-only or unreachable) is answered `503 unavailable` with `Retry-After`, never as a success.
- The node's logs, its deliveries' and its actions' stderr among them, are relayed to the engine's log and live tail
  every second. Its deliveries' working directories are created on a tmpfs when it has one (`$XDG_RUNTIME_DIR`,
  `/dev/shm`, the temporary directory), else 0700 in the temporary directory, and removed when their process ends.

**Following the active engine.** `--join` lists the engines (`--join https://a:7070,https://b:7070`). A node tries the
next one at once when one cannot be reached, and backs off (250 ms doubling to 5 s) once it has tried them all. A
standby answers every node request `503` naming the active engine in `X-Millstream-Active-Address`, which the node
follows (an engine listening on an unspecified address names nothing reachable: the node tries its next URL). A new
active engine does not know the node and answers `unregistered`: the node registers again and resends what it
buffered; its leases still hold under their fencing tokens.

**Draining.** `millstream node drain` signals the node running from the state directory (its pid file), as SIGTERM
does: it stops pulling, lets its deliveries finish within `--drain-timeout`, then leaves: the engine ends what it
still holds at once, each attempt consumed, and records it draining until it registers again from a new process:
each node process sends a nonce of its own at registration, so a draining node registering again from the same
process, with a new active engine after a failover, stays draining.
`POST /api/v1/nodes/{node}/drain` drains a node from the engine's side: it is leased nothing more and finishes what it
holds.

### 5.11 Transactions

Every guarantee in this section rests on a short list of atomic units. Each is applied whole by the engine's writer
loop (section 5.9), inside one transaction, on Postgres and SQLite alike.

| Operation | Commits together |
| --- | --- |
| Lease | After the engine's in-memory checks (concurrency, `limits`, rate), check the budgets of an agent delivery (section 7.5): when its reservation fits, write it on the delivery; otherwise leave the delivery pending, and the first time a budget stops one at its current limit, pause the pipeline's agent steps and record `budgetReached`; mark the leased deliveries `leased` with their owner, a new fencing token and an expiry; record the events |
| Done | Check the fencing token; check the key rule (section 5.2); route the staged outputs (section 4.3) to their streams, or to the `dlq` as `unrouted` dead letters; insert each item or apply the first-commit rule; create the consumer deliveries, unique on (step, item, generation); mark the delivery `done`; release its slots; settle its budget reservation; record the events. For a delivery of a cancelled run: discard the outputs and mark it `cancelled` instead |
| Fail | Check the fencing token; discard staged outputs; settle its budget reservation (charged in full when the attempt's cost went unreported); schedule the retry, or mark the delivery `dead` and publish its dead letter; record the events |
| Abstain | Check the fencing token; discard staged outputs; keep the attempt's artifacts and settle its budget reservation; hand the delivery to the step's fallback action, pending at once with its retry budget restarted (attempts numbered on), recording `deliveryFallback`; or, when the step has no fallback for `abstain` or the fallback itself abstained, fail it as non-retryable (class `abstain`). A non-retryable Fail hands the delivery to the fallback the same way when `when` lists `error`. For a delivery of a cancelled run: mark it `cancelled` |
| Audit | Done of a delivery the primary covered samples it at the step's `auditRate` and inserts its audit with the primary's outputs; Lease leases pending audits after the deliveries, within the steps' slots, reserving an agent fallback's `maxCostUsd` against the day budget only (one with no room is cancelled, pausing nothing); EndAudit checks the fencing token, records the fallback's outputs and their agreement (or its failure), settles the reservation and charges the day, never retried; an expired lease fails the audit, its reservation charged in full |
| Stream import | Part of every unit that publishes (Done, and the units that pass items on as Done does, dead letters and back-fills included): for each item newly inserted on a stream other pipelines import, publish its copy on each importer's stream, opening the importer's run for that producer run on its first item, and, the copy being an item like any other, its deliveries and its own copies down a chain of imports. Settling a run settles the import runs it held open; reopening it reopens them |
| Proposal acceptance | Check that the proposal is `ready` and its patch hash is the one the decider saw; check that the pipeline's active revision is the proposal's base, else mark it `stale` (committed, answered as a conflict); mark the proposal `accepted` and every other open (drafting, validating, ready) proposal of the pipeline touching one of its files or steps `stale`; record the events (section 11.3). Every unit that changes a pipeline's active revision (apply, rollback) also marks its open proposals on another base `stale` |
| Start replay | Return the run if it already exists; check each selected item is on one of the step's input streams and has not expired; take the pipeline's next generation; insert the replay run; create a delivery of the step for each item in that generation; record the event |
| Trigger | Insert the run and its trigger item under their deterministic ids (a conflict means the firing already happened); publish the item to the trigger stream; create the deliveries of the steps reading it |
| Trigger tokens | At apply, store a token hash for each webhook trigger that has none; at a rotation, replace the trigger's hash; record `triggerTokenSet` without the hash (section 4.6) |
| Filter | Check the fencing token; mark the delivery `filtered` with its reason; record the event; settle the run. For a delivery of a cancelled run: mark it `cancelled` |
| Dedupe | Check the fencing token; look up (pipeline, step, generation, key): when the key is absent or was seen longer ago than `window`, pass the item as Done does and set `seenAt` and the first item; otherwise mark the delivery `filtered` with reason `duplicate`. A key seen exactly `window` ago is still a duplicate |
| Park | Check the fencing token; for an item `autoApprove` holds for: pass it as Done does, record the review as approved by `rule`, and open a review sample when it is sampled; otherwise mark the delivery `awaitingReview` without a lease, insert its review (inbox, deadline, the step's editable pointers, reason codes and output schemas, the display rendering) and record the event; settle the run, which is `waitingReview` while only parked reviews remain. A review parked again after a dead-letter replay starts afresh at a new version. For a delivery of a cancelled run: mark it `cancelled` |
| Review decision | Check that the review is open, its delivery `awaitingReview`, and at the version the reviewer saw (escalation and parking again move it on); for an approval, apply the edit within the editable pointers and check the edited payload against one of the output schemas reaching the step, then pass it on as Done does; for a rejection, require a reason code when the step lists some and mark the delivery `filtered` with it; record the decision, who, why and the edit's diff, and the event. Two concurrent decisions: the writer applies one, the other finds the review decided (`conflict`) |
| Sample decision | Check that the review sample is open; record agree or disagree, who and why; never emit, never touch the run (section 8) |
| Review timeout | For every open review past its deadline: apply `onTimeout` once (reject with reason `timeout`, approve, or escalate: move it to the other inbox at a new version with a fresh deadline; an escalated review timing out again is rejected); every open review sample past its deadline becomes `unreviewed` |
| Cancel | Mark the run `cancelled`; move its pending, retry-waiting and awaiting-review deliveries to `cancelled`, and their reviews with them; discard its open dead letters |
| Dead-letter replay | Mark the dead letter `replayed`; move a `dead` delivery back to `pending`, or route and publish an `unrouted` output; reopen the run |
| Dead-letter discard | Mark the dead letters `discarded`; settle the run if nothing else remains |

Lease expiry and review deadlines are evaluated with the database clock (`now()`), never a node's clock. An expired
lease is a Fail whose cost went unreported: its budget reservation is charged in full. The crash tests (section 16)
kill the process at every boundary of every unit, not only at random points.

## 6. Actions

### 6.1 Manifest

Each action is a directory or OCI artifact containing `action.yaml`:

```yaml
name: lab/score-listing
version: 2.1.0
description: Scores a real estate listing for renovation potential
kind: agent               # exec | container | agent
effects: none             # none | external
input:  { $ref: schema/input.json }
output: { $ref: schema/output.json }
config: { $ref: schema/config.json }
lifecycle: perItem        # long (default for exec/container) | perItem (default for agent)
runtime:
  agent:
    harness: claude-code   # claude-code | api
    model: claude-sonnet-5-5
    prompt: prompt.md
    tools: [WebFetch]
    mcp: []
    network: [api.anthropic.com, "*.homesite.example"]
    maxTurns: 20
    maxCostUsd: 0.50
```

Schemas are JSON Schema 2020-12. `effects: external` declares that the action changes something outside Millstream
(sends email, writes to a CRM); it drives the safety check in section 4.8 and the idempotency key in section 6.3.

An agent action declares an `output` schema, which every answer is validated against, and `runtime.agent` with:
`harness` and `model` (required); `prompt`, the template's path relative to the action directory (`prompt.md` by
default, inside the package); the allowlists `tools`, `mcp` and `network`; `maxTurns` (10 by default) and
`maxCostUsd`; and for the `api` harness `provider` (`anthropic`, the default, or `openai` for any OpenAI-compatible
endpoint), `baseUrl` (required for `openai`, the base to which `/chat/completions` is appended) and `apiKeySecret`,
the name of a pipeline secret holding the API key, which also gives `claude-code` its `ANTHROPIC_API_KEY`. In M2,
MCP servers and tools for the `api` harness resolve as unavailable (a `check` warning; deliveries fail as
unsupported). `check` fails on a missing prompt file, a missing output schema and an `apiKeySecret` the pipeline does
not declare, and warns on an agent without `network`, which its sandbox could not let reach its model.

The other runtimes take their own keys: `runtime.exec.command` (a list of strings, section 6.2), and for a container
action `runtime.container` with `image` (the image a local action runs, built by the user's toolchain), an optional
`command` run in the image instead of its own, and an optional `network` list of destinations. A registry action is a
container action whose manifest is the image's `io.millstream.manifest` label, as JSON with inline schemas; its
image is the action itself, so it needs no `image` key.

### 6.2 References and resolution

| Form | Example | Resolves to |
| --- | --- | --- |
| Local path | `./actions/rentability` | A directory in the pipeline's package (section 4.9) |
| Registry | `lab/score-listing@2` | An OCI artifact; `@2` is a semver range, resolved to an exact version and digest |
| Builtin | `filter` | Compiled into the engine |

The command of a local `exec` action (`runtime.exec.command`) resolves as follows: a bare program name runs
`bin/<os>-<arch>/<name>` from the action directory when the package ships it, and otherwise the program of that name
on the node's `PATH`, but for `millstream`, which runs the node's own millstream binary (the `improve` package's
actions are its hidden `improve-action <step>` subcommand, section 11.3); a path containing `/` is a file of the
action directory and must stay inside the package; an absolute path is refused, since a package must not depend on
the machine it runs on.

`millstream lock` writes `millstream.lock` in the package with the exact version and digest of each registry
reference, and the image digest of each local container action; `run` and `apply` use the lock and refuse a digest
mismatch. The registry namespace maps to an OCI registry in the environment file
(`lab` → `ghcr.io/monolithiclab/millstream-actions`).

- **Registry references.** `lab/score-listing@2` names the repository `<prefix>/score-listing`. The range is an exact
  version (`2.1.0`) or a major or minor prefix (`2`, `2.1`) matching every `MAJOR.MINOR.PATCH` tag that starts with
  it; the highest wins, unless the lock file pins the reference, in which case its version is used and must fall in
  the range. Until remote tag listing arrives (M4), versions resolve against the tags of local images only, so an
  image is pulled or built before `lock` or `run`; the manifest's `version` must equal the tag.
- **Digests.** An image's digest is its registry digest when it was pulled or pushed (the one remote nodes can pull
  by), else its local image id. Containers run by that pinned reference, never by tag, and are never pulled at run
  time.
- **The lock file** is YAML: `actions`, keyed by the reference as steps write it, each with `version` (registry
  references only), `image` (repository and tag) and `digest`. It is a file of the package, so locking changes the
  revision. `check` and `run` fail on an entry whose image or digest differs from the image found, and `check` warns
  on a container action the lock does not pin. A container action on a machine without the configured runtime
  resolves to a warning in `check` and fails its deliveries as unsupported.

### 6.3 The action protocol

Actions talk to the engine over stdin and stdout, one JSON object per line (D3). The protocol is published as its
own versioned document so third parties can implement it: [the action protocol](../protocol.md).

Engine to action:

```text
{"type":"hello","protocol":1,"action":"lab/score-listing","version":"2.1.0","config":{…},"vars":{…},"lessons":{…}}
{"type":"item","delivery":"dl_…","id":"it_…","key":"…","payload":{…},"artifacts":[…],"run":{…},"attempt":1,"idempotencyKey":"…","audit":false}
{"type":"shutdown"}
```

Action to engine:

```text
{"type":"ready"}
{"type":"emit","delivery":"dl_…","key":"…","payload":{…},"artifacts":[{"name":"report.pdf","path":"out/report.pdf"}]}
{"type":"metric","delivery":"dl_…","name":"pages_fetched","value":12,"labels":{"source":"homesite"}}
{"type":"done","delivery":"dl_…","artifacts":[{"name":"transcript.json","path":"transcript.json"}]}
{"type":"error","delivery":"dl_…","message":"…","retryable":true,"artifacts":[…]}
{"type":"abstain","delivery":"dl_…","reason":"…"}
```

- `emit` stages an output; outputs are published when the delivery is `done` (section 5.2).
- `hello.lessons`, optional, carries the step's lessons (section 11.4) as JSON, `rules` and `examples`; the engine
  sends it to agent steps that have a lessons file, and a process serves only deliveries with the same lessons.
- `abstain` ends a delivery without output and hands it to the step's `fallback` (section 11.5); on a step without
  one, it is a non-retryable error.
- `audit: true` marks a fallback audit (section 11.5): its output is stored for comparison, never published. The
  engine omits the key when false.
- `abstain` may name attempt artifacts, as `done` and `error` do (an agent's transcript).
- `metric` messages are recorded with the attempt that sent them (section 10.2), at most 256 per attempt; a metric
  without a name or with a value that is not a finite number is dropped. A `metric` for the delivery just answered
  that arrives after its `done` is ignored, not a violation.
- Anything written to stderr is a log line; the node re-emits it with the run, step, item, delivery and attempt
  (section 10.3).
- A long-lived action process handles one delivery at a time; concurrency comes from running several processes.
  This keeps actions simple to write.
- Artifacts are files written under the working directory the node gives the action process (`MILLSTREAM_WORKDIR`);
  they are moved to the artifact store when the delivery is done, before the outputs that name them are published.
  An artifact's name is a file name, distinct among an output's artifacts; its path must lead, without a symbolic
  link, to a regular file inside the working directory, or the delivery fails as a non-retryable protocol error.
  Input artifacts are materialised under `in/<name>` in the same directory before the `item` message, which lists
  them by that path.
- `done` and `error` may name **attempt artifacts**: files of the attempt itself, such as an agent's transcript,
  kept with the delivery's attempt (by attempt number) rather than carried by its outputs, and kept for a failed
  attempt too. The same rules apply as to output artifacts; after `error`, one the node cannot move is dropped with a
  warning and the action's error is reported.
- `idempotencyKey` is `hash(step, item id, generation)`: stable across retries, new on replay.
- A protocol violation (malformed line, `done` for an unknown delivery) kills the action process; the delivery is
  retried.

### 6.4 Runtimes

Runtimes are provided by nodes (section 5.10); a delivery goes only to a node offering the runtime it needs.

| Kind | Runs as |
| --- | --- |
| `exec` | A child process of the node, only on nodes started with `--allow-exec` |
| `container` | `docker run -i` or Podman, stdio attached (below) |
| `agent` | The agent adapter in a sandbox container (section 7) |
| builtins, `review` | In the engine |

A container runs `--rm --pull=never` from its pinned image with: the delivery's working directory mounted at the same
path, and `MILLSTREAM_WORKDIR` pointing at it; only the environment variables the engine passes explicitly, never the
node's, each by name with its value in the runtime CLI's environment, so no value (a secret) appears on a command
line, unless the CLI sets that variable itself; a read-only root file system with a private `/tmp`; no capabilities
and `no-new-privileges`; the node's user (`--user uid:gid`, or `--userns keep-id` under rootless Podman), so the
files it writes stay the node's to read and remove; and no network unless its manifest declares destinations. A
declared list grants the runtime's default network in M2: per-destination filtering is not enforced yet. Each
process's container is named after its working directory, so killing the process also removes its container. The
runtime (`docker` or `podman`) comes from the environment file.

### 6.5 Action process lifecycle

- **Long-lived processes** (default for `exec` and `container`) handle deliveries one after another, which amortises
  start-up. Go actions are well suited to this. A process serves only deliveries with the same launch spec as the
  one it started with: action digest, image, command, network, mounts and environment (secrets included), and the
  config, vars and lessons of its `hello`. Runs on different revisions, pipelines with other secrets or packages, and
  a process started before a secret rotated never share a process.
- **Per-item processes** (default for agents) start fresh for each delivery, so no context leaks between items.
- A process that crashes is replaced, and its delivery retried. Process starts and crashes are metrics. Each
  process runs in its own process group; on a timeout, a lost lease, a protocol violation or a shutdown that does
  not complete, the node kills the whole group, so children the action started do not outlive it.
- **Engine memory.** The engine streams payloads from the log store. Its RSS target is under 150 MB on the benchmark
  workload, independent of stream sizes, checked by a benchmark in CI.

### 6.6 SDKs

SDKs are thin wrappers over the protocol; writing an action without one is supported and documented.

```go
func main() {
    millstream.Map(func(ctx millstream.Context, in Listing) ([]Priced, error) {
        ctx.Metric("works_estimate_eur", float64(estimate))
        return []Priced{price(in, ctx.Config())}, nil
    })
}
```

- Go SDK in v1 (`millstream.Map`, and `millstream.MapKeyed` for several keyed outputs), with schema generation from
  Go types. Returning `millstream.Abstain(reason)` as the error sends `abstain`.
- Python SDK after v1.

## 7. Agent actions

### 7.1 Harness-agnostic adapter

An agent action is run by the **agent adapter**, a program shipped with Millstream that speaks the action protocol on
one side and drives an LLM harness on the other (D4). The engine never knows which model ran.

| Harness | How it runs |
| --- | --- |
| `claude-code` | Claude Code in headless mode, with the action's tools and MCP servers as an explicit allowlist |
| `api` | A direct model call with an adapter-run tool loop: Anthropic, or any OpenAI-compatible endpoint (Mistral, a local model) |

For each delivery the adapter:

1. renders `prompt.md` (Go template) with the payload, config, vars and the step's lessons (section 11.4);
2. runs the harness in the sandbox (section 7.3) with `maxTurns` and `maxCostUsd`;
3. obtains structured output, using the harness's native structured-output support where it exists and a final
   fenced JSON block otherwise;
4. validates it against the output schema, and reports a retryable error if it does not match; an answer that is an
   object holding only the key `abstain`, with a string, is not validated but answered `abstain` with that reason
   (section 11.5): an output schema that lets the model abstain admits `{"abstain": "<why>"}` as an alternative
   (`anyOf`), which `claude-code`'s `--json-schema` then allows, and the prompt says when to use it;
5. emits the result with metrics: `tokens_in`, `tokens_out`, `cost_usd`, `turns`, `duration_ms`, each labelled with
   the `model`.

Cost is taken from the harness when it reports it, otherwise computed from token counts and the price table in the
environment file; with neither, it is 0 and the adapter logs a warning.

- **The adapter** is the `millstream` binary's hidden `agent` subcommand. The engine starts it with the package
  directory and the step's action reference, the names of the pipeline's secrets (their values in its environment,
  for redaction and the API key, never in its arguments) and the model's price. An action that cannot run (a
  manifest error, an unset API key secret) answers every item with a non-retryable error naming why.
- **`claude-code`** runs `claude --print --output-format stream-json --verbose` with the prompt on stdin, the
  manifest's `tools` as both `--tools` and `--allowedTools` (none when empty), `--strict-mcp-config`,
  `--no-session-persistence`, `--max-turns`, `--max-budget-usd` from `maxCostUsd`, and the output schema as
  `--json-schema`. Its environment is `PATH`, `HOME`, `TMPDIR`, `USER` (on macOS the CLI reads its login from the
  user's keychain by account name), `CLAUDE_CONFIG_DIR`, `XDG_CONFIG_HOME` and the API key, nothing else. Usage,
  cost and turns come from its result line; a run stopped by the budget is not retried.
- **`api`** makes one call in M2, with no tool loop: Anthropic's Messages API (`x-api-key`, `anthropic-version`) or
  an OpenAI-compatible chat completions endpoint (a bearer token), `max_tokens` 4,096. The prompt asks for a final
  fenced JSON block matching the output schema. Rate limits, server errors and transport failures are retryable;
  other refusals are not.
- **Record and replay.** `MILLSTREAM_HARNESS_MODE` (`live`, the default; `record`; `replay`) and
  `MILLSTREAM_HARNESS_DIR` select the mode; the engine passes both to the adapter. A recording is keyed by the
  SHA-256 of the harness, the model, the rendered prompt and the output schema, and stored as `<key>.json`; a replay
  miss is a non-retryable error naming the key. A replay never calls the harness, so it needs no API key. Since
  lessons are rendered into the prompt, editing them misses the old recordings rather than replaying a stale answer.

### 7.2 Transcripts

The full transcript of each attempt (prompts, tool calls, results, final output) is stored, gzip-compressed, as an
artifact of the delivery in the artifact store, never in the database, and shown in the item view. Secrets are
redacted before storage. Transcripts have their own retention (`retention.transcripts`).

The adapter writes it as `transcript.json`, an attempt artifact (section 6.3) named by its `done` or `error`, so a
failed attempt, a schema mismatch included, keeps its transcript and its error message points at it. Every secret
value of the pipeline is redacted from every string of the transcript, the harness's own records included, after
decoding, so the harness's JSON escaping cannot hide one. The adapter compresses it with gzip (the standard library's,
at its default level) before it leaves the action process; the API serves an artifact holding gzip data under a name
that does not end in `.gz` decompressed, its type read from its name, so the UI reads the JSON. Harness
recordings (section 7.4), which are committed with tests and evals, are redacted the same way: the response's text,
structured output and every turn, the prompt included; a recording is still keyed by the request as sent.

### 7.3 Sandbox

Agents run in a container with a read-only filesystem except the working directory, a network allowlist taken from
`runtime.agent.network`, and only the declared tools and MCP servers. On a laptop without Docker, agents may run
unsandboxed only when the environment file sets `agents.allowUnsandboxed: true`, which is logged at every start.

- The sandbox needs a container runtime, an image (`agents.image`) and the adapter: the running binary on Linux,
  else a Linux build of `millstream` for the image's platform (`agents.linuxBinary`). The image holds what the
  harness needs and nothing of Millstream's: CA certificates for `api`, the `claude` CLI as well for `claude-code`.
- The adapter is mounted read-only at `/millstream`, the package read-only at its own path, a recordings directory
  when one is set (writable only to record); `HOME` is the container's private `/tmp`. The container is otherwise a
  container action's (section 6.4): no network unless `runtime.agent.network` lists destinations, which grants the
  runtime's default network in M2, as for container actions.
- Without a sandbox and without `agents.allowUnsandboxed`, an agent delivery fails at once, not retried, with the
  error class `sandbox`. Unsandboxed, the adapter runs as a child process of the node with the variables the
  `claude-code` harness passes on (`PATH`, `HOME`, `TMPDIR`, `USER`, `CLAUDE_CONFIG_DIR`, `XDG_CONFIG_HOME`) only.

### 7.4 Evals

Each agent action may ship an `evals/` directory of cases: an input, and assertions on the output (CEL over the
output, or an LLM judge with a rubric). `millstream eval <action>` runs them, reports a score per case, and stores the
result as metrics so prompt and model changes are compared before they ship. Record/replay of harness calls keeps
eval and test runs deterministic in CI (section 16).

```yaml
# actions/score/evals/renovated.yaml
name: renovated flat              # defaults to the file name
input: { url: https://example.com/listings/2 }   # the item's payload
config: { rooms: 2 }              # the hello's config and vars, as a step would resolve them
vars: { city: Lyon }
assert:                           # CEL over output, input and vars; each must hold
  - output.score < 30
judge:                            # optional: an api harness call scoring the output against the rubric
  rubric: The score reflects the recent renovation.
  model: claude-haiku-4-5
  provider: anthropic             # or openai, with baseUrl
  apiKeySecret: anthropicKey      # read from MILLSTREAM_SECRET_ANTHROPIC_KEY
```

- **Running.** Agent actions run in-process through the agent adapter, exec actions through the exec runtime, as a
  node runs them (container actions are not evaluated in M2). `output` is the payload of the action's one output, the
  list of payloads when it emits several, null when none. The step's lessons are not applied: a case evaluates the
  action. `--harness-mode` (`replay` by default, `record`, `live`) and `--harness-dir` (by default
  `<action>/evals/recordings`) apply to the agent's calls and the judge's alike; a replay needs no API key.
- **Judge.** The judge is asked for `{"score": 0..1, "reason": "..."}` against the rubric, with the input and the
  output in its prompt, through the same record/replay layer: its recording is keyed by its prompt, so a changed
  output misses the old verdict.
- **Scores.** A case's score is the mean of its parts: the share of its assertions that hold, and the judge's score.
  An action that fails, or a judge that cannot answer, scores 0. The command prints a line per case (assertions
  passed over total, judge score, reported cost, score), the total (the mean), then each failed assertion, the
  judge's reason and each error; it exits 1 when an assertion does not hold or a case cannot be scored, never for a
  judge's low score.
- **Results.** With `--db`, or an environment file naming the store (section 14), the scores are recorded in
  `eval_results` with the action's digest (the content hash of its directory, as the engine computes it), and each
  line shows the case's previous score. `/metrics` exposes each case's latest as the gauge
  `millstream_eval_score{action,case}` (section 10.2).

### 7.5 Budgets

- `maxCostUsd` per delivery: the adapter stops the agent and reports a non-retryable error whose message starts with
  `budget:`. `claude-code` stops itself at `--max-budget-usd`; for both harnesses the adapter also refuses an attempt
  whose cost, reported or priced from its tokens, ends above the limit.
- `budget.runUsd` and `budget.dayUsd` per pipeline, enforced by reservation at dispatch (section 5.9). An agent
  delivery is leased only when the spend and reservations already counted plus its own reservation stay within both:
  the run's (`runs.cost_usd` and the reservations of its leased deliveries) against `runUsd` of the run's revision,
  and the pipeline's for the current UTC day of the store clock (`budget_days`, where every cost is charged to the
  day it is settled on, and every outstanding reservation) against `dayUsd` of the active revision. Under either
  budget every agent step must set `maxCostUsd` (section 5.9): an error for `check`, a `config` failure at dispatch.
  Once a budget is reached, any agent delivery is held back. A held-back delivery stays `pending` and does not take
  its step's slot, so other runs are served past it: within one lease, a run budget holds back the run's step and a
  day budget the step of that revision, so the lease reads past them once rather than delivery by delivery.
- The first time a budget stops a delivery, per run for `runUsd` and per pipeline and day for `dayUsd` at a given
  limit, every agent step of the pipeline is paused with the cause `budget.run` or `budget.day` and a
  `budgetReached` event records `{scope, limit, spent, reserved, steps}`. `millstream status` and the UI show the
  cause. Resuming is a user action: `millstream resume <pipeline>` lifts the pauses a budget made (a step a user
  paused stays paused). A run that reached its own budget does not pause the pipeline again after a resume: its
  agent deliveries wait until its reservations settle below the budget, or until it is cancelled. Raising the budget
  in a new revision lets the new limit be reached, and pause, once more.

## 8. Human review

`review` is a builtin step that parks each item in an inbox until a person decides.

| Config | Meaning |
| --- | --- |
| `inbox` | Inbox name; access to it is controlled by RBAC in the commercial layer |
| `timeout` | How long an item may wait |
| `onTimeout` | `reject`, `approve` or `escalate: <inbox>` |
| `editable` | JSON pointers the reviewer may change before approving |
| `notify` | A generic webhook (JSON, compatible with Slack incoming webhooks) carrying a link to the item in the inbox: its URL, or `{ secret: <name> }` |
| `display` | Optional template rendering the item for the reviewer |
| `reasons` | Reason codes offered to the reviewer; a rejection then requires one, with optional free text |
| `autoApprove` | CEL expression; matching items skip the inbox and are recorded as approved by `rule` |
| `sampleRate` | Share of auto-approved items also given to a person as a review sample, default `0.05`, minimum `0.01` so a rule is always measured |

- **Approve** emits the payload, as edited, to `out`. **Reject** marks the delivery `filtered` with the reviewer's
  reason. Every decision records who, when, the reason and the diff of any edit.
- **Review samples.** An auto-approved item is emitted at once. When it is sampled, a record in `review_samples`
  (delivery, state `open`, `decided` or `unreviewed`, decision) appears in the inbox, marked as a sample. Its decision
  only measures the rule (the "Sample decision" unit of section 5.11): it never emits, never recalls the item, does
  not affect the run's state or settlement, and `onTimeout` does not apply; an expired sample becomes `unreviewed`.
- Reviews are made from the web inbox or `millstream inbox`. On a server without `auth.token`, and writing to the store
  directly, the CLI names the reviewer with `--as`, by default `$USER`, else the account the system names; with
  `auth.token` every decision made through the API is recorded under `auth.user` (section 12.1). A decision names the
  version of the review the reviewer saw (`inbox approve|reject --version`; without it the CLI decides the current
  version and says so), so one escalated meanwhile is a conflict. The same decision sent again by the same reviewer
  (same version, reason and edit), its answer lost, succeeds again and changes nothing; any other decision on a decided
  review is a conflict. So does a sample decision.

How M3 runs it:

- **Config.** `inbox` defaults to the step's name; inbox names are letters, digits, dots, dashes and underscores, as
  they appear in links. `timeout` is a duration (`72h`, `3d`); without it an item waits for ever and `onTimeout` is an
  error. `onTimeout` is `reject` (the default with a timeout), `approve`, or the mapping `{ escalate: <inbox> }`.
  `editable` lists JSON pointers: an edit may change a listed pointer or anything below it. `notify` is an http or
  https URL, or `{ secret: <name> }` naming a secret the pipeline declares, whose value is the URL: a webhook URL is
  a credential, and a secret keeps it out of the pipeline file and the store; it is read when a notification is
  sent. `display` is a Go text/template whose dot holds `item` (the payload), `key`, `id` and `step`, rendered
  when the item parks (at most 16 KB; a template that fails renders as its error). `reasons` lists distinct codes.
  `sampleRate` is a number from `0.01` to `1`. `check` validates every key; the config is not interpolated.
- **Parking.** A parked delivery holds no lease and no concurrency slot. Its run stays open, `waitingReview` while
  nothing else is live; `run --once` and `test pipeline` stop waiting at that point, and the next `run --once` resumes
  the runs a decision moved on.
- **Auto-approval and samples.** An item is sampled when the first 8 bytes of its id's SHA-256, as a fraction of
  2^64, fall under `sampleRate`: deterministic per item, so a retried or replayed delivery is sampled alike. A sample
  expires `unreviewed` after the step's `timeout`, never without one.
- **Edits.** An approval carries a JSON Patch (RFC 6902): every pointer it writes or moves from must be editable, and
  the edited payload must match one of the output schemas reaching the step (the producers' output schemas and
  triggers' input schemas, through builtins), when any is declared. The review records the edit as a diff from the
  original payload to the edited one, objects compared member by member and other values replaced whole. An `add`,
  `replace` or `test` operation without a `value` is refused (`null` is a value).
- **Reasons.** A rejection needs a code from `reasons` when the step lists some; the delivery is filtered with the
  code as its reason (`rejected` without one, `timeout` when `onTimeout` rejects; an approval on timeout has no
  reason). A code given with an approval must be listed too.
- **Timeouts.** The engine applies the Review timeout unit at every tick and once before its node starts pulling, so a
  review that came due while no engine ran is decided first. A decision arriving after it is refused with `review of
  delivery … timed out at <time>, applied <action>`; one on a review escalated since is refused as a conflict naming
  the new inbox. A review that cannot time out (its item no longer passes, say) is logged and skipped, its partial
  work rolled back, and tried again at the next tick: it never holds back the other reviews due.
- **Notifications.** After a review parks or is escalated, the engine posts `{text, blocks}` to `notify`: Slack
  incoming webhooks render it, and any JSON webhook can read it. Both carry the link
  `<ui.baseUrl>/inbox/<inbox>/<deliveryId>` (`http://127.0.0.1:7070` by default, section 14) and the deadline the
  review was stored with; every value from the pipeline or the item is escaped for Slack's mrkdwn (`&`, `<`, `>`), so
  an item cannot forge a link or a mention. A failed POST is retried three times, after 1, 2 then 4 seconds; a
  notification that still fails is logged and counted (`review_notifications_failed`, reported by
  `/api/v1/nodes` as the engine's `notificationsFailed` and by `/metrics`, section 10.2). Logs name a webhook by
  its host, or by its secret, never by its URL. Notifications never block the engine or a decision: they wait in a
  bounded queue (256) for one of 8 senders, and one that finds the queue full is dropped and counted. They outlive
  the request or run that parked their item: when the engine stops (`run --once` settling on a review included), no
  failed POST is retried any more, and what is queued and in flight gets 5 seconds to be sent.
- **Events.** `reviewParked` (the parking attempt's end, with its work time), `reviewDecided` (decision, reviewer kind
  `person`, `rule` or `timeout`, never the person's name, reason, time to decision, edited pointers),
  `reviewEscalated`, `reviewSampled`, `sampleDecided`, `sampleExpired`; each names its `deliveryId` and `itemId`.
- Metrics: decisions by outcome and reason code, time to decision, edit rate, auto-approval rate, sampled-rule
  agreement, and **intervention rate** (reviewed items over items reaching the step), per step and per pipeline.

Migrations are versioned and run at start-up. Before the first public release, the schema may change without
migrations (no compatibility shims before launch): a database recording a newer schema version than the build's is
refused rather than written to.

The two stores share one implementation (`internal/store/sqlstore`): the writer loop, the units and the reads, in
the same SQL, with the few differences (placeholders, the clock, JSON arrays) behind a dialect. Each declares the
logical schema above in its own types:

| Data | SQLite | Postgres |
| --- | --- | --- |
| Instants | text, `2006-01-02T15:04:05.000Z` UTC, so text order is time order | `timestamptz` |
| An instant that has not come (no lease, not finished, no deadline) | NULL | NULL |
| Counts, ids, attempts, fencing tokens, milliseconds | `INTEGER` | `bigint` |
| Costs, scores, rollup sums | `REAL` | `double precision` |
| A budget's UTC day | text, `2006-01-02` | `date` |
| A step's pause | `BOOLEAN` (stored 0 or 1) | `boolean` |
| Package bundles | `BLOB` | `bytea` |
| An item's parents (queried) | JSON text | `jsonb` |
| Payloads, vars, evidence, patches and other JSON documents | JSON text, canonical | `text`, canonical |
| Creation order, the paging cursor of runs, items, deliveries, reviews | the implicit `rowid` | a `rowid bigint` identity column (a rolled-back insert leaves a gap) |

Times are stored to the millisecond, and every unit reads the batch's instant from the database clock (SQLite's
`strftime('%Y-%m-%dT%H:%M:%fZ', 'now')`, Postgres's `now()`, the start of the batch's transaction).

### 9.2 Artifacts

Artifacts are content-addressed (SHA-256) in a local directory or an S3-compatible bucket, under a prefix per
pipeline, and deduplicated by hash within it. Nodes read and write them through signed URLs. Remote nodes need the
S3-compatible store; a local directory works with one host, where the engine proxies transfers.

- The local directory is `artifacts/<pipeline>/<sha256>` next to the state database (`.millstream/` by default). A
  file is written to a temporary name and renamed to its hash once complete, so a crash leaves no partial artifact.
- Items carry their artifacts as `{name, sha256, size, type}`, the type sniffed from the content. The log store's
  `artifacts` table counts the items referencing each artifact, in the transaction that publishes them; a retry that
  republishes an existing item counts nothing, and keeps the first attempt's artifacts with its payload (section
  5.2). The count is what retention (section 9.3) deletes by.
- A copy published through an imported stream (section 4.12) counts a reference in the consumer's prefix to an
  artifact whose file is in the producer's: the first time a node opens it for the consumer, the engine copies the
  file into the consumer's prefix (a server-side copy on S3), where the consumer's retention and erasure find it.
  Until then the file is the producer's: when the producer's retention or a purge leaves the producer's entry
  unreferenced, the artifact sweep copies the file into each pipeline still referencing it without holding it before
  deleting the producer's.
- The **artifact sweep** (section 9.3) deletes the file of every entry whose count fell to zero, then the entry; and
  the files no entry names (outputs of a retry whose item already existed, a file whose entry the sweep removed
  before a crash) once older than a day. Storing content that is already there touches its file, and the periodic
  sweep leaves an unreferenced file stored within the last day, so a delivery in flight never loses a file it is
  about to reference. A purge sweeps its pipelines' unreferenced files at once.
- **The S3-compatible store** (`artifacts.s3`) keeps `<prefix>/<pipeline>/<sha256>`, addressed path-style
  (`<endpoint>/<bucket>/<key>`), every request signed with AWS Signature Version 4: a minimal implementation of the
  few requests the store makes, checked against the AWS documentation's examples and against a real S3-compatible
  server in the tests, rather than an SDK. The engine sends an artifact with its hash signed, so the store checks
  what it received, and skips content it holds already. The sweep lists the prefix (`ListObjectsV2`), reads an
  object's `Last-Modified` and deletes objects; touching content already there copies the object onto itself.
- **Nodes move artifacts** only for the deliveries they hold (section 15.7): a node asks the engine for a URL for an
  input of its lease, or for an output whose hash, size and type it computed. With `artifacts.s3` the engine answers a
  presigned GET or PUT valid 15 minutes, a PUT signing the output's `Content-Length` and `x-amz-checksum-sha256`, so the
  store refuses any other length or content under that hash; with a local directory, a URL of its own proxy
  (`/node/v1/artifacts/blob`), signed by the engine (an HMAC of the operation, pipeline, hash, name, size and expiry
  under a key of the process) and expiring alike; it refuses a body of another size before writing anything. An output
  the store holds already is not sent: the engine touches it instead, as storing it again would.

### 9.3 Retention and erasure

- **Retention** is set per stream (`streams.<name>.retention`: payloads and artifacts, unlimited by default; an
  imported stream's declaration sets its copies'), and globally for events, transcripts and rollups (the environment
  file's `retention`, section 14). The engine's retention job runs every `retention.every` (an hour by default) and at
  the end of `run --once`, in passes of the `retain` unit bounded to 500 records of each kind:
  - **Payloads.** An item of a stream older than its retention gets a **tombstone**: its payload becomes `null`, its
    artifact references are dropped (their counts with them), and `items.tombstone` says `expired`; its envelope
    (id, run, stream, step, key, parents, generation, time) stays, so counts and lineage remain correct. One
    representation serves retention and erasure alike, `erased` for a purge, which also drops the key. Retention never
    tombstones an item unfinished work needs: one with a delivery that is not terminal (a parked review included),
    an open dead letter that is the item or whose dead delivery it is the input of, or an open review sample. It is
    kept until they are resolved, and the next pass takes it. A tombstoned item is never replayed or back-filled
    (section 5.7), and an item republished onto a tombstoned one creates no delivery.
  - **Events** are deleted by time, oldest first, only once every projection has read them (the metric rollup's
    cursor), and never the last one, whose sequence number the next event follows; a live stream resuming from a
    deleted position gets `snapshotRequired` (section 12.1).
  - **Transcripts**, the artifacts attempts keep, are deleted by age, but those of a delivery not terminal or with an
    open dead letter. Agent transcripts are stored compressed (section 7.2).
  - **Rollups** are deleted by their minute; each series' running totals (`metric_totals`) stay.
  - The **artifact sweep** (section 9.2) then deletes the files nothing references, and the job prunes the package
    cache (`packages/`) and the engine's caches of the revisions that are neither a pipeline's active one nor the
    revision of a run not yet settled; the store's revision caches are bounded (64 per store, 256 per process).
- **Erasure.** `millstream purge --key <key>` (or `--item <id>`, either with `--pipeline`) erases the items named,
  their descendants, their artifacts and transcripts, following lineage into the pipelines that received copies
  through imported streams (and down a chain of imports), for GDPR erasure requests. A purge is a durable operation
  recorded in `purges`, in three units:
  - `startPurge` records it and **fences** its lineage in one transaction: the items are listed in `purge_items` and
    tombstoned `erased` at once (no longer served or replayable), their pending and parked deliveries are cancelled
    with their reviews, their open review samples become `unreviewed`, and their open dead letters are discarded;
    a delivery already leased is cancelled when it reports, its outputs discarded (Done, Fail, the builtins' units and
    lease expiry alike). Nothing can lease work on the lineage once the fence committed.
  - `erasePurge`, 200 items at a time, erases each item's payload, key and artifact references, its deliveries'
    attempt artifacts, error messages, review renderings, edits and free text, sample reasons and the error their
    failure events quote, its dead letter's error and the dedupe keys it set, marking it erased in `purge_items`.
  - Once none is left, the engine sweeps the purge's pipelines' unreferenced artifact files without waiting, and
    `finishPurge` closes it.
  A purge interrupted by a crash resumes where it stopped: the engine finishes every purge not done when it starts and
  at every retention pass, and the command finishes them before its own; repeating the command with the same
  `--request-id` finds the purge it started (its id is `purge_<request id>`). Neither the purge's row nor its events,
  `purgeStarted` and `purgeCompleted` in each pipeline it erased items of, with the purge's id, scope and item count,
  hold the key or item named.
- **Evidence bundles.** `startPurge` also lists the evidence bundles exported holding the key named or the key of an
  item it fences (`evidence_export_keys`, section 11.2), records their ids in the purge (`bundles`) and deletes those
  keys' rows: the exports keep no trace of an erased key either. The command prints the bundles: their copies are
  out of the purge's reach, in the development deployments that imported them until they expire.
- **Imported evidence** past its expiry is deleted by the retention job (`expireEvidence`): the import's row and its
  reference, then the bundle's file, without the sweep's grace.

## 10. Observability

### 10.1 One source of truth

Every state change is an event in `events`. Metrics, lineage, the live view and the audit trail are projections of
that table, so they cannot disagree (D10).

### 10.2 Metrics

| Scope | Metrics |
| --- | --- |
| Step | items in, out (per output stream), filtered, failed, dead, unrouted, nondeterministic outputs; queue depth; oldest pending age; delivery latency (histogram); retries |
| Action process | starts, crashes |
| Nodes | nodes by state, slots used and free per runtime, unschedulable deliveries, lease expiries, fencing refusals |
| Engine | role (active, standby), API latency, dispatch rate, writer batch size and latency, failovers |

Metrics are rolled up per minute in the log store and queried by the UI, so a laptop needs nothing else. The engine
also exposes `/metrics` in Prometheus format, beside the API on the same listener, behind the same token unless
`metrics.public` is set (section 14), as `text/plain; version=0.0.4` (a request accepting HTML, a browser loading
the UI's metrics explorer at the same path, gets the UI): every rollup series' running totals (below), which the
rollup keeps in `metric_totals` beside the minutes it adds and retention never deletes, so a counter never falls
back, and the metrics the engine measures itself:

| Metric (M4) | Labels | Kind | From |
| --- | --- | --- | --- |
| `leases_held` | pipeline, node | gauge | the deliveries each node holds leased, at the scrape |
| `writer_batch_size` | | histogram (1, 2, 4, 8, 16, 32, 64) | the units of each batch the store's writer committed since the engine started |
| `review_notifications_failed` | | counter | the review notifications that failed or were dropped since the engine started (section 8) |
| `eval_score` | action, case | gauge | each eval case's latest score in `eval_results` (section 7.4) |

An action's metric named as one of these is stored as `action_<name>`, as for the rollups' names.

Metrics are a projection of `events` (section 10.1). The end of an attempt records in its event the attempt's work
time, its cost and the action's `metric` messages, and a delivery's latency once it is terminal; a lease records its
queue wait. The engine's **rollup** unit, on a ticker (every 15 seconds) and at the end of `run --once`, reads the
events after its cursor (at most 5,000 per pass), adds each measurement to the row of its metric, label set and
minute (count, sum, minimum, maximum) and to its series' running totals, and moves its cursor in the same
transaction: a pass that fails leaves no trace, and a pass repeated adds nothing. Each pass also samples every
step's queue depth and oldest pending age, zero for an empty queue.

| Metric (M2, M3) | Labels | Kind | From |
| --- | --- | --- | --- |
| `items_in` | step | counter | a first lease |
| `items_out` | step, stream | counter | an item published (a trigger's under its trigger stream) |
| `items_filtered` | step, reason | counter | a builtin filtering a delivery |
| `attempts_failed`, `retries`, `items_dead` | step, class | counter | a failed attempt, retried or dead |
| `items_unrouted` | step | counter | an unrouted dead letter |
| `nondeterministic_outputs` | step, stream | counter | a retry publishing another payload |
| `lease_expiries` | step | counter | an expired lease |
| `deliveries_unschedulable` | step, class | counter | an attempt failed `unsupported` or `sandbox` |
| `queue_depth`, `oldest_pending_seconds` | step | gauge | sampled at each pass |
| `delivery_latency_seconds` | step | histogram | a terminal delivery, creation to end |
| `delivery_wait_seconds`, `delivery_work_seconds`, `delivery_cost_usd` | step | distribution | each attempt |
| `run_duration_seconds`, `run_cost_usd` | state | distribution | a settled run |
| `review_decisions` | step, decision, reason | counter | a review decided: `approve` or `reject` by a person or `onTimeout` (reason `timeout`), `autoApprove` by the rule; reason is the code, absent without one |
| `review_time_to_decision_seconds` | step | distribution | a review a person decided, parked to decided |
| `review_samples` | step, agreement | counter | a review sample decided (`agree`, `disagree`) or expired (`unreviewed`) |
| `fallback_deliveries` | step, producedBy | counter | a delivery of a step with a fallback done, by `primary` or `fallback`: coverage is the primary's share, the fallback rate the fallback's (section 11.5) |
| `fallback_handoffs` | step, cause | counter | a delivery handed to the fallback, on `abstain` or `error` |
| `fallback_cost_usd` | step, use | distribution | an attempt of the fallback action (`delivery`) or an audit (`audit`) |
| `audits` | step, agreement | counter | an audit ended: `agree`, `disagree`, `failed` or `cancelled`; audit agreement is agree over agree and disagree |
| an action's metric (`tokens_in`, `tokens_out`, `cost_usd`, `turns`, `schema_validation_failures`…) | its own and step | distribution | each attempt; renamed `action_<name>` when an engine metric has the name |

`millstream metrics` prints the rollups, or with `--prometheus` their exposition as the `/metrics` endpoint serves it:
counters as `<name>_total`, gauges at their latest minute's mean, distributions as summaries (`_sum`, `_count`), the
latency histogram with cumulative buckets from 50 ms to 30 minutes, every name prefixed `millstream_` and every
series labelled with its pipeline. Names are sanitised to `[a-zA-Z0-9_]`: of two metrics exposed under one name
(`a.b` and `a_b`), the first by stored name keeps it and the other is left out, with a warning in the log. `/metrics`
leaves out a gauge whose latest minute started over five minutes before the scrape: it is no longer sampled.

### 10.3 Logs

Millstream does not store logs (D27). The engine and nodes log through Go's `log/slog` with the JSON handler on
standard error, and the host keeps them: journald, Docker, or any log system collecting from there.

- Every line carries the keys that locate it: `pipeline`, `runId`, `step`, `itemId`, `deliveryId`, `attempt` and
  `node`. A node re-emits each line an action writes to stderr through slog with those keys, so a delivery's logs are
  found with the host's own tools, for example `journalctl -o cat | jq 'select(.deliveryId == "dl_…")'`.
- **Live tail.** While someone watches a run, a step or an item, in the UI or with `millstream tail`, nodes stream the
  matching lines of their current attempts to the engine, which relays them over SSE without storing them. The live
  tail is best effort: after a reconnect it shows a gap marker, and history is in the host's logs.
- What Millstream keeps about a failure is on the delivery: its class and a truncated message (section 5.5).
- Actions and the engine never log payload values; the SDK logs item ids, not items.

## 11. Self-improvement

A pipeline learns from its production runs: what is slow, what fails and why, what reviewers reject or correct, and
which agent steps have become predictable enough to replace with code. Learning happens on production data, and
changes are made in development (D31): nothing changes production behind its package, so revisions and replay stay
deterministic, and every change reaches production through the normal release (D29).

The loop has four parts:

1. **Insights** (section 11.1): deterministic analysis of the log store, in every deployment, no LLM.
2. **Evidence** (section 11.2): production exports a redacted, expiring bundle that a development deployment imports.
3. **Proposals** (section 11.3): reviewable changes drafted in development by the `improve` pipeline, an ordinary
   package, and validated against the evidence.
4. **Adoption**: an accepted proposal becomes a development revision or a pull request, and reaches production when the
   package is released there.

### 11.1 Insights

The **insights projector** reads `events`, `deliveries`, `reviews` and the metric rollups at the end of every run
and on a schedule (`insights.every`, default `15m`), and writes to the `insights` table. Each insight has a `kind`, a
scope (pipeline or step), the window it covers, a severity, its evidence (the figures and up to 20 sample item ids),
a fingerprint so a recurring problem updates one row instead of adding rows, and a state: `open`, `acknowledged`,
`resolved` or `muted`. No LLM is involved.

| Kind | What it detects |
| --- | --- |
| `slowStep` | The step's share of the run's critical path, split into queue wait (raise `concurrency`) and work time (the action is slow); p95 latency regressions against the previous seven days |
| `failureCluster` | Errors normalised into a fingerprint (numbers, ids and paths stripped), with count, rate, first and last seen, and the share that succeeded on retry: flaky failures need retries, deterministic ones need a fix |
| `cost` | Cost per output item and per approved item, turns per delivery, schema-validation failures, by model |
| `reviewPattern` | Per review step: rejection rate by reason code, the JSON pointers reviewers edit most, time to decision, sampled-rule agreement |
| `waste` | Items an agent step paid for that a later filter or reviewer discarded; suggests moving the filter upstream |
| `drift` | A field's output distribution moving away from its baseline (fields chosen from the output schema), and fallback audit disagreements (section 11.5) |
| `distillable` | An agent step that has become a candidate for replacement by code (section 11.5) |
| `unschedulable` | Deliveries no node can take (section 5.10) |

Every **run report** gives the critical path, the slowest steps, failures by cluster, cost, and a comparison with
the median of the last 10 runs; a running run shows an ETA computed from history. Reports come straight from the
events and are kept even when insights are off.

How M2 and M3 compute them:

- **Kinds.** M2 computes `slowStep`, `failureCluster`, `cost` and `unschedulable`; M3 adds `reviewPattern`; M5 adds
  `drift` from audits, `waste` and `distillable`, and the attribution and proposal hints of `reviewPattern`
  (section 11.6); `drift` from output distributions comes later. The projector runs for each pipeline at most every 15
  seconds when a run of it settled since its last pass or `insights.every` passed, and at the end of `run --once`.
- **Window.** An insight covers the last 24 hours; regressions compare it with the 7 days before.
- **Critical path.** A delivery's producer is the delivery that published its item; the critical path is the chain
  whose latencies add up the most. Each delivery on it splits into queue wait, work and backoff.
- **`slowStep`**, per step: more than half of the critical paths of the last 10 runs settled in the window, with the
  share of queue wait, work and backoff (info); or a p95 latency at least 1.5 times the baseline's and 1 second
  longer, with 5 deliveries or more on each side (warning).
- **`failureCluster`**, per step, error class and normalised message (URLs, paths, ids, hex strings and numbers
  replaced by placeholders, cut to 200 bytes): count and rate in the window, first and last seen over 8 days, and
  the share of its terminal deliveries that ended done: under one half is an error (deterministic), otherwise a
  warning (flaky). Unschedulable classes are left to `unschedulable`.
- **`cost`**, per step that spent or ran a harness in the window: cost, outputs, cost per output, cost per approved
  item (the step's cost over the items the pipeline's review steps approved in the window, by anyone), turns per
  delivery and schema-validation failures, by model; a warning when the cost per
  output is 1.5 times the baseline's or schema validation fails on a tenth of the attempts, info otherwise.
- **`reviewPattern`**, per review step with decisions or samples in the window, from the `reviewDecided`,
  `sampleDecided` and `sampleExpired` events: decisions by outcome (approved and rejected by a person, auto-approved,
  timed out), rejections by reason code and the rejection rate, the auto-approval rate, the edit rate of a person's
  approvals and the ten most edited pointers, time to decision (p50 and p95 of a person's decisions), the samples by
  agreement and the sampled-rule agreement (agree over agree and disagree), and the intervention rate (decisions by a
  person over the step's deliveries created in the window); a warning when the sampled-rule agreement is under 90%,
  info otherwise. Samples are rejected or edited items. From M5 it also gives each edit's attribution (the ten most
  frequent pointer and step pairs, a step of `null` when unattributed, and the count of unattributed edits) and its
  `proposals`: one hint per pattern of section 11.6 that the step's decisions by a person match, in the table's
  order. A filter candidate (`topology`) is a CEL condition on one field every decided item holds, keeping what it
  would not drop: `item.f != <value>` for a string or boolean that at least 5 rejected items hold and at most
  `improve.filter.maxFalseDrop` of the approved items do, or `item.f <= <max>` (`>= <min>`) beyond every approved
  item's number; it names the step the field comes from (`after`, by attribution, `null` when unattributed) and the
  costliest step between it and the review on the item's lineage (`before`), at most three, the most rejections
  first. Recurring edits (`lessons`, or `prompt`) are 3 edits or more of one field attributed to one step;
  near-universal approval (`config`) is at least 20 decisions by a person, 98% of them approvals without an edit;
  uncovered reasons (`reasons`) are at least 3 rejections with a reason text and no reason code (events record only
  that a text was given, never the text).
- **`waste`**, per step that spent: walking the lineage of each item a filter, a dedupe or a reviewer discarded in
  the window upwards, every delivery with a cost that published an ancestor of it is charged its cost over its
  outputs, once per ancestor; at least 5 discarded items make an insight, with the wasted cost and its share of the
  step's cost in the window, the discarded items by discarding step, and, when a filter discarded the most, the
  suggestion to move that filter before the step. A warning from a quarter of the step's cost, info otherwise.
- **`distillable`**, per agent step meeting every criterion of section 11.5: at least
  `improve.distill.minDeliveries` deliveries created in the window; three quarters or more of its output schema's
  leaf fields bounded (an `enum` or `const`, a boolean, a number with a minimum and a maximum, a string with a
  `format`, a `pattern` or a `maxLength` of at most 64, local `$ref`s followed, `anyOf`/`oneOf` of bounded leaves) or
  copied (every sampled output holding the field has its input's value there; up to 50 deliveries are sampled); a
  p95 of at most two turns per delivery and no `tools` or `mcp`; and, when people decided items it published, at
  least 95% of those decisions approving without an edit attributed to it. Its evidence lists the fields by class,
  the cost in the window and the monthly saving (the window's cost times 30), and `rank` orders the pipeline's
  candidates by saving. Info.
- **`drift`** from audits, per step with at least 5 audits that ended in the window with an agreement (from the
  `auditEnded` events): a warning when the fallback disagreed with the primary on more than 5% of them, with the
  counts (agreed, disagreed, failed), the agreement and up to 20 disagreeing items as samples.
- **`unschedulable`**, per step and class: attempts failed `unsupported` (a kind or runtime this deployment lacks) or
  `sandbox` (an agent step without a sandbox); an error.
- **States.** A fingerprint is a hash of the kind, the pipeline and what makes the insight distinct (its step, and a
  cluster's class and message). The first pass that finds one opens it; later passes update its figures; a pass that
  evaluates its kind without finding it resolves it, an acknowledged one included; a resolved insight found again
  reopens. A muted insight keeps its state whatever the projector finds. Opening and resolving record
  `insightOpened` and `insightResolved` events, and a rise of an open or acknowledged insight's severity records
  `insightEscalated`. A kind that `insights.disable` turns off is not evaluated, and its
  insights stay as they are; so do a pipeline's when `insights.enabled` is false.
- **Run report.** Slowest steps by p95 latency; failures grouped as for `failureCluster`; the comparison is with the
  median duration, cost, item count and failed attempts of the last 10 runs of the same kind settled before the run
  started; the ETA of a running run is its start plus their median duration.

New, reopened and escalated insights are also published through `insight` triggers (section 4.6), which is how the
`improve` pipeline is started. Insights are on by default. `insights.enabled: false` turns them off, in the pipeline
file or for the whole deployment in the environment file; `insights.disable: [drift, waste]` turns off individual
kinds.

### 11.2 Evidence

Production is where the data is; development is where changes are made. The environment file says which one a
deployment is (`environment: production | development`; `serve` defaults to production, `run` to development). In
production the `improve` pipeline does not run and `improve.publish: apply` is refused (D31): an environment file
that names production refuses `improve.enabled` and `improve.publish: apply` when it is parsed, `serve` refuses them
under its production default before it opens anything, and the commands that run the `improve` pipeline refuse to
in production. The engine reports its environment in `/api/v1/nodes`, and the web UI's header shows it.

- **Export.** `millstream evidence export --pipeline <p> [--since 30d] [--insight <id>]` runs in production and writes
  an **evidence bundle**: the open insights; a stratified sample of items (`improve.evidence.sample`, default 500)
  with the inputs and outputs of every step on their lineage; review decisions with reason codes and edit diffs; agent
  transcripts; and the production revision hash.
- **Bundle.** A gzip-compressed tar: `manifest.json` first (`format: millstream-evidence`, `version: 1`, the bundle id,
  the pipeline, the production revision with its package hash, exported and expiry instants, the scope, the sampled
  deliveries per stratum), `evidence.json` (insights, the sample, items, deliveries, reviews, transcripts' entries),
  `package` (the production revision's package) and `transcripts/<sha256>`. A reader refuses another format or version.
- **Sample.** The deliveries created within `--since` that ended are stratified by outcome: `done`, `filtered`, `dead`,
  and for a review step's, its decision, `approved`, `rejected` or `edited`. Each stratum gets an equal share of the
  sample, a stratum with fewer deliveries handing what it leaves to the others, and within a stratum the picks are
  evenly spaced in the order the deliveries finished, so the sample spans the window. The bundle holds each sampled
  delivery's item with its ancestors and descendants in the pipeline (a dead letter included), every delivery of those
  items within the window (state, attempts, error class and message, filter reason, cost, timings), the decided and
  timed-out reviews among them, and the artifacts their attempts kept. `--insight` carries that insight alone, samples
  its step, and adds the items its evidence lists.
- **Redaction.** Secrets are already redacted. A stream may list JSON pointers to redact
  (`streams: { listings.raw: { redact: [/seller/phone] } }`); an item's pointers are its stream's and its ancestors'
  streams', over every revision of the pipeline, since steps carry fields along. Exported payloads replace those values
  with a stable hash, so they can still be compared but not read: `hmac:` and the HMAC-SHA256 of the value's canonical
  JSON under the deployment's redaction key, cut to 128 bits. The key is made at random by the first export and kept in
  the store (`evidence_key`), never exported, so a hash cannot be reversed or matched against guesses outside the
  deployment, and two bundles of one deployment hash a value alike. A string value of 4 bytes or more, an object or an
  array found at a pointer is also replaced wherever else the bundle holds it: other payloads, edits, error messages,
  item keys, transcripts and the insights' evidence (an example error, a filter's condition), a string inside a longer
  text included. Reviewer identities are never exported: a review says only whether a person, the rule or the timeout
  decided it, and keeps no free text.
- **Expiry and audit.** A bundle expires (`improve.evidence.ttl`, default 30 days). Production records every export in
  `evidence_exports`: who, when, the scope and the item keys it contains, so `millstream purge --key` lists the
  bundles that held an erased key.
- **Import.** `millstream evidence import <bundle>` loads a bundle into a development deployment as read-only history
  that insights, backtests and the `improve` pipeline use like local history. Imported evidence is a namespace of its
  own: the bundle is kept whole in the artifact store under its pipeline's prefix, recorded in `evidence_imports`, and
  read back by those consumers (`internal/evidence.Load`) as items, deliveries and reviews in the store's shapes;
  nothing is written to the deployment's own items, deliveries or reviews. Import refuses a production deployment (the
  environment's effective mode: `run`'s and the commands' default is development, `serve`'s production) and an expired
  bundle, and the development engine deletes imported evidence when it expires. Importing a bundle again changes
  nothing. Import, and backtests, report when the development package has diverged from the bundle's production
  revision (their package hashes differ).

### 11.3 Proposals

A **proposal** is a reviewable change to the pipeline's sources: a patch against the pipeline file, an action's
`prompt.md`, a lessons file, action code or evals, with its rationale, the insights it answers, the base revision
hash and a validation report.

| Kind | Changes |
| --- | --- |
| `config` | Retries, timeouts, concurrency, thresholds, `review.autoApprove` |
| `prompt` | An agent action's `prompt.md` |
| `lessons` | A step's lessons file (section 11.4) |
| `topology` | Inserting, moving or removing steps, such as moving a filter upstream |
| `distill` | Code replacing an agent step, with the agent kept as fallback (section 11.5) |

States: `drafting`, `validating`, `ready`, then `accepted`, `rejected` or `stale`. A proposal becomes `stale` when its
base revision is no longer current; it is revalidated on the current revision (the patch is rebased, and the evals and
backtest rerun) or closed.

**The `improve` pipeline** is an ordinary package, `millstream/improve`, embedded in the binary and run only in
development deployments (D30). It is off until `improve.enabled` is set and a harness is configured, so insights work
without an API key. It reads an `insight` trigger stream (insights at or above `improve.minSeverity`), a weekly cron,
and the manual trigger behind "Propose a fix". Its steps are ordinary actions calling the public HTTP API with a token
limited to proposals: `gather-evidence`, `draft` (an agent), `validate` (the backtest and eval endpoints), `propose` and
`publish`. It has budgets, transcripts, replay and the UI like any pipeline, and its own `improve.budget.dayUsd`;
backtests that call agents count against it. The engine holds no improvement logic beyond insights, evidence, the
backtest endpoint and the proposal rules it enforces; the package can be read, forked
(`millstream init pipeline --from improve`) or replaced.

How M5 builds it (`internal/improve`, its package under `internal/improve/package`):

- **Hosting.** `run` (while it serves the API) and `serve` load the embedded package when `improve.enabled` is set,
  refusing it in production and without `improve.harness`, with the environment file's settings filled in: the
  draft agent's harness (`claude-code`, the CLI's `sonnet`; or `api`, `claude-sonnet-5-5` with its key in the
  `anthropicKey` secret), `budget.dayUsd` from `improve.budget.dayUsd`, and the defaults of its variables
  `publisher` (`improve.publish`), `lessonsMaxTokens`, `maxFalseDrop` and `minSeverity`. At start the engine mints
  the proposals-only token and gives the package two secrets, `improveApi` (the URL it serves the API on) and
  `improveToken`. The exec steps run the binary itself, `millstream improve-action <step>` (section 6.2).
- **Triggers.** `insights` (an insight trigger at `improve.minSeverity`), `weekly` (Mondays 06:00) and `propose`
  (manual, `{pipeline?, insight?}`: the Improve view's "Propose a fix", and `millstream improve`).
- **`gather-evidence`** reads the insight named (any severity), or on the weekly run and a manual run naming none
  every open insight of the other pipelines at or above `minSeverity`, and the lessons files past 80% of
  `lessons.maxTokens`. Each insight gives its ideas: a `reviewPattern`'s hints (`lessons` from recurring edits,
  `config` for `autoApprove` or new reason codes, `topology` for a filter), `config` for a `failureCluster` or a
  `slowStep`. An idea's fingerprint hashes the pipeline, the kind and what its hint names, never an id; an idea
  with a drafting, validating or ready proposal is left out, and a filter hint dropping more of past approvals
  than `maxFalseDrop` too. Each idea is one output: the pipeline, its active revision's package hash, the kind, the
  fingerprint, the insights, and the brief the agent reads: the insight's evidence without its times and item ids,
  the hint, up to five reviewer edits (the item as the review received it, the value before and after), the
  reasons people rejected proposals of the same fingerprint, and the files the kind may change.
- **`draft`** is an agent action. Its answer is `{kind, rationale, insights, files: [{path, content}]}` (each
  changed file's whole content) or `patch` (the `internal/patch` diff) instead of `files`; kind `none` proposes
  nothing.
- **`validate`** reads the draft's evidence back (its parent item), diffs the files against the base revision with
  its `Millstream-Base` trailer, and creates the proposal with the idea's fingerprint; the engine validates it before
  it answers. Its outcome is `proposed` (with the proposal's state), `suppressed` (a conflict: rejected, evidence
  unchanged), `refused` (the path rules, or a draft of another kind) or `skipped`.
- **`propose`** reads the proposal back and records its state, rationale and insights. **`publish`** hands each
  accepted proposal (those of its run, and on the weekly run every accepted one) to the `improve.Publisher`
  registered under `improve.publish`; without one the proposal stays accepted, unpublished, and says why.

**Validation** is done by the engine, not by an LLM:

1. `check` on the patched pipeline.
2. The evals of every affected action, before and after.
3. **Backtest** (`POST /api/v1/backtests`): the changed steps are replayed on a stratified sample of past items, from
   local history or imported evidence (`improve.backtest.sample`, default 200, including reviewed and dead-lettered
   items), in a scratch store with every `effects: external` action stubbed, so a backtest has no side effects.
   Unchanged upstream steps reuse their recorded outputs. A topology change that admits items the historical runs
   discarded reruns the downstream steps those items now reach, charged to the improve budget. The report compares,
   before and after: agreement with historical outputs, agreement with reviewer decisions, failure rate, cost and
   latency. As built (`internal/backtest`):
   - **The patch** is a unified diff against the base revision's package files, as `git diff` writes it
     (`internal/patch`), its base named in its preamble by a `Millstream-Base: <package hash>` trailer; it applies only
     to that revision, each hunk at the lines it names, exactly. A path is relative and clean, never under `.git` or
     `.millstream`, never the environment file; renames, copies, mode changes, symlinks and binary contents are
     refused. The exec actions whose files a patch touches run in the container sandbox (section 15.3), and a
     deployment without a container runtime refuses the patch, since exec actions otherwise run with the node's
     privileges; the container actions whose files it touches run without the network.
   - **Changed steps** are those whose action, inputs, outputs, config, retry, timeout, fallback or lessons the patch
     changes, whose action directory or lessons file it touches, that name a variable whose default it changes, or
     that read a stream a removed step produced; a request may add steps. The sample is drawn as an export draws it
     (section 11.2) from the deliveries that ended at the changed steps, the steps reading their inputs in the base,
     and everything downstream; only lineages that replay from a trigger item count (not import or replay runs, nor
     a payload gone). Local history is used when it has any, else the imported evidence.
   - **Replays.** Each sampled delivery's run is fired again, with its trigger, key and variables (those it took from
     a default the patch changes take the new default), in a SQLite Memory store, so its items keep their historical
     ids; once on the base revision ("before") and once patched ("after"). Every delivery is decided before it runs:
     one off the sampled lineages is cut short; an `effects: external` action takes its recorded outcome when its
     input is the historical one and publishes nothing otherwise, never running; an unchanged review takes its
     recorded decision, or stops (nobody reviews a backtest); an unchanged step on its historical input takes its
     recorded outcome; everything else runs. A replay makes the attempts its step's retry policy allows.
   - **The report** measures each replay over the sample and per changed step: agreement (the same state and outputs as
     the historical delivery), split between the lineages no review lies below and the reviewed ones, with the share of
     the latter that moved toward the reviewers' truth, deliveries newly reached and no longer reached, agreement with
     the reviewers (an approved item still reaching its review, an edited one reaching it with the edited values, a
     rejected one no longer reaching it) and the approved items no longer reaching their review (what a filter wrongly
     drops), failure rate, cost and mean latency of what ran, and the revisions the sample was recorded on other than
     the base (divergence). What both replays cost is charged to `improve.budget.dayUsd`: a backtest is refused once the
     day's budget is spent, and stops when its replays pass what is left. A production deployment runs no backtest.
4. Acceptance uses the evals of the base revision. A proposal that changes evals is judged by the base evals, and its
   new evals are reported separately, so a proposal cannot redefine its own success.

**Adoption.** Accepting a proposal hands it to the action named by `improve.publish`. `apply` creates a development
revision directly; `patch-file` writes a patch; `git-pr-gh` and `git-pr-glab` open a branch and pull request through
the `gh` and `glab` CLIs, with credentials the environment file only names: the variables passed to the action's
container (`improve.git.env`). Millstream itself stores no forge credential (D32). Publishing follows the rules of
section 11.7. The change reaches production when the package is released there, like any other change.

**Acceptance is conditional on the base revision** (D34):

- Accepting is one writer transaction (section 5.11) that succeeds only if the pipeline's active revision is still the
  proposal's base; otherwise the proposal becomes `stale`. The `apply` publish action creates the new revision under
  the same condition.
- In that transaction, every other open proposal that touches the same files or the same step becomes `stale`, so
  two proposals validated on the same base are never combined unvalidated.
- With the git publish actions, acceptance opens a pull request and the merge happens outside Millstream. When a
  revision is applied, the engine reads the `Millstream-Proposal` trailers of its commits. If the revision's parent is
  not the proposal's validated base, the proposal is recorded as accepted but not validated in this combination, and
  the engine runs the evals and a backtest of the new revision against the previous one, raising an insight on a
  regression.

**Rejection** asks for a reason, which is recorded and given to later drafts. The proposal's fingerprint is
suppressed, so the same idea comes back only when its evidence changes materially (by default, when the insight's
severity doubles).

How M5 implements them (`internal/proposals`, `engine/proposals.go`, the units of section 5.11):

- **Patches.** A proposal's patch is the backtest's (`internal/patch`, above): a unified diff of the package as
  `git diff` writes it, applied in memory to the base revision's files, each hunk at the lines it names, exactly; a
  `Millstream-Base` trailer, when present, must name the proposal's base. The patch's SHA-256 (`patch.Hash`) is its
  hash. The patched package must parse; `check` is the validation's.
- **Creation.** `POST /api/v1/proposals` (or `millstream proposals create`) names the pipeline, the kind, the patch,
  a rationale and the insights it answers. The engine applies the patch to the pipeline's active revision under its
  kind's path rules (section 11.7), derives the paths and steps it touches (steps added, removed or changed in the
  pipeline file, steps whose action or fallback is an action directory it changes, steps whose lessons file it
  changes), and records it `drafting`; then it validates it before answering. A proposal's fingerprint is the
  drafter's, or else a hash of the pipeline, the kind, the insights and the paths.
- **Validation.** The proposal is `validating` while it runs, for at most `improve.validation.timeout` (default 30
  minutes), whether or not the request that started it waits: one validating for longer is presumed lost and the next
  validation takes it over, and an engine that starts or takes the lead puts the proposals left validating back to
  `drafting`. Evals affect a step when the patch changes its action, or its action's directory: the base revision's
  cases of the base action run on the base action (before) and on the step's action after the patch (after); they pass
  when no case that passed before fails after. Cases the patch adds or changes run after alone, under `newEvals`, and
  never decide. Evals run as `millstream eval` runs them (replay of the action's recordings by default). The backtest is
  the engine's backtest runner (section 13's `backtest`, the one behind `POST /api/v1/backtests`) on the patch, with the
  touched steps the patched pipeline keeps. It passes when, over the whole sample, the patched replay against the base
  revision's: agreement with the reviewers' decisions falls by at most 0.02 (two points); agreement with the historical
  outputs of the lineages no review lies below falls by at most 0.02; on the reviewed lineages (a decided review below
  the delivery's item) it may fall further only by the share of their deliveries that moved toward the reviewers' truth,
  changed so that every review below now agrees (the edited values reached, the rejected item no longer reaching its
  review) with an edit or rejection among them, so that fixing one reviewed item never pays for changing the outputs
  nobody reviewed; an agreement with nothing to compare not counting; the failure rate does not rise at all; and the
  approved items no longer reaching their review stay within `improve.filter.maxFalseDrop` of the sample's approvals
  (section 11.6). A pipeline whose history never reaches the changed steps has nothing to regress: its backtest samples
  nothing, says so in its report's warnings, and passes. Any other refusal (a spent improve budget, a production
  deployment, proposed exec code without a sandbox, or that does not build there) fails the backtest, its reason in the
  report. The evals' "after" side runs proposed exec code in the same sandbox; without one, those cases fail unrun. A
  check error stops the validation before the evals and the backtest. The report is kept with the proposal: `ready` when
  it passed, `drafting` again otherwise, `stale` when the base moved meanwhile.
- **Revalidation.** `POST /proposals/{id}/revalidate` validates a proposal again. A stale one is first rebased: its
  patch is applied to the active revision, each hunk where its context and removed lines now are, exactly, at the
  line it names or the nearest offset (never with fuzz), and the patch from the active revision to the result, with
  that revision's `Millstream-Base` trailer, becomes its patch, with a new hash; one that does not apply stays stale.
  A proposal made stale by an accepted one while its base is still the active revision is not revalidated (a
  conflict) until the accepted one is applied.
- **Suppression.** Severities weigh info 1, warning 2, error 4: a rejection records the highest weight among the
  proposal's insights, and a new proposal of the pipeline with the same fingerprint is refused (a conflict) until one
  of its insights weighs twice that. A proposal answering no insight is never suppressed. Rejected proposals, with
  their reasons, are listed with `state=rejected` for later drafts.
- **The proposals-only token.** `POST /api/v1/proposal-token` (or `millstream proposals token`) mints it, replacing
  the earlier one, and answers it once; the store keeps its SHA-256 (`proposal_token`). A request bearing it reaches
  listing, reading, creating, revalidating and publishing proposals, the backtest endpoints (starting one and reading
  it) and the OpenAPI document, and the reads the improve pipeline gathers evidence with (insights, pipelines, a
  revision and its files, an item and its lineage), and is `forbidden` anywhere else, with or without `auth.token`:
  accepting and rejecting stay a person's. Proposals it creates are recorded as created by `improve`.
- **Publishing** (`internal/publish`). The publish actions run in the engine (`run`, `serve`): `publish.New` returns
  the action `improve.publish` names, behind `Verify`: the patch must hash to the validated hash and pass its kind's
  path rules on its base (`proposals.Prepare`), or it is refused. `POST /proposals/{id}/publish` (`publish.Proposal`)
  publishes an accepted proposal whose `patchSha256` the caller names, once, and records `proposalPublished` with
  where it went; asked again, it answers that with `again`. The improve package's publish step reaches it through
  the publisher its four names are registered to (`improve.RegisterPublisher`), with the proposals-only token, after
  checking the patch's hash itself; the token never applies a revision otherwise.
  `apply` hands the patched files to the engine, which applies them only while the active revision is still the base,
  in the apply unit itself (`store.PackageRecord.Base`), and never in production; `patch-file` writes the validated
  bytes as `<improve.patchFile.dir>/<id>.patch`, refusing other bytes under that name; the git actions are section
  11.7's.
- **Applied proposals.** `millstream apply` reads the `Millstream-Proposal` trailers of the last commit that touched
  each package directory (`git log -1 --format=%B -- .`, hooks disabled; the trailers of its last paragraph) and
  sends them with the package (`POST /revisions`, `proposals`). The apply unit records `proposalApplied` for each
  accepted proposal of the pipeline, `validated` when the revision before it is the proposal's base and the revision
  is exactly its patch over it. A revision carrying one in any other combination is validated as a proposal is, the
  change from the revision before it as the patch (check, the evals, the backtest): in the background while the engine
  runs, else before `apply` returns; a check or eval failure, or a backtest that ran and did not hold, opens a
  `regression` insight on the pipeline (warning; its evidence the revision, the proposals and the report), unless
  `insights.disable` names the kind.

### 11.4 Lessons

Lessons belong to a step, not to an action: an action may be locked, shared or from the catalog, while what was
learned is specific to how this pipeline uses it (D28).

- A step's lessons live in `lessons/<step>.yaml` in the package, or at the path given by the step key `lessons`.
  The file is part of the revision hash, so replay stays deterministic. Engineers edit it like any other file, and
  `lessons` proposals change it too.
- Content:

  ```yaml
  rules:
    - text: Listings without a surface area are not scored; return score 0 and reason "missingSurface".
      source: proposal/p-0142
      added: 2026-11-03
  examples:
    - input: { … }        # trimmed payload excerpt
      output: { … }       # the corrected output, such as a reviewer's edit
      why: "Reviewer lowered the score: ground-floor flats on a main road."
      source: review/r-8812
  ```

  A rule or example cites its `source` (a proposal, a review or an insight), and the UI links it.
- The agent adapter exposes lessons to `prompt.md` as `.Lessons` (`.Lessons.Rules`, `.Lessons.Examples`). A
  template that does not mention `.Lessons` gets a "Lessons from past runs" section appended, so lessons work with
  unchanged actions. The engine reads the file of the run's revision and sends it in `hello.lessons` (section 6.3).
- The file is parsed strictly: `rules` (each a `text`, with optional `source` and `added`) and `examples` (each an
  `input` and an `output`, with optional `why` and `source`); an unknown key is an error. `check` fails on a file
  that does not parse, an explicit `lessons` path the package lacks, and a file over `lessons.maxTokens` in the
  environment file (default 2,000; tokens are approximated as characters divided by four), never truncating
  silently. It warns on lessons given to a step that is not an agent step. As a file nears the limit, `improve`
  drafts a `lessons` proposal that merges and prunes rules.
- Lessons apply to agent steps only. In v1 every example is included in the prompt.

### 11.5 Replacing agents with code

**Candidates.** The `distillable` insight flags an agent step that meets all of:

- at least 500 deliveries in the window (`improve.distill.minDeliveries`);
- a bounded output schema: mostly enums, booleans, bounded numbers or fields copied from the input, not free prose;
- at most two turns per delivery and no external tool calls;
- where the step is reviewed, at least 95% reviewer agreement with its outputs.

Candidates are ranked by the monthly agent cost they would save.

**The `distill` proposal.** `improve` builds input and output pairs from history, treating a reviewer's edit as the
truth where there is one, and splits them into a training set given to the drafting agent and a **holdout set it never
sees**. The split is made by time and by entity (item key) before any evidence is gathered, so no holdout item, retry
of one, or lesson example derived from one reaches the drafting agent. The agent writes a code action in
`improve.distill.language` (default Go, with the SDK), with unit tests and evals. The action may **abstain** on any item
it is unsure of (section 6.3). Validation requires agreement of at least `improve.distill.minAgreement` (default 0.98)
on the holdout items the code covers, coverage (the share not abstained) of at least `improve.distill.minCoverage`
(default 0.6), and at least 200 covered holdout items, then runs the evals. The holdout is the most recent part of the
evidence, so it stands in for live traffic. The patch makes the code the step's action and moves the agent under
`fallback`.

How M5 builds it (`internal/distill`, the improve package's `distill.go`, `proposals/distill.go`):

- **The split is the engine's.** An agent step's pairs are read as backtests read history (local, else the imported
  evidence): each generation-0 delivery that ended done on an input whose payload is kept, its truth the outputs
  with the edits people made to them at a review downstream (the values the review received unchanged from the
  output); an output a person rejected has no truth and makes no pair. An entity is every pair sharing an input
  item, an item key or a lineage root, so the retries and dead-letter replays of an item, and later items of its
  key, stay with it; entities are ordered by when their first input was published, and the most recent ones making
  up half the pairs (`distill.HoldoutShare`) are the holdout, ties at the boundary included. `GET
  /api/v1/pipelines/{p}/steps/{step}/distill-training` serves the training side and the boundary (`holdoutFrom`),
  never the holdout, with the step's lessons less the examples derived from a holdout pair (whose `source` is a
  review of its truth or its item, `review/<delivery>`, `item/<id>`, or whose input is an excerpt of its input).
- **The draft.** A `distillable` insight is a `distill` idea on its step. `gather-evidence` reads the training set
  (an unsplittable history skips the idea) and writes a brief of the agent's schemas, prompt and lessons and up to
  400 training pairs, with no time or id; the new action is `actions/<step>-rules/`. The draft agent answers the
  files of that directory alone: `main.go` (the SDK's `Map`, abstaining with `Context.Abstain`), its unit tests
  and evals. `validate` adds what is not the agent's to write: the manifest (an exec action with `effects: none`,
  the agent's input and output schemas, run as a bare program of its name), `go.mod` (requiring the SDK the sandbox
  builds against), `distill.yaml` (the step, the agent and `holdoutFrom`) and the pipeline change: the step's
  block-style `action` line replaced by the new action, with `fallback: { action: <agent>, when: [abstain] }`.
- **Validation.** For a `distill` the engine reads `distill.yaml`, checks the patched step runs the new action with the
  agent as its fallback on abstain, recomputes the holdout from history with `holdoutFrom` (pairs recorded since only
  ever join it, unless their entity trained), refusing a `holdoutFrom` earlier than the earliest boundary
  `distill-training` served for the step (or, when the engine served none since it started, than the split of history
  made then): the proposer never moves the boundary back over items it trained on, and runs the code in the container
  sandbox on each holdout input, in one process: an abstention leaves the item uncovered, an error is a covered item it
  got wrong, and outputs agree when they are the truth's by key and canonical payload. The report's `distill` gives the
  holdout, the covered and agreeing items, coverage, agreement, the agent's cost over the holdout and over what the code
  covers (what it saves), the thresholds and the first disagreeing items; it takes the backtest's place. Then the evals
  decide as for any proposal: a base case the code abstains on is answered by the step's fallback.

**Fallback.** `fallback` is a general step key, also useful for hand-written rules backed by an agent:

```yaml
score:
  action: ./actions/score-rules
  fallback:
    action: ./actions/score-agent
    when: [abstain]          # also: error, for non-retryable errors
    auditRate: 0.02
```

- An abstained delivery goes to the fallback action on the same step, so output ids are unchanged; staged outputs are
  discarded first. The envelope records `producedBy`: `primary` or `fallback`. `when` defaults to `[abstain]`;
  `error` covers the primary's non-retryable errors (an abstention is not one), retryable ones being retried first.
  The fallback starts with its own retry budget; a fallback that abstains, or ends dead, dead-letters the item. A
  dead-letter replay starts again from the primary. The fallback runs with the step's config, which its config
  schema must accept.
- `auditRate` also runs the fallback on a sample of the items the primary covered; only the primary's output is
  emitted. Audits are allowed only when both actions declare `effects: none` (`check` fails otherwise). An audit is
  sent with `audit: true`, its output goes to the `audits` table, it reserves budget and is not retried. Audits are
  records, not deliveries of the run, so they never hold a run open. Disagreements raise a `drift` insight, so when
  data drifts away from the rules, `improve` proposes a fix or a rollback.
- The sample is deterministic per delivery (the audit's id, `hash("audit", delivery id)`, against the rate), so a
  delivery is audited at most once. Audits lease after the deliveries, using the slots they leave; an agent
  fallback's audit reserves its `maxCostUsd` against the day budget only, and one the budget has no room for is
  cancelled. Agreement is 1 when the fallback's outputs equal the primary's (by key, then canonical payload, in any
  order) and 0 otherwise. `run --once` exits once its runs settled and their audits ended. An audit of an item that
  expires or is erased is cancelled and keeps no outputs.
- `check` also fails on a fallback on a builtin step, a fallback action that does not resolve or is a builtin, and
  a fallback whose output schema the primary's does not accept.
- Metrics: coverage, fallback rate, fallback cost, audit agreement.

### 11.6 Learning from reviews

Each review decision records the outcome, a reason code and optional text, the diff of any edit, the time to
decision, and, through lineage, the upstream items and steps that produced the item.

**Attribution.** An edited field is attributed by walking the item's lineage upwards: the author of a value is the
nearest step whose output differs from its input on that field. Items are immutable, so the comparison is exact, and
pass-through steps (every builtin, and actions that copy a field) are never blamed. When no single step changed the
value, for example when it came from a trigger or from two parents, the edit is kept as unattributed evidence.
Precisely, from the decided item (the review's input): a builtin's item passes to its parent; an action's item with
one parent whose value at the pointer (or its absence) differs from the parent's names the action, else passes to
the parent; an action's item with several parents names the action only when it differs from every parent. A
trigger item, an item copied from another pipeline, several parents under a builtin or a value equal to one parent's,
and a parent no longer held (expired, erased, outside the store) leave the edit unattributed. The insights projector
reports the attribution and the patterns below as `reviewPattern` evidence and hints (section 11.1); the `improve`
pipeline drafts the proposals.

| Pattern | Proposal |
| --- | --- |
| Rejections predictable from fields known upstream | `topology`: a `filter` with a CEL condition, placed before the most expensive step it can precede; the backtest must show it would wrongly drop at most `improve.filter.maxFalseDrop` (default 1%) of past approvals |
| Recurring edits to the same field | `lessons` (a rule and examples taken from the edits) or `prompt`, on the attributed step |
| Near-universal approval without edits | `config`: a `review.autoApprove` rule |
| Free-text reasons no reason code covers | New codes for the step's `reasons` list, grouped by the `improve` agent |

`autoApprove` and `sampleRate` (section 8) keep people reviewing a sample of what a rule approves, so a rule that
stops being right raises an insight. The intervention rate is the headline measure of whether a pipeline is
learning. The `improve` agent sees reason codes, reason text and edit diffs, never reviewer identities, and text goes
through the same secret redaction as transcripts.

### 11.7 Publishing safely

A proposal's patch is written by an agent that read untrusted data, so publishing it follows three rules, enforced by
the engine (D33):

1. **Paths per kind.** A patch may touch only the files its kind allows, inside the package:

   | Kind | Allowed paths |
   | --- | --- |
   | `lessons` | `lessons/<step>.yaml` |
   | `prompt` | `actions/<action>/prompt.md` |
   | `config`, `topology` | `pipeline.yaml` |
   | `distill` | a new `actions/<name>/` directory, and `pipeline.yaml` |

   Symbolic links, file-mode changes and any path outside the package (CI configuration, root build files) are
   refused when the proposal is drafted and again when it is published.
2. **Separate environments.** The publish action runs in its own container with the forge credentials and nothing
   else. It never builds, never runs candidate code, and runs git with hooks disabled (`core.hooksPath=/dev/null`).
   Candidate code runs only in the network-less sandbox (section 15.3), which never holds forge credentials.
3. **The reviewed patch is the published patch.** The publish action receives the hash of the validated patch and
   refuses any other content. Pull requests carry the validation report and a `Millstream-Proposal: <id>` trailer.

Millstream cannot control a repository's CI. The documentation tells users not to expose secrets to branches pushed
by the publish action; the path rules already keep proposals away from CI files.

How M5 enforces rule 1 (`proposals.Prepare`): a `lessons` path is `lessons/<step>.yaml` for a step of the base
revision; a `prompt` path is `actions/<action>/prompt.md` of an action directory the base revision has, changed or
added, never deleted; `config` and `topology` change `pipeline.yaml` alone; a `distill` must change `pipeline.yaml`
and add files under exactly one `actions/<name>/` directory the base revision lacks. `pipeline.yaml` is only ever
changed. Whatever the kind, a patch naming a file mode other than `100644` (a symbolic link's `120000`, an executable,
an `old mode`/`new mode` change), a binary file, a rename or copy, a quoted path, or a path that is not clean and
inside the package is refused. The rules apply when the proposal is created, when it is rebased and again when it is
accepted, which also checks that the stored patch still hashes to its recorded hash, and once more when it is
published (`publish.Verify`).

How M5 enforces rules 2 and 3 (`internal/publish`): the git actions run `improve.git.image`, pinned by digest, with
the container runtime: removed on exit, never pulled, a read-only root with a private `/tmp`, no capabilities, the
node's user, the network, a work directory mounted at `/work`, and as variables only those `improve.git.env` names.
git runs with `core.hooksPath=/dev/null` (on its command line and in the global configuration it is given, so the
git processes it starts keep it), no system configuration, no prompt, the forge's CLI as its only credential helper,
and `commit --no-verify`. The container clones `improve.git.base` alone; Millstream, outside it, applies exactly the
validated patch to the package directory (`improve.git.path`) through an `os.Root`, each hunk at its lines with no
offset or fuzz, refusing a changed file that is not regular (a symbolic link) or a created one that exists; the
container then commits it with a `Millstream-Proposal: <id>` trailer (the rationale's lines that read as trailers
dropped), pushes `millstream/<id>`, never forced, and opens the pull request (`gh pr create`, `glab mr create`)
whose body holds the rationale, the base and patch hashes, whether the branch's package is the base revision, and the
validation report. Nothing from the repository is built or run, and the action holds no package, store or other
credential.

## 12. API and web UI

### 12.1 HTTP API

A versioned REST API (`/api/v1`) with a published OpenAPI 3.1 document, `internal/api/openapi.yaml`, served at
`/api/v1/openapi.yaml`: it is the contract, its tests check every route against it, and the UI's types are generated
from it. The UI and the CLI use only this API. Its JSON follows the conventions of section 5.2: lowerCamelCase keys,
RFC 3339 times, US dollars.

- Scope. Every record but a pipeline is scoped by its pipeline (section 4.10): two pipelines may hold a run, an item
  or a delivery with the same id, so resources sit under `/api/v1/pipelines/{p}`. The inbox, insights and metrics
  read across pipelines and take the pipeline as a filter.
- Read: pipelines with their active revision's graph (its imported streams with their producers among it) and state;
  revisions, a revision's graph and its package files (`GET /pipelines/{p}/revisions/{r}/files`: each UTF-8 file's text
  by path, the others named under `binary`); streams with their producers, consumers and item counts; runs, a run with
  its item counts, its report and its deliveries; items, filtered by stream, run and a CEL `where` (over `item`,
  `envelope`, `vars` and `run`, as replay's `--where`; an expression that does not compile is `invalid`, and one that
  fails on an item at run time, such as on a field the item lacks, does not match that item, as a `filter` step would
  not pass it); an item, with the pipeline of its parents when it is a copy published through an imported stream, its
  lineage up and down (each node with its pipeline: lineage crosses pipelines through imported streams, section 4.12),
  its deliveries, the fallback audits of those deliveries (`GET /pipelines/{p}/items/{i}/audits`, section 11.5) and its
  artifacts; a delivery with its attempts (read from its run's events) and the artifacts each kept, such as an agent's
  transcript; dead letters grouped by step, kind and error fingerprint; metric rollups of one metric over a range,
  grouped by a label, and the metric names; the inbox and review samples; insights; the lessons of each step of the
  active revision; the engine, with its environment and its count of failed review notifications, the deployment's
  engines (the active one with its leadership epoch and since when it leads, the standbys with since when they wait) and
  its nodes with the leases each holds: the embedded node, and the remote nodes the store records, each with its state
  (active, draining, revoked), its health from its last heartbeat (healthy within three heartbeat intervals, late within
  a lease, lost beyond) and whether it runs another version than the engine; and, from the active engine, the steps
  whose pending deliveries no registered node can take, with what they need; the session (`GET /session`: whether the
  server requires the token, who the request decides as, and the deployment's environment); a purge with its progress
  (`GET /purges/{id}`). An item, and a lineage node, carries its `tombstone` (`expired` or `erased`) once its payload is
  gone (section 9.3); an output of a step with a fallback carries `producedBy` (`primary` or `fallback`), and a delivery
  its fallback runs `fallback: true`. A standby engine serves the reads and the UI from a read-only connection and
  answers every action `503 unavailable`, naming the active engine in the `X-Millstream-Active-Engine` and
  `X-Millstream-Active-Address` headers. M4 to M6 add evidence bundles, proposals with their validation reports, and the
  pipelines importing each stream. An import run names its producer pipeline and run.
- Actions: trigger a run (a manual firing, a request id making it idempotent), rotate a webhook trigger's token
  (`POST /pipelines/{p}/triggers/{t}/token`, answering the new one once), cancel a run, pause and resume a step
  or a pipeline, replay (a replay run of a step, section 5.7, or a back-fill of an imported stream, section 4.12),
  replay or discard dead letters (one, a selection by ids, a fingerprint group, or all; a replay runs one Dead-letter
  replay unit per run), review and sample decisions,
  acknowledge or mute an insight; create, revalidate, accept (naming the `patchSha256` the decider saw) or reject (with
a `reason`) a proposal (`/proposals`, section 11.3), publish an accepted one (`POST /proposals/{id}/publish`,
naming its `patchSha256`; section 11.7) and mint the proposals-only token (`POST /proposal-token`);
disable a pipeline (`POST /pipelines/{p}/disable`; `resume` enables it again),
  roll back to a revision (`POST /pipelines/{p}/rollback`, `{revision}` or the one before the active one), and apply
  packages as new revisions (`POST /revisions`: each package's files as base64 by path with the `proposals` its
  commit's `Millstream-Proposal` trailers name, `force`, `message`; up to 64 MiB; a check error refuses them all as
  `invalid`, the warnings come back with the revisions), and purge
  (`POST /purges`: `key` or `item`, `pipeline`, `requestId`; it runs to its end before the answer, 201 when it started
  it, 200 when the request id names one already started; its `bundles` are the evidence bundles that held a key it
  erased), export evidence (`POST /pipelines/{p}/evidence`: `since`, `insight`; 201 with the bundle as
  `application/gzip`, its id in `X-Millstream-Bundle`, recorded under the request's user) and import it
  (`POST /evidence/imports`: the bundle base64 in `bundle`, up to 64 MiB; 201, or 200 when imported already, with
  both revisions and whether they diverged; `conflict` in production or for an expired bundle). M4 to M6 add draining
  or revoking a node, and requesting, accepting or rejecting a proposal. A backtest (section 11.3) is
  `POST /backtests` (`pipeline`, `baseRevision`, `patch` as the diff's text, optional `sample`, `steps` and `source`:
  `local` or `evidence`): what can be refused without running (a malformed or misbased patch, a production
  deployment, a spent improve budget) is refused at once, otherwise it answers `202` with the backtest's id and its
  `Location`, `GET /backtests/{id}`, which answers its state (`running`, `done` with its report, `failed` with an
  error's code and message). Backtests live in the engine process's memory, the last 100 kept. The training side of an
  agent step's distill split (section 11.5) is `GET /pipelines/{p}/steps/{step}/distill-training`: the training
  pairs, the boundary `holdoutFrom`, the counts and the step's lessons less the examples derived from the holdout;
  `invalid` for a step that is not an agent's or a history with nothing to split.
- Errors are `{"error": {"code", "message"}}` with a stable code: `notFound` (404), `conflict` (409: a review decided
  or escalated since the version named, a settled run cancelled, a sample decided twice), `invalid` (400: a malformed
  body, filter (an enumerated one outside its values included), cursor or CEL expression, an edit outside the
  editable pointers, a missing reason code), `unavailable` (503: the server cannot do it as configured, such as no
  artifact store, or cannot now: its term ended, or its database is out of resources or connections, shutting down,
  starting or unreachable; with `Retry-After`), `methodNotAllowed`,
  `tooLarge` (a body over 1 MiB), `unauthorized` (401), `forbidden` and `unsupportedMediaType` (below),
  `tooManyRequests` (429, with `Retry-After`: a webhook over its rate, or an address past its failed attempts, below)
  and `internal` (500, its detail logged, not sent).
- Failed attempts. A wrong token posted to `POST /session` and a failed webhook token check count against the
  request's remote address (an IPv6 one by its /64): after ten within a minute of the first, the address is answered
  `429 tooManyRequests` until that minute ends, whatever it sends. Successes do not count. The table is held in the
  engine's memory and bounded; behind a reverse proxy the address is the proxy's.
- Paging. Lists that grow without bound (runs, items, the inbox, samples) answer `{items, next}`: `next`, absent on
  the last page, is an opaque cursor the client passes back as `cursor`; `limit` is 1 to 500, 50 by default. A
  filtered item list reads at most 5,000 items per page and may answer a short page with a cursor.
- Access and who decides. Without `auth.token` (section 14), the API listens on a loopback address only (section 13)
  and records a decision under the `X-Millstream-User` header, else the server's user (`$USER`, else the system's
  account name: `millstream run` refuses to serve without one). With it (section 15.2), every request under
  `/api/v1` carries the token, as `Authorization: Bearer <token>` (the CLI's `MILLSTREAM_TOKEN`, scripts) or as the
  web UI's session cookie (`unauthorized` otherwise, with `WWW-Authenticate: Bearer`): `POST /session` with
  `{token}` sets it (`HttpOnly`, `SameSite=Strict`, `Secure` when the UI is reached over HTTPS: `tls`, a non-loopback
  `listen` or an https `ui.baseUrl`), holding a random session id that expires after 12 hours, and
  `DELETE /session` ends it; sessions live in the engine process's memory, kept across its own terms (section 5.9),
  so a restart, a token change among them, or a failover to another engine signs everyone out. A standby requires
  the token as the active engine does, and signs the UI in. Tokens are compared in constant time. The open-source
  edition is single-user: every decision is recorded under `auth.user` (`operator` by default) and
  `X-Millstream-User` is ignored. Against a web page elsewhere
  acting on it from a browser: the server answers only requests naming a loopback host, and with the token also
  `ui.baseUrl`'s host and the `listen` address's (`forbidden` otherwise, against DNS rebinding); every POST carries
  `Content-Type: application/json` (`unsupportedMediaType` otherwise), which a cross-site page cannot send without a
  CORS preflight the server never grants; a request that changes state naming another origin than the server's own
  or `ui.baseUrl`'s in its `Origin` header is `forbidden`, as is one authenticated by the cookie that names none.
  A review decision must name the version the reviewer saw (section 8), so a review escalated meanwhile is a
  conflict.
- No response may be framed by a page elsewhere (clickjacking): every one carries `X-Frame-Options: DENY` and
  `Content-Security-Policy: frame-ancestors 'none'`, and the UI's pages a policy that loads scripts, styles, fonts
  and API calls from the server only (inline styles and `data:` images allowed).
- Artifacts are served with their media type, under `Content-Security-Policy: sandbox` and without sniffing, and as
  attachments unless their type is passive (images, PDF, plain text, JSON), with a `Content-Disposition` naming the
  file either way: what an action wrote never runs in the UI's origin. They answer `Range` requests (206) and
  `If-None-Match` on their content-addressed ETag (304). Only the UI's own pages may embed one
  (`frame-ancestors 'self'`), for a PDF preview.
- Live data over **server-sent events** (D5), fed by one broker that the writer wakes after each commit, by event
  sequence, rather than one poll per client (it also reads the log every 15 seconds, for the writes of other
  processes on the same SQLite file):
  - `/api/v1/live/pipelines/{p}`: `snapshot` events, per step: queued, in flight, awaiting review, and over the last
    five minutes throughput, error rate and p95 latency; the first on connecting, then at most four a second
    (coalesced, whatever the event volume), never older than one already sent; only for a pipeline that exists;
  - `/api/v1/live/runs/{r}?pipeline={p}` and `/api/v1/live/items/{i}?pipeline={p}`: `state` events, the run's
    events or those naming the item (its publication and its deliveries' lifecycle), each with the event's sequence
    number as its id and the event as data;
  - `/api/v1/live/logs?pipeline=&run=&step=&item=&delivery=`: the live log tail (section 10.3), `log` events.
- State events carry the event sequence number, so a client reconnecting with `Last-Event-ID`, or the `lastEventId`
  query parameter for a client that opens a new EventSource, receives exactly the events of its scope it missed, in
  order, then the live ones, including across a failover. A cursor that cannot be resumed (more than 10,000 events
  behind, older than event retention, or not a position of this store) gets one `snapshotRequired` event and the
  stream ends (an EventSource cannot read a 409): the client reloads state through the REST API, then subscribes
  without a cursor. A client that falls 256 events behind is dropped, never waited for, and resumes the same way.
  Coalesced pipeline state is a snapshot each time and is not resumable. Live logs are best effort: a line's id is
  the process's epoch and the line's number; a reconnecting client gets the lines it missed while the server still
  holds them (the last 2,000), and a `gap` event first when it does not; a line's message is cut at 8 KiB, ending
  `…[truncated]`. Every stream sends a heartbeat every 15 seconds while quiet: a comment on the snapshot and log
  streams, and on a state stream a `heartbeat` event (`data: {}`) whose id is the stream's position, sent on
  subscribing too, so a quiet stream's client resumes from where the log is, not from its last event in scope,
  which may fall out of retention (a heartbeat sent while events are queued, which carry their own ids, has no id).
  Each write has a 10-second deadline: a client that stops reading is cut off.
- Webhook triggers are served at `POST /hooks/{pipeline}/{trigger}`, documented in the same OpenAPI document under
  its own server and security: like nodes, their senders are services, not browsers, so the endpoint is outside the
  Host and Origin guards and outside `auth.token`, and the trigger's own token authenticates each request (section
  4.6). A pipeline's graph names each webhook trigger's `path` and `rate`.
- Nodes use a separate, versioned endpoint (`/node/v1`) authenticated by the node token (section 15.7); the engine
  refuses a node with an incompatible protocol version (section 5.10). An engine without `node.token` serves no remote
  nodes (`notFound`); a standby answers them `503` naming the active engine. A node is not a browser: the endpoint is
  outside the Host and Origin guards and outside `auth.token` and the session cookie, which admit no node.
- A path is routed as sent, so one holding a `.` or `..` segment, escaped (`%2e%2e`) or not, is `notFound` before
  anything else: it could name `/node/v1` or `/hooks` and resolve to `/api/v1` once cleaned. Browsers resolve dot
  segments before they send a request.

is set; every command takes
`--env-file` (section 14).

Commands that change state (`apply`, `rollback`, `disable`, `pause`, `resume`, `trigger`, `cancel`, `replay`, `dlq
discard`, `purge`, the inbox decisions, `insights ack` and `mute`, `evidence export` and `import`, `proposals create`,
`accept`, `reject`, `revalidate` and `token`) go through the API of
a served engine when `--server <url>` (or `MILLSTREAM_SERVER`) names one, sending `MILLSTREAM_TOKEN` as a bearer token
when it is set and the decider as `X-Millstream-User`; through the server, `--var` is refused (the server resolves
variables from its own environment), and the inbox decisions and insight states need `--pipeline`. Otherwise they write
from their own process (section 5.9): on SQLite under its file locking; on Postgres only with `--direct`, which takes
the deployment's leadership lock like an engine but, while one holds it, fails at once naming it (for maintenance while
no engine runs), and they are refused without it, since the active engine is the only writer. Commands that only read
open Postgres without the lock, read-only, and never wait for the active engine.

`run --once` fires each pipeline's manual triggers (its first cron trigger for the current
minute when it has none), waits until those runs and every other unsettled run of the pipelines settle (replay runs
and reopened runs included) or wait only on reviews (`waitingReview`, section 8), prints each run's state and item
counts per stream, and exits 1 unless all succeeded.
`--request-id` names the manual firings, so rerunning the same command after a crash resumes the same runs instead of
firing new ones. `run --once` also waits for, and reports, the runs imported streams open for the runs it waits on
(section 4.12).

`millstream test pipeline` runs each `tests/*.yaml` of the package on a temporary store:

```yaml
name: one listing scored          # defaults to the file name
trigger: adhoc                    # defaults to the first manual trigger
payload: { city: Lyon }           # the trigger input
stubs:                            # stubbed steps complete without running their action
  crawl:
    outputs: [{ key: a, payload: { price: 1 } }]   # or error: { message: down, retryable: false }
expect: { listings: 1 }           # item count per stream once the run settles
```

`millstream test action` runs each `tests/*.yaml` of an action directory through the action, the way `eval` does: an
exec or container action as a process, an agent through the adapter with its harness calls replayed from
`tests/recordings/` by default. Outputs compare to the golden ones as JSON, as a list in emitted order:

```yaml
name: one listing scored          # defaults to the file name
input: { city: Lyon, priceEur: 180000 }   # the item's payload
config: { strict: true }          # the hello's config and vars, as a step would resolve them
vars: {}
expect:                           # outputs, or error: { retryable: false }
  outputs: [{ key: a, payload: { score: 81 } }]   # a key, when given, must match
```

It prints `PASS` or `FAIL` per case, with a line diff of the expected and actual outputs on a mismatch, and exits 1
when any case fails, 2 when there is none. The package defaults to the nearest directory above holding
`pipeline.yaml`; an exec or container action outside any package runs alone, an agent action needs its package.

`millstream init pipeline <name>` writes `<name>/` with a manual trigger and one step running a Go SDK action
(`actions/greet/`: manifest with schemas, `main.go`, `go.mod`, a fixture and an eval), a package test stubbing the
step, and a `.gitignore`; the package passes `check` and `test pipeline` as generated. `init action <name>` writes the
action alone: `--lang go` the same Go files, `--lang raw` a Python 3 program speaking the protocol with the standard
library only, a README of the protocol's messages and a fixture. A POSIX shell implementation is not offered: parsing
JSON in `sh` is not realistic. Until the Go SDK module is published, the generated `go.mod` is pointed at a checkout
with `go mod edit -replace`. Names follow the pipeline identifier rule, and init refuses a directory that exists and is
not empty.

## 14. Deployment

The package is identical everywhere; the **environment file** `millstream.yaml` describes where it runs:

```yaml

store: { postgres: { dsn: { env: MILLSTREAM_DSN } } }    # or { sqlite: { path: .millstream/millstream.db } }
artifacts: { s3: { bucket: millstream-artifacts, endpoint: https://s3.fr-par.scw.cloud } }   # or { local: { path } }
listen: 127.0.0.1:7070

tls: { cert: tls/cert.pem, key: tls/key.pem }        # optional: serve HTTPS rather than behind a TLS proxy
metrics: { public: false }                            # true: /metrics without the token
node: { embedded: true, token: { env: MILLSTREAM_NODE_TOKEN } }   # embedded: run a node inside the engine
registries: { lab: ghcr.io/monolithiclab/millstream-actions }
```

Commands read `--env-file`, else `./millstream.yaml` when it exists, else run on the defaults. Every key above parses
from M4 on; each is used as follows.

  it; a command that only reads opens it read-only, without the lock (section 13).

## 15. Security

### 15.1 Tenancy

Single-tenant: one deployment per customer, on their infrastructure or on a dedicated VPS (D6). A deployment holds
several pipelines of that organisation, isolated as in section 4.10. Data never crosses deployments.

### 15.2 Access

- The API listens on localhost by default. Exposed, it requires a bearer token (open-source edition: `auth.token`,
  the CLI's `MILLSTREAM_TOKEN`, the UI's session cookie after signing in with it, a single user named by
  `auth.user`; section 12.1), or OIDC sessions with RBAC per pipeline and inbox (commercial edition). `serve`
  refuses a non-loopback `listen` without the token. TLS is terminated by a reverse proxy in front of a loopback
  or private listener (`ui.baseUrl` https), or by the engine itself with `tls`.
- `auth.token` and `node.token` hold at least 32 characters (`openssl rand -hex 32` prints 64): `serve`, `run` and
  `node --join` refuse to start with a shorter one, naming the key and the minimum, and `check` reports it when it
  can read the value.
- Nodes authenticate with the deployment's node token over TLS (section 15.7).
- Each webhook trigger has its own token, generated at `apply`, stored as its SHA-256, rotated on demand and rate
  limited (section 4.6).
- Accepting a proposal is a separate permission in the commercial RBAC.
- The `improve` package calls the API with the proposals-only token (section 11.3), stored as its SHA-256: it reaches
  proposals, backtests, the training side of a distill split and the reads it gathers evidence with, never accepts
  or rejects, and never reaches the rest
  of the API.

### 15.3 Isolation

- `exec` actions run with the node's privileges, only on nodes started with `--allow-exec`, and are for trusted code
  only. The node embedded in `millstream run` allows `exec`: the operator runs their own packages on their own
  machine.
- A pipeline resolves only the secrets mapped for it; secrets reach nodes inside deliveries and never touch their
  disks.
- Third-party and registry actions run as containers.
- Agents run in their sandbox (section 7.3).
- Proposed code is untrusted until accepted: backtests and evals run it in the container sandbox with no network and
  with `effects: external` actions stubbed; agents run in their own sandbox as configured. The `improve` agent has
  the same sandbox and budgets as any agent.
- The sandbox (`internal/runtime/sandbox`) runs the exec actions whose files a proposal's patch touches, whether a step
  names them or not (an added action directory's evals run it too), Go modules only: each is built in a pinned Go image
  (the release Dockerfile's build stage) with no network, its source read-only, in a workspace with the SDK the binary
  embeds (`millstream.Source`), the module proxy off and the image's toolchain, so it compiles against the standard
  library and the SDK alone; then it runs in that image with no network, a read-only root, no capabilities, the node's
  user, its action directory read-only and no variable of the node's environment. Container actions whose files the
  patch touches run without the network. Without a container runtime, proposed exec code does not run: a backtest
  refuses the patch and its eval cases fail.

### 15.4 Prompt injection

Crawled pages and documents reach agents, so agent output is treated as untrusted data:

- it is validated against the output schema before it goes anywhere;
- an agent gets only the tools, MCP servers and network destinations its manifest declares, and no secrets beyond
  its config;
- `millstream check` warns when agent output can reach an `effects: external` step with no `review` step without
  `autoApprove` between them. A `filter` does not count: its condition says nothing about whether an effect is
  authorised. The check is advisory, not a security guarantee.

### 15.5 Supply chain

Registry actions and local container images are pinned by digest in `millstream.lock`. Catalog actions are signed
with cosign; the engine verifies signatures on pull when `registries.<name>.verify` is set.

### 15.6 Personal data

Streams may hold personal data (a seller's name and phone number in a listing). Retention per stream, erasure by
key (section 9.3) and secret redaction are in the open-source core: an expired payload is gone from the database
and its artifacts from the artifact store within a sweep (a day's grace for files stored again), and a purge erases
payloads, keys, artifacts, transcripts, review renderings and quoted error messages before it reports, recording
neither the key nor the item it was asked for. Event retention deletes the events themselves; database backups
taken before a purge still hold what it erased. Encryption at rest is delegated to the database
and the disk. Millstream never writes payload values to logs; logs kept by the host are outside Millstream's
retention and erasure (section 10.3).

- Evidence bundles copy production data into development: they replace the values at the pointers each stream lists,
  wherever those values travel, with a hash keyed per deployment, never carry reviewer identities or review free text,
  expire and are deleted from development when they do, and are recorded so that erasure lists the bundles holding an
  erased key; a bundle already exported is beyond a purge's reach until it expires (section 11.2).
- An imported stream copies items into the importing pipeline; `purge` follows lineage across pipelines, so erasing an
  item erases its copies and their descendants too.
- Request ids are identifiers, not data: a manual or webhook firing's request id (`Idempotency-Key`,
  `--request-id`) is the run's trigger key and part of its id (`run_<request id>_<trigger>`), which deliveries,
  events and the import runs it opened name, so a purge does not erase it (ruling of the M4 review). Senders must not
  put personal data in it: one that derives its idempotency key from personal data sends a hash of it.

### 15.7 Nodes

A deployment has one node token (D25), at least 32 characters (section 15.2), set in the environment file and given
to each node; nodes connect over TLS.

- **Leases are the capability.** A node fetches a package, or obtains a signed artifact URL, only for a delivery it
  currently holds; with no lease it can fetch nothing, so a node never reads another pipeline's data by guessing a
  hash.
- **Labels** route deliveries; they are not a security boundary in v1, since every node is run by the deployment's
  operator.
- **Revocation.** `millstream nodes revoke <id>` refuses that node id from then on and expires its leases at once, so
  fencing refuses anything it sends afterwards. Rotating the node token disconnects every node until it is given the
  new one.
- As built (M4): every fetch names the lease (pipeline, delivery, fencing token) and is checked against the engine's
  leases in flight, their owner included; a package only when it is the package of the delivery's run, an artifact URL
  only for an input of the delivery's item or an output into its pipeline; a `done` or `error` under a lease another
  node holds is refused as stale, and one naming an artifact whose content is not stored in the lease's pipeline is
  refused `invalid`. The engine copies an artifact's content into a pipeline only from the pipeline an import copy came
  from (the item's parent pipeline), never from any other pipeline holding the same hash. Revocation is recorded in the
  store's `nodes` table (an id never registered too), so a revoked id cannot register with any engine; a revocation
  another process recorded is refused from the node's next heartbeat. A revoked node, and one whose token the engine
  refuses (the token is rotated by restarting the engines with the new one), stops at once and exits with an error,
  abandoning what it holds: its leases were ended or expire, each consuming an attempt.

## 16. Testing

Testing is planned from the first commit and gated by `make ci`, which includes lint. Each milestone extends the
crash suite to the atomic units it adds.

## 20. Prior art and positioning

| Tool | What it is | Why Millstream differs |
| --- | --- | --- |
| Temporal | Durable execution of code-first workflows | Item streams and declarative graphs fit poorly; a laptop needs the dev server; our standard would be a layer on someone else's engine (D1) |
| Airflow, Dagster, Prefect | Python data orchestration | Batch and task oriented rather than item streaming; Python-centric; no agent or human step model |
| Argo Workflows | Kubernetes-native workflows | Kubernetes only |
| n8n | Low-code automation | Visual-first, sustainable-use licence, not built for engineers' code or durable item lineage |
| Redpanda Connect (Benthos) | Declarative stream processing in Go | Stream ETL, with no agents, humans, runs or lineage; part of it is now commercially licensed |
| Inngest, Trigger.dev | Event-driven functions | Function-centric, tied to their hosted models |
| LangGraph, CrewAI | In-process agent frameworks | They orchestrate inside one agent; they can run inside a Millstream agent action |

Millstream's position: declarative item-stream pipelines that mix code, agents and people in one graph; one binary from
laptop to a server with a hot standby and remote nodes; isolated pipelines that can read each other's streams; lineage,
evals,
cost, insights and human-intervention rate built in; pipelines that learn from production through validated
proposals; an open action protocol any language can implement.
