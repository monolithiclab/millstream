# Millstream: platform design

Date: 2026-10-14. Status: draft for review. Name chosen in
[the naming note](../research/20261014.naming.md), pending a trademark search.

Millstream is a pipeline platform for processing work that mixes code, LLM agents and human decisions. A pipeline is
a graph of actions connected by persisted streams of items. It runs on a laptop with one binary, and unchanged on a
VPS or a Kubernetes cluster. Every pipeline is instrumented by default.

Decisions referenced as `Dn` are recorded in [`docs/decisions.md`](../decisions.md).

## 1. Purpose

### 1.1 The problem

Most of the automation a forward-deployed engineering (FDE) team builds for a customer has the same shape: a chain
of `input → action → output` steps, where one step's output is the next step's input. Some steps are plain code
(crawl, compute, render), some are LLM agents (classify, score, extract, write), and some need a human to approve.

Built ad hoc, each project re-implements scheduling, fan-out, retries, error collection, cost tracking and a way to
see what happened. The result can't be reused at the next customer, and nobody can answer "how many listings did we
score yesterday, what did it cost, and which ones failed?" without reading logs.

### 1.2 What Millstream is

- **A standard way to define pipelines:** a declarative file describing triggers, streams and steps, validated
  before it runs.
- **A standard action contract:** any program that speaks a small JSON-lines protocol is an action, whatever its
  language, and agents are actions like any other.
- **A durable, observable runtime:** every item is persisted, every state change is an event, and metrics, lineage,
  logs and a live view come for free.
- **One engine from laptop to cluster:** the same pipeline package runs with SQLite on a laptop, and on Postgres with
  an active engine, a hot standby and a fleet of worker nodes on VPSs or Kubernetes.
- **Many pipelines per instance:** each pipeline is a package with its own actions, agents, lessons, assets, secrets,
  quotas and lifecycle.
- **Pipelines that learn:** the engine analyses its own runs and reviews, and proposes validated changes (prompt
  lessons, filters, tuning, code that replaces an agent) for a person to accept.

It is used by engineers to build and run customer pipelines on customer infrastructure. The engine is open source;
a commercial layer adds what larger organisations pay for (section 17).

### 1.3 Reference example

The running example in this spec, and the end-to-end acceptance test of the platform:

1. Every day, crawl new real estate listings matching a set of filters, from several sources.
2. Score each listing.
3. For each listing scoring above a threshold, compute rentability: fees, renovation work, resale margin.
4. For each listing whose margin clears a threshold, have an analyst approve it.
5. Generate a PDF report for each approved listing.

Later, a deduplication step is inserted between crawling and scoring without touching the other steps.

### 1.4 Success criteria

- The reference pipeline runs end to end on a laptop with `millstream run`, with no service to install.
- Killing the active engine, the standby or any worker node at any point loses no item and publishes no output twice
  downstream (section 5.11).
- Hundreds of pipelines share one instance, and a backlog in one never starves another.
- Inserting a step is a change of a few lines in the pipeline file, and past items can be replayed through it.
- For any pipeline, the UI answers: what is running now, how many items went through each step, what failed and
  why, what each agent step cost, and how often a human intervened.
- On the reference pipeline, review history yields accepted proposals that lower the intervention rate and the agent
  cost without lowering agreement with reviewers.
- The same pipeline file runs on a laptop, a VPS and Kubernetes; only the environment file differs.

## 2. Scope

### 2.1 Goals for v1

- Declarative pipeline file with variables, secrets and CEL expressions; static validation.
- Durable item log with at-least-once delivery and idempotent item identity.
- Action runtimes: local executable, container, LLM agent (harness-agnostic), human review, builtins.
- Cron, manual and webhook triggers.
- Retries, dead letters, replay, pause and resume.
- Metrics, logs, lineage and traces built in; Prometheus and OpenTelemetry export.
- Self-improvement: insights, run reports, validated proposals, step lessons, and agent steps replaced by code with
  an agent fallback.
- A web UI with a live pipeline graph, run timelines, item browsing, logs, metrics and a review inbox.
- Many isolated pipelines per instance, each deployed as a package.
- An active engine with a hot standby on Postgres, and a fleet of pull-based worker nodes; 2,000 deliveries per
  second, measured.
- Laptop, VPS and Kubernetes deployments.

### 2.2 Non-goals for v1

- A graphical pipeline editor. The pipeline file in git is the source of truth (D7).
- Multi-tenant SaaS. Each customer gets their own deployment (D6).
- Exactly-once side effects on external systems. Millstream passes an idempotency key; the external system enforces it.
- Sub-second stream processing. v1 commits to 2,000 deliveries per second on one Postgres and 300 on SQLite, on a
  documented benchmark workload; about 10,000 per second is the design goal (section 5.9). Both are far above what
  agent steps need.
- An active-active control plane, with several engines dispatching at once (D25).
- Sharding pipelines across several Postgres stores (the pipeline id is already the partition key; D20).
- Federation of independent instances with their own stores, for data residency.
- Streams shared across pipelines.

## 3. Core concepts

| Concept | Definition |
| --- | --- |
| **Item** | The unit of work: a JSON payload and an envelope (section 5.2). Binaries are stored as artifacts and referenced, never inlined. |
| **Stream** | A named, persisted, typed channel of items. Steps read from and write to streams; they never reference each other. |
| **Action** | A reusable, versioned implementation described by a manifest: input, output and config schemas, a kind and a runtime. |
| **Step** | One use of an action in a pipeline: its source (triggers or streams), output stream, config and execution policy. |
| **Trigger** | What starts a run: `cron`, `manual` or `webhook`. A trigger `x` publishes one item per run to the stream `trigger.x`, which steps read like any other stream (section 4.6). |
| **Run** | One firing of a trigger. Every item descends from exactly one run. |
| **Pipeline** | One file declaring variables, secrets, triggers, streams and steps, deployed in a **package** with its local actions, lessons and assets (section 4.9). |
| **Engine** | The control-plane process: API, UI, scheduling and dispatch. One is active per deployment; a standby takes over if it dies (section 5.9). |
| **Worker node** | A process that pulls deliveries and runs actions; nodes form the fleet (section 5.10). |

Because steps only know streams, the graph is defined by which steps write to and read from each stream:

- Several steps reading one stream each receive every item (fan-out).
- Several steps writing one stream merge their outputs (fan-in of producers, for example several crawlers).
- Inserting a step means pointing it at an existing stream and re-pointing one consumer to its output.

## 4. The pipeline file

### 4.1 Example

```yaml
pipeline: property-sourcing
description: Daily sourcing of renovation opportunities

vars:
  city: Lyon
  maxPrice: 400000
  minScore: 70
  minMarginPct: 15

secrets:
  homesiteToken: { env: HOMESITE_TOKEN }

triggers:
  daily: { cron: "0 6 * * *", tz: Europe/Paris }

streams:
  listings.raw: { retention: 90d }

steps:
  crawl-homesite:
    action: lab/crawl-homesite@1.2
    in: trigger.daily
    out: listings.raw
    config:
      filters: { city: "${vars.city}", maxPrice: "${vars.maxPrice}" }
      token: "${secrets.homesiteToken}"
  crawl-classifieds:
    action: lab/crawl-classifieds@0.9
    in: trigger.daily
    out: listings.raw
    config:
      filters: { city: "${vars.city}", maxPrice: "${vars.maxPrice}" }

  dedupe:
    action: dedupe
    in: listings.raw
    out: listings.unique
    config: { key: "item.addressNorm + ':' + string(item.surfaceM2)", window: 30d }

  score:
    action: lab/score-listing@2
    in: listings.unique
    out: listings.scored
    concurrency: 8
  keep-good:
    action: filter
    in: listings.scored
    out: listings.shortlist
    config: { expr: "item.score >= vars.minScore" }

  rentability:
    action: ./actions/rentability
    in: listings.shortlist
    out: listings.priced
  keep-profitable:
    action: filter
    in: listings.priced
    out: listings.selected
    config: { expr: "item.marginPct >= vars.minMarginPct" }

  analyst-review:
    action: review
    in: listings.selected
    out: listings.approved
    config: { inbox: analysts, timeout: 72h, onTimeout: reject, editable: [/marginPct, /notes] }

  report:
    action: lab/pdf-report@1
    in: listings.approved
    out: reports.pdf

budget:
  runUsd: 25
```

### 4.2 Top-level keys

| Key | Required | Meaning |
| --- | --- | --- |
| `pipeline` | yes | Identifier, unique in a deployment: lowercase letters, digits and `-`. |
| `description` | no | Shown in the UI. |
| `vars` | no | Named values usable in config interpolation and in CEL (section 4.4). |
| `secrets` | no | Named secret references (section 4.5). |
| `triggers` | yes | Map of trigger name to trigger definition (section 4.6). |
| `streams` | no | Per-stream settings: `schema` override, `retention`. Streams are otherwise declared implicitly by use. |
| `steps` | yes | Map of step name to step definition (section 4.3). |
| `budget` | no | Cost guards: `runUsd`, `dayUsd` (section 7.5). |
| `limits` | no | `workers`, `priority`: the pipeline's share of the fleet (section 4.10). |
| `placement` | no | `labels` worker nodes must have; a step's own `placement` overrides it (section 5.10). |
| `insights` | no | `enabled`, `every`, `disable` (section 11.1). Defaults come from the environment file. |
| `improve` | no | `enabled`, `budget`, `minSeverity`, `publish`, `backtest`, `distill`, `filter` (section 11.2). Defaults come from the environment file. |

A pipeline has no version field. The engine stores each distinct package content as a **revision** (its SHA-256,
plus the git commit when the package is in a clean git tree; section 4.9), and every run records the revision it
used.

### 4.3 Step keys

| Key | Default | Meaning |
| --- | --- | --- |
| `action` | required | An action reference (section 6.2) or a builtin name. |
| `commit` | `done` | When outputs become visible downstream: `done` (atomically with the delivery's completion) or `emit` (as emitted, for streaming steps such as crawlers; section 5.2). |
| `in` | required | Stream name or list of stream names, including trigger streams (`trigger.<name>`; section 4.6). |
| `out` | — | Where outputs go, in one of three shapes (see below). Omitted only for terminal steps. The step graph is computed from `in` and `out` alone. |
| `dlq` | `<step>.dlq` | The step's dead-letter stream (section 5.3). Required when `out` uses route objects. |
| `config` | `{}` | Validated against the action's config schema. Builtins take all their parameters here. |
| `concurrency` | `1` | Maximum deliveries of this step in flight. |
| `rate` | none | Maximum deliveries of this step started per period, for example `10/min`, or `{ pool: <name> }` for a pool shared across pipelines (section 4.10). |
| `placement` | pipeline's | `labels` worker nodes must have, for example `{ gpu: "true" }`. |
| `retry` | `{maxAttempts: 3, backoff: 10s, maxBackoff: 10m}` | Exponential backoff with jitter for retryable errors. |
| `timeout` | `10m` | Per delivery. On timeout the worker is killed and the error is retryable. |
| `resources` | from manifest | `memory`, `cpu`; enforced for containers, advisory for local executables (section 6.5). |
| `paused` | `false` | Starts the step paused. |
| `fallback` | none | `action`, `when` (`abstain`, `error`), `auditRate`: a second action for the deliveries the first one abstains on or fails (section 11.4). |
| `lessons` | `lessons/<step>.yaml` if present | Agent steps: the step's lessons file (section 11.3). |

**Outputs and routing** (D33). `out` takes exactly one of three shapes, for every step, builtin or not:

```yaml
out: listings.raw                               # one stream
out: [listings.raw, listings.audit]             # every output goes to each stream
out:                                            # route objects: first match wins
  - { when: "item.city == 'Lyon'", out: listings.lyon }
  - { when: "item.city == 'Paris'", out: listings.paris }
  - { when: "true", out: listings.other }       # an explicit catch-all, if wanted
dlq: listings.unrouted
```

- Route objects are evaluated in order when an output is published (on `done`, or on `emit` for streaming steps);
  the output goes to the first route whose `when` holds. `when` is CEL over the output `item`, `vars` and `run`.
- An output that matches no route goes to the step's `dlq` as an `unrouted` dead letter (section 5.3), so a gap in
  the routes is visible and replayable, never a silent loss. A step with route objects must therefore set `dlq`.
- A list holds either stream names or route objects, never both.
- A `when` that fails to evaluate is deterministic, so the delivery fails without retry.

### 4.4 Variables and CEL

Expressions use [CEL](https://cel.dev) (D8): typed, side-effect free, bounded in cost, and with a mature Go
implementation.

- **Variables** are declared under `vars` with their default values. Values are resolved in this order, highest
  first: `--var name=value` on the command line, the overlay named by the environment file
  (`vars/prod.yaml` in the package; section 4.9), then the pipeline defaults. The resolved set is stored on each run.
- **Config interpolation.** A string in `config` may contain `${expr}`. The expression is CEL evaluated once when
  the run starts, over `vars`, `run` and `secrets`. A string made of a single `${expr}` takes the expression's type
  (`"${vars.maxPrice}"` is an integer); otherwise the result is spliced into the string.
- **Item expressions.** Builtins (`filter`, `dedupe`) and route objects in `out` evaluate CEL per item over `item`,
  `vars` and `run`.
  `item` is the payload; `envelope` gives `id`, `key`, `ts` and `attempt`.
- Action config never depends on `item`: the same config applies to every item of a run.
- Every expression is compiled and type-checked by `millstream check`. Evaluation has a cost limit; exceeding it fails
  the item as non-retryable.

The CEL context:

| Name | Type | Available in |
| --- | --- | --- |
| `vars` | map | interpolation, item expressions |
| `run` | `{id, trigger, started_at, revision}` | interpolation, item expressions |
| `secrets` | map | interpolation only |
| `item` | the payload | item expressions only |
| `envelope` | `{id, key, ts, attempt, step}` | item expressions only |

### 4.5 Secrets

`secrets` maps a name to a source: `{ env: NAME }` or `{ file: path }` in v1; Vault and Kubernetes secrets later.
A pipeline resolves only the secrets the environment file grants it (section 4.10). Secrets:

- are only usable in config interpolation, never in item expressions;
- are passed only to steps whose config references them;
- are redacted from logs, events, stored config and the UI, by value as well as by name.

### 4.6 Triggers

| Kind | Definition | Run input |
| --- | --- | --- |
| `cron` | `{cron: "<5-field spec>", tz: <IANA zone>, catchup: latest \| all \| none}` | `{trigger, scheduledAt}` |
| `manual` | `{manual: {}}`, optional `inputSchema` | The input given by `millstream trigger` or the UI, validated |
| `webhook` | `{webhook: {path: /hooks/x}, inputSchema}` | The request body, validated; authenticated by a per-trigger token |

Firing a trigger creates a run and one **trigger item** whose id is derived from the trigger name and the scheduled
time (cron) or a request id (manual, webhook). A cron trigger that fires twice for the same scheduled time, for
example after a restart, therefore creates one run, not two.

The trigger item is published to the trigger's stream, `trigger.<name>`, and steps receive it by reading that
stream with `in` (D31). Trigger streams are roots: only their trigger writes to them, and each item on them starts a
run, while items on every other stream belong to an existing run. The `trigger.` prefix is reserved, and a trigger's
`inputSchema` is the schema of its stream. A step may read trigger streams and ordinary streams together, for
example `in: [trigger.rescore, listings.unique]`.

Firings missed while no engine was running are handled by the trigger's `catchup`: `latest` (default) fires the
most recent missed time once, `all` fires each missed time, `none` records them as skipped events.

### 4.7 Builtins

| Builtin | Config | Behaviour |
| --- | --- | --- |
| `filter` | `expr` | Emits the item unchanged when `expr` is true; otherwise marks the delivery `filtered`. |
| `dedupe` | `key`, `window` | Emits the item if no item with the same key passed this step within `window`; otherwise `filtered` with reason `duplicate`. The first one wins. |
| `collect` | `onDead: wait \| proceed` | Waits for the run's items on `in`, then emits one item per run with the items as a JSON Lines artifact (section 5.6). |
| `review` | section 8 | Parks the item until a human decides. |
| `sink` | `to: file \| webhook \| artifacts`, target | Writes each item to the target. Without `out` it is terminal; with `out` it also forwards the item unchanged once written, like `tee`, so processing continues. |

Every builtin takes its parameters under `config`, like any action, and its outputs in `out`. Routing is not a
builtin: any step routes through route objects in `out` (section 4.3).

Thresholds live in `filter` steps, not inside actions, so one scoring action serves every customer and every
threshold is visible in the pipeline file.

### 4.8 Validation

`millstream check` runs before every `run`, `serve` reload and `apply`, and fails on:

- unknown actions, triggers or streams, or steps without `in`;
- an `out` list mixing stream names and route objects, a step with route objects and no `dlq`, or a `when` that
  does not compile;
- a step whose `out` is a `trigger.*` stream, or a stream named with the reserved `trigger.` prefix that matches no
  trigger;
- cycles in the step graph;
- streams that are read but never written, and `out` streams that nobody reads (warning only);
- config that does not match the action's config schema, after interpolation types are inferred;
- CEL expressions that do not compile or type-check;
- **schema incompatibility** between producers and consumers, within the subset of section 4.11; parts of a schema
  outside the subset are listed as not statically checked, and every item is also validated against the consumer's
  input schema at runtime (section 5.5);
- an agent step that can reach a step whose action declares `effects: external` without a `review` step that has no
  `autoApprove` in between (warning, advisory only; section 15.4).

`millstream graph` prints the resolved graph as Mermaid or DOT.

### 4.9 Packages

A pipeline is deployed as a **package**: a directory holding the pipeline file and everything it uses (D17).

```text
property-sourcing/
  pipeline.yaml      the pipeline file
  actions/           local actions: source with a Dockerfile, or prebuilt binaries
  lessons/           per-step lessons (section 11.3)
  evals/             pipeline-level eval cases
  assets/            static files for actions: templates, reference data, shared prompt fragments
  vars/              overlays per environment: prod.yaml, staging.yaml
  millstream.lock
```

- A **revision** is the SHA-256 of the package's content, so a change to a local action, a lesson or an asset is a
  new revision, exactly like a change to `pipeline.yaml`.
- `millstream apply <dir>` uploads the package as a content-addressed bundle. Worker nodes fetch it by hash and cache
  it (section 5.10); assets are materialised read-only under `MILLSTREAM_ASSETS` for every action of the pipeline.
- The environment file names the overlay (`varsOverlay: prod` selects `vars/prod.yaml` in every package).
- `millstream run <dir>` runs a package locally; a lone pipeline file is a package of one file.

### 4.10 Isolation between pipelines

An instance runs many pipelines of one organisation (D6), each isolated from the others:

| Concern | Mechanism |
| --- | --- |
| Data | The pipeline id scopes streams, items, deliveries, runs, events, logs, metrics, insights, proposals, inboxes and budgets. Artifacts are stored under a per-pipeline prefix. Streams are never shared across pipelines |
| Secrets | The environment file declares secret providers and grants each pipeline the secrets it may resolve; `check` fails on a reference outside the grant |
| Capacity | `limits.workers` caps a pipeline's concurrent deliveries across the fleet; `limits.priority` (`high`, `normal`, `low`) weights the dispatcher's fair queuing, so one pipeline's backlog never starves another |
| Rate limits | A step's `rate` applies to that step. A limit shared across pipelines, such as one site's crawl quota, is a named pool in the environment file, referenced as `rate: { pool: <name> }` |
| Placement | `placement.labels` on the pipeline or a step restricts its deliveries to worker nodes with those labels (section 5.10) |
| Lifecycle | Each pipeline is applied, paused, disabled, rolled back to an earlier revision or deleted on its own |
| Access | One token for every pipeline in the open-source edition; RBAC per pipeline in the commercial edition |

### 4.11 Schema compatibility

`check` proves that producers and consumers fit within a defined subset of JSON Schema 2020-12, says exactly where it
cannot, and leaves the rest to runtime validation (section 5.5) (D30).

- **Supported:** `type` (one type, or one type and `null`), `properties`, `required`, `items` as a single schema,
  `enum`, `const`, `allOf` (merged before checking), and `$ref` to the schema's own `$defs` (resolved, recursion
  allowed).
- **Rule.** For every property the consumer requires, every producer must declare it **and require it**; the
  producer's types must be a subset of the consumer's (`integer` counts as `number`, and `null` only where the
  consumer allows it); a producer's `enum` or `const` must be a subset of the consumer's `enum`; arrays and objects
  are checked recursively. Extra producer properties are allowed.
- **Not provable:** an unconstrained producer value against a consumer `enum` is a warning, not an error.
- **Outside the subset:** `anyOf`, `oneOf`, `not`, `if`/`then`/`else`, `patternProperties` and `dependentSchemas` mark
  that subtree **not statically checked**; `check` lists each one as a warning. `format`, `pattern` and numeric or
  length bounds are enforced at runtime only.
- **Refused:** a `$ref` to anything outside the schema document, which would make `check` depend on the network and
  revisions irreproducible.
- Schemas generated by the Go SDK stay inside the subset, so the common path is fully checked.

## 5. Execution model

### 5.1 Overview

The **control plane** is one active engine, optionally with a standby (section 5.9): a scheduler (triggers), a
dispatcher (deliveries), the review inbox, the HTTP API and the metrics projections, all over one **log store** (section
9). Actions run on **worker nodes** that pull deliveries (section 5.10); on a laptop one worker is embedded in the
engine. Workers are stateless and disposable; the log store is the only state (D2).

### 5.2 Item identity and envelope

Every key and every multi-word value that Millstream defines is lowerCamelCase (D34, D35): in JSON (the item
envelope, the action protocol of section 6.3, the HTTP API, event payloads) and in YAML (the pipeline file, action
manifests, the environment file, lessons), for example `runId`, `autoApprove`, `maxCostUsd`, `awaitingReview`.
Acronyms are written as words. Other names keep their own conventions: metric names follow Prometheus (`tokens_in`),
log-store tables and columns follow SQL (`staged_outputs`), CLI flags are kebab-case, environment variables are
upper snake case, and names chosen by users (pipelines, steps, streams, triggers, vars, payload fields) follow their
own grammar; the examples use camelCase for vars and payload fields.

```json
{
  "id": "it_7f3a…",
  "key": "https://www.homesite.example/annonces/123",
  "runId": "run_2026-10-14T06:00Z_daily",
  "stream": "listings.raw",
  "step": "crawl-homesite",
  "parents": ["it_19c2…"],
  "generation": 0,
  "ts": "2026-10-14T06:00:12.481Z",
  "payload": { "...": "..." },
  "artifacts": [{ "name": "photo-1.jpg", "sha256": "…", "size": 183402, "type": "image/jpeg" }]
}
```

Item ids are deterministic:

```text
id = hash(producing_step, out_stream, input_item_id, generation, key ?? output_index)
```

- `key` is set by the action on emit. It is optional for a delivery's first output and required from the second on:
  `output_index` is only stable for a single output, so the engine refuses a second emit without `key` as a
  non-retryable protocol error. A crawler keys by listing URL; the Go SDK enforces the rule.
- **Items are immutable and the first commit wins.** A retried delivery re-emits its outputs under the same ids. An
  output whose id already exists with the same payload hash is a no-op. With a different payload, the existing item
  is kept, the new payload is discarded and a `nondeterministicOutput` event is recorded, counted per step. Downstream
  steps therefore see each output once even though the action ran twice (D9).
- `generation` is allocated atomically for each replay (section 5.7), so a replay produces new items rather than
  colliding with earlier ones.

**Commit point** (D21). The step key `commit` decides when outputs become visible downstream:

- `done` (default): outputs are staged with the attempt and published in the transaction that records `done`. An
  attempt that fails, loses its lease or ends dead publishes nothing, and its staged outputs are discarded.
- `emit`: each output is published as soon as it is emitted, so a crawler's first listings are scored while it is
  still crawling. Outputs published by an attempt that later fails stay published, and a later attempt's outputs
  follow the first-commit rule. This is the documented price of streaming.

### 5.3 Deliveries

A **delivery** is one (step, input item, generation) triple, owned by one run. It is created when an item is
published to a stream the step reads, by a replay (section 5.7), or for a `collect` step when its barrier closes
(section 5.6).

```text
pending → leased → done
                 → filtered          (builtin decided not to pass it on)
                 → awaitingReview   → done | filtered
                 → failed → pending  (retryable, attempts left, after backoff)
                          → dead     (non-retryable, or attempts exhausted)
```

- **Leases.** A leased delivery has an owner node, a fencing token and an expiry, renewed by the node's heartbeat.
  When a node or the engine disappears, expired leases return to `pending`, and messages carrying a stale fencing
  token are refused (section 5.10). Lease duration defaults to 60 seconds.
- **Ordering.** Deliveries of one step are dispatched oldest first. No ordering is guaranteed across steps or across
  concurrent deliveries.
- **Dead letters.** A step's dead-letter stream is its `dlq` key, `<step>.dlq` by default. It is an ordinary
  stream: several steps may share one, and a step may read it, for example to alert. A dead letter carries its kind,
  its origin step and the error:
  - `dead`: the **input** item of a delivery that failed, with the last error;
  - `unrouted`: an **output** that matched no route object (section 4.3). The delivery itself completes and its
    other outputs are published; only that output is diverted.

  Dead letters are replayed into their run (section 5.7) or discarded with `millstream dlq discard`. Replaying a
  `dead` letter runs the step again; replaying an `unrouted` one re-evaluates the routes on the stored output,
  usually after a revision fixed them (`--migrate`).
- **Pause.** A paused step keeps receiving deliveries in `pending` and dispatches none.

### 5.4 Runs

A run is **settled** when every delivery it owns is in a terminal state (`done`, `filtered`, `dead`) and every
collect barrier of the run is closed (section 5.6). Run states:

| State | Meaning |
| --- | --- |
| `running` | Some deliveries are pending, leased or failed-awaiting-retry. |
| `waitingReview` | Only deliveries in `awaitingReview` remain. |
| `blocked` | A `collect` barrier with `onDead: wait` is held by a dead upstream delivery; nothing else can progress. |
| `succeeded` | Settled with no dead letter. |
| `completedWithErrors` | Settled with at least one dead letter (`dead` or `unrouted`). |
| `cancelled` | Cancelled by a user: pending deliveries are dropped, leased ones finish. |

### 5.5 Errors

| Class | Source | Handling |
| --- | --- | --- |
| Retryable | `{"type":"error","retryable":true}`, worker crash, timeout, agent output failing schema validation | Retry with backoff, then dead |
| Non-retryable | `retryable: false`, input failing the step's input schema, CEL cost limit exceeded | Dead immediately |
| Config | Interpolation failure at run start, missing secret | The run fails before any delivery; recorded as a run error |

Every error is stored with the attempt, the worker's last 200 log lines and, for agents, the transcript.

### 5.6 Collect

`collect` is the only way to gather a run's items, and it is a builtin run by the engine (section 4.7). There is no
collect mode in the action protocol: the action downstream of `collect` is an ordinary map action that receives one
item (D32).

When a run starts, the engine creates a **barrier** for every `collect` step the run can reach. The barrier of a
`collect` step reading stream `S` closes when, for that run:

- no delivery is non-terminal at any step that can, transitively, write to `S`;
- every barrier upstream of it is closed;
- with `config.onDead: wait` (the default), no dead letter (`dead` or `unrouted`) of the run is held upstream of it.

Closing the barrier and creating the `collect` delivery are one transaction (section 5.11), so the step fires exactly
once per run, including when `S` received nothing. The engine then streams the run's items on `S`, paged from the log
store, into a JSON Lines artifact `items.jsonl`, and emits **one** item `{run, stream, count, dead}` with that artifact
attached, under the id `hash(step, out stream, run id, generation)`. The action downstream reads the artifact line by
line (`millstream.Items` in the Go SDK), so neither the engine nor the payload ever holds the whole run.

- `onDead: wait` holds the barrier while an upstream dead letter of the run is unresolved: the run is `blocked`, the UI
  shows why and an insight is raised. It is released when the dead letters are replayed into the run and succeed, or are
  discarded.
- `onDead: proceed` fires on what succeeded and lists the dead item ids in `dead`.
- The output item's lineage records the barrier (run, step, stream) instead of every parent id; the UI expands it on
  demand. The artifact follows the retention of `S`.
- A `collect` step downstream of a `review` step waits for every review of the run, bounded by the review timeout.

### 5.7 Revisions, replay and topology changes

- **Runs are pinned to their revision** (D22). A run executes entirely on the revision it started with: graph, action
  digests, config, vars and lessons. Applying or rolling back a revision affects runs started afterwards; in-flight
  runs finish on their own revision, so a run waiting three days on a review keeps its prompt, and a step removed by
  the new revision still completes for the runs that started before it.
- **Replay** creates a run of kind `replay` that owns new deliveries for a selection of items on a step:
  `millstream replay --step score --since 7d`, `--run <id>`, `--where '<CEL>'`. It runs on the active revision (or
  `--revision`), takes a generation from a per-pipeline counter in the same transaction, and its outputs carry its own
  run id, so collect steps downstream batch per replay run. Two concurrent replays are two runs with distinct
  generations. This is how a newly inserted `dedupe` step is back-filled, and how last week's listings are re-scored
  with a new prompt.
- **Dead-letter replay** (`millstream replay --from dlq --run <id>`) reopens the original run instead, so its collect
  barriers can close. It uses the run's revision, or the active one with `--migrate`, which records the revision
  change on the run.

### 5.8 Backpressure

The log store absorbs bursts: a slow step builds a queue, visible as queue depth and oldest-pending age, and never
slows its producers. Throughput is bounded by step `concurrency` and `rate`, the pipeline's `limits`, and the
capacity of the worker nodes that match its placement.

### 5.9 Active engine and standby

One engine is active per deployment (D25). On Postgres, a second `millstream serve` on the same store runs as a **hot
standby**.

- **Leadership.** At start-up an engine opens a dedicated connection and takes a Postgres session advisory lock for
  the deployment. The holder is the active engine; a standby blocks on the lock. That connection is also the engine's
  only write connection, so an engine without the lock cannot write: there is never a second writer, whatever the
  clocks or the network do. An engine whose write connection fails stops dispatching at once and steps down. When the
  active engine dies or loses its database session (detected by TCP keepalives within about 15 seconds), Postgres
  releases the lock; the standby takes it, rebuilds its in-memory state from the store and starts dispatching,
  typically within 30 seconds.
- **Single writer** (D26). The active engine applies every state change through one writer loop that batches
  operations into transactions (group commit). Each atomic unit of section 5.11 is applied whole within a batch, and
  the writer assigns event sequence numbers in commit order, so `Last-Event-ID` resumption is gap-free, including
  across a failover. A cursor older than event retention gets `409 snapshot required`: the client reloads state
  through the REST API, then resubscribes. Reads (API, UI, projections) use a separate connection pool. SQLite uses
  the same writer loop.
- **Coordination in memory.** Step `concurrency`, pipeline `limits`, fair queuing across pipelines and rate pools
  are enforced in the active engine's memory. Budgets reserve before they spend: leasing an agent delivery writes a
  reservation of its `maxCostUsd` on the delivery, counted against the run and day budgets, and completion
  replaces it with the reported cost. A delivery whose node dies keeps its reservation as spent, so unreported spend
  is charged in full. Retries, fallbacks, audits and shadows reserve the same way, so a budget is never exceeded.
- **Takeover.** The new active engine rebuilds slots and reservations from leased deliveries, and starts each rate
  pool one interval in the future, so a failover never causes a burst. Background work (cron scheduling, collect
  barriers, the insights projector, rollups, retention) runs as loops in the active engine. Triggers fire once across
  a failover, because run and trigger item ids are deterministic and unique in the store (section 4.6).
- **Nodes during a failover** keep running their deliveries, reconnect to the new active engine (a standby answers
  `503` with the active engine's address until it takes over) and renew their leases. The 60-second lease outlasts a
  normal failover, so in-flight work is not redone.
- **Postgres availability** is the database's job: a managed service or a replicated setup. Millstream reconnects
  after a database failover. SQLite has no standby; on a laptop or a single VPS, systemd or Docker restarts the
  engine, which resumes from the store.
- **Scale** (D23). v1 commits to 2,000 deliveries per second with one active engine on one Postgres, on the
  benchmark workload of section 16. Nodes lease deliveries in batches, the writer group-commits, and `events` is
  partitioned by time so retention drops partitions. A feasibility benchmark opens M5. About 10,000 per second
  remains the design goal; it needs post-v1 work (an active-active control plane or sharding by pipeline, both in
  the roadmap), and the pipeline id is already the partition key of every table.

### 5.10 Worker fleet

Actions run on **worker nodes**: `millstream worker --join <url> --token <join token>` on a VM, a GPU machine, an
on-premises server or a Kubernetes Deployment (D19).

- **Registration.** A node registers its id, version, labels and capacity per runtime: `exec` (only with
  `--allow-exec`), `container` (Docker or Podman), `kubernetes` (the node launches action pods), and the agent
  harnesses it has. It keeps one long-lived HTTP/2 connection to the active engine and follows it across a failover
  (section 5.9).
- **Pull.** A node with free slots asks for deliveries matching its labels. The engine leases them from the store,
  following placement and fair share across pipelines, and sends each with its payload, resolved config (secrets
  included), signed URLs for input artifacts, and the package hash. The node runs the action with the stdio protocol
  of section 6.3, so actions do not change. Nodes never connect to the store.
- **Failure.** A heartbeat every 5 seconds renews all of a node's leases. A dead node's leases expire after
  `lease.duration` (60 seconds) and its deliveries return to `pending` for other nodes. Every lease carries a
  **fencing token**: a node cut off and later reconnected has its `emit` and `done` refused, so a stale owner can
  never complete a delivery that was handed to another node. When the active engine fails over, nodes reconnect to
  the new one and resend buffered messages; deterministic ids and fencing make that safe.
- **Draining.** `millstream worker drain` or SIGTERM stops pulling, lets in-flight deliveries finish within a timeout
  and releases the node, for rolling upgrades.
- **Data on nodes.** Packages are fetched by hash and cached. Artifacts move directly to and from the S3-compatible
  store through signed URLs; with a local artifact directory, the engine proxies them. Secrets stay in memory and in
  the delivery's tmpfs working directory, never on disk.
- **Placement.** A delivery no node can take (no matching label or runtime) is shown as **unschedulable** and raises
  an insight, rather than waiting silently. Queue depth per label set is exported for KEDA or a Kubernetes HPA;
  Millstream has no autoscaler of its own.
- **One code path.** `millstream run` on a laptop starts an embedded worker that pulls over an in-memory transport;
  the same dispatcher, leases and protocol run everywhere.

### 5.11 Transactions

Every guarantee in this section rests on a short list of atomic units. Each is applied whole by the engine's
writer loop (section 5.9), inside one transaction, on Postgres and SQLite alike.

| Operation | Commits together |
| --- | --- |
| Lease | After the engine's in-memory checks (concurrency, `limits`, rate slot), write the budget reservation on the delivery; mark it `leased` with its owner, a new fencing token and an expiry; record the event |
| Emit (`commit: emit`) | Check that the delivery is still leased under the message's fencing token; route the output (section 4.3): to its streams, or to the `dlq` as `unrouted`; insert each item or apply the first-commit rule (section 5.2); create its consumer deliveries, unique on (step, item, generation); record the events |
| Done | Check the fencing token; route and publish staged outputs (`commit: done`) with their consumer deliveries; mark the delivery `done`; release its slots; settle its budget reservation; close every `collect` barrier this makes closable and create its delivery (section 5.6); record the events |
| Fail | Check the fencing token; discard staged outputs; schedule the retry, or mark the delivery `dead` and append its input item to the step's `dlq`; record the events |
| Trigger | Insert the run and its trigger item under their deterministic ids (a conflict means the firing already happened); publish the item to the trigger stream; create the run's barriers and the deliveries of the steps reading that stream |
| Dedupe | Insert the dedupe key, unique on (step, key): the first insert wins and the others are `filtered` |
| Review decision | Check that the delivery is `awaitingReview`; record the decision; emit or filter |

Lease expiry is evaluated with the database clock (`now()`), never a node's clock. The
crash tests (section 16) kill the process at every boundary of every unit, not only at random points.

## 6. Actions

### 6.1 Manifest

Each action is a directory or OCI artifact containing `action.yaml`:

```yaml
name: lab/score-listing
version: 2.1.0
description: Scores a real estate listing for renovation potential
kind: agent               # exec | container | agent
effects: none             # none | external
input:  { $ref: schema/input.json }
output: { $ref: schema/output.json }
config: { $ref: schema/config.json }
lifecycle: perItem       # long (default for exec/container) | perItem (default for agent)
resources: { memory: 512Mi, cpu: "1" }
recycle: { maxItems: 5000, maxRss: 400Mi }
runtime:
  agent:
    harness: claude-code   # claude-code | agent-sdk | api
    model: claude-sonnet-5-5
    prompt: prompt.md
    tools: [WebFetch]
    mcp: []
    network: [api.anthropic.com, "*.homesite.example"]
    maxTurns: 20
    maxCostUsd: 0.50
```

Schemas are JSON Schema 2020-12. `effects: external` declares that the action changes something outside Millstream
(sends email, writes to a CRM); it drives the safety check in section 4.8 and the idempotency key in section 6.3.

### 6.2 References and resolution

| Form | Example | Resolves to |
| --- | --- | --- |
| Local path | `./actions/rentability` | A directory in the pipeline's package (section 4.9) |
| Registry | `lab/score-listing@2` | An OCI artifact; `@2` is a semver range, resolved to an exact version and digest |
| Builtin | `filter` | Compiled into the engine |

`millstream lock` writes `millstream.lock` in the package with each reference's exact version and digest;
`run` and `apply` use the lock and refuse a digest mismatch. The registry namespace maps to an OCI registry in the
environment file (`lab` → `ghcr.io/monolithiclab/millstream-actions`).

### 6.3 The action protocol

Actions talk to the engine over stdin and stdout, one JSON object per line (D3). The protocol is published as its
own versioned document so third parties can implement it.

Engine to action:

```text
{"type":"hello","protocol":1,"action":"lab/score-listing","version":"2.1.0","config":{…},"vars":{…}}
{"type":"item","delivery":"dl_…","id":"it_…","key":"…","payload":{…},"artifacts":[…],"run":{…},"attempt":1,"idempotencyKey":"…","audit":false}
{"type":"shutdown"}
```

Action to engine:

```text
{"type":"ready"}
{"type":"emit","delivery":"dl_…","key":"…","payload":{…},"artifacts":[{"name":"report.pdf","path":"out/report.pdf"}]}
{"type":"metric","delivery":"dl_…","name":"pages_fetched","value":12,"labels":{"source":"homesite"}}
{"type":"done","delivery":"dl_…"}
{"type":"error","delivery":"dl_…","message":"…","retryable":true}
{"type":"abstain","delivery":"dl_…","reason":"…"}
```

- Anything written to stderr is a log line, tagged with the run, step, item and attempt.
- A long-lived worker handles one delivery at a time; concurrency comes from running several workers. This keeps
  actions simple to write.
- Artifacts are files written under the working directory the engine gives the worker
  (`MILLSTREAM_WORKDIR`); the engine moves them to the artifact store on `emit`. Input artifacts are materialised in the
  same directory before the `item` message.
- `idempotencyKey` is `hash(step, item id, generation)`: stable across retries, new on replay.
- A second `emit` without `key` in one delivery is a non-retryable protocol error (section 5.2).
- `audit: true` marks an audit delivery (section 11.4): its emits are stored for comparison, never as items.
- `abstain` ends a delivery without output, before any `emit`. It hands the delivery to the step's `fallback`
  (section 11.4); on a step without one, it is a non-retryable error.
- A protocol violation (malformed line, `done` for an unknown delivery) kills the worker; the delivery is retried.

### 6.4 Runtimes

Runtimes are provided by worker nodes (section 5.10); a delivery goes only to a node offering the runtime it needs.

| Kind | On a node | On a Kubernetes node |
| --- | --- | --- |
| `exec` | A child process, only on nodes started with `--allow-exec` | Not offered: use `container` |
| `container` | `docker run -i` or Podman, stdio attached | A pod per worker; see below |
| `agent` | The agent adapter in a sandbox container (section 7) | Same, as a pod |
| builtins, `review` | In the control plane | In the control plane |

A node in `kubernetes` mode cannot attach to a pod's stdio. Each action pod runs `millstream worker relay` as its
entrypoint: an init container copies the static `millstream` binary into a shared volume, and the relay starts the
action's own command as a child, speaks the stdio protocol to it, and relays it to its node over an authenticated
HTTP/2 stream. Action images need no change.

### 6.5 Worker lifecycle and memory

- **Long-lived workers** (default for `exec` and `container`) handle deliveries one after another, which amortises
  start-up. Go actions are well suited to this. A worker serves only deliveries with the same action digest, config
  and vars as its `hello`, so runs on different revisions never share a worker.
- **Per-item workers** (default for agents) start fresh for each delivery, so no context leaks between items.
- **Recycling.** Each node's supervisor samples each worker's RSS every 5 seconds. A worker that reaches
  `recycle.maxRss` or `recycle.maxItems` is sent `shutdown` after its current delivery and replaced.
- **Hard limits.** Containers and pods get the manifest's memory and CPU limits. Local executables get
  `GOMEMLIMIT` set to 90% of `resources.memory` (honoured by Go SDK actions) and are killed above twice the value.
- Worker RSS, CPU, restarts and recycles are metrics, so a leak shows as a slope before it becomes a crash.
- **Engine memory.** The engine streams payloads from the log store, and `collect` pages a run's items into its
  artifact. Its RSS target is under 150 MB at the design throughput, independent of stream sizes, checked by a
  benchmark in CI.

### 6.6 SDKs

SDKs are thin wrappers over the protocol; writing an action without one is supported and documented.

```go
func main() {
    millstream.Map(func(ctx millstream.Context, in Listing) ([]Priced, error) {
        ctx.Metric("works_estimate_eur", float64(estimate))
        return []Priced{price(in, ctx.Config())}, nil
    })
}
```

- Go SDK in v1 (`millstream.Map`, `millstream.MapKeyed` for multi-emit with keys, and `millstream.Items` to read a
  `collect` artifact), with schema generation from Go types. Returning `millstream.Abstain(reason)` as the error sends
  `abstain`.
- Python SDK after v1.

## 7. Agent actions

### 7.1 Harness-agnostic adapter

An agent action is run by the **agent adapter**, a program shipped with Millstream that speaks the action protocol on
one side and drives an LLM harness on the other (D4). The engine never knows which model ran.

| Harness | How it runs |
| --- | --- |
| `claude-code` | Claude Code in headless mode, with the action's tools and MCP servers as an explicit allowlist |
| `agent-sdk` | The Claude Agent SDK, for actions that ship code around the agent loop |
| `api` | A direct model call with an adapter-run tool loop: Anthropic, Mistral, any OpenAI-compatible endpoint, or a local model |

For each delivery the adapter:

1. renders `prompt.md` (Go template) with the payload, config, vars and the step's lessons (section 11.3);
2. runs the harness in the sandbox (section 7.3) with `maxTurns` and `maxCostUsd`;
3. obtains structured output, using the harness's native structured-output support where it exists and a final
   fenced JSON block otherwise;
4. validates it against the output schema, and reports a retryable error if it does not match;
5. emits the result with metrics: `tokens_in`, `tokens_out`, `cost_usd`, `model`, `turns`, `duration_ms`.

Cost is taken from the harness when it reports it, otherwise computed from token counts and the price table in the
environment file.

### 7.2 Transcripts

The full transcript of each attempt (prompts, tool calls, results, final output) is stored as an artifact of the
delivery and shown in the item view. Secrets are redacted before storage.

### 7.3 Sandbox

Agents run in a container with a read-only filesystem except the working directory, a network allowlist taken from
`runtime.agent.network`, and only the declared tools and MCP servers. On a laptop without Docker, `claude-code`
and `api` agents may run unsandboxed only when the environment file sets `agents.allowUnsandboxed: true`, which is
logged at every start.

### 7.4 Evals

Each agent action may ship an `evals/` directory of cases: an input, and assertions on the output (CEL over the
output, or an LLM judge with a rubric). `millstream eval <action>` runs them, reports a score per case, and stores the
result as metrics so prompt and model changes are compared before they ship. Record/replay of harness calls keeps
eval and test runs deterministic in CI (section 16).

### 7.5 Budgets

- `maxCostUsd` per delivery: the adapter stops the agent and reports a non-retryable error.
- `budget.runUsd` and `budget.dayUsd` per pipeline, enforced by reservation at dispatch (section 5.9): when
  reached, every agent step of the pipeline is paused, an event is recorded and the UI shows the cause. Resuming is a
  user action.

## 8. Human review

`review` is a builtin step that parks each item in an inbox until a person decides.

| Config | Meaning |
| --- | --- |
| `inbox` | Inbox name; access to it is controlled by RBAC in the commercial layer |
| `timeout` | How long an item may wait |
| `onTimeout` | `reject`, `approve` or `escalate: <inbox>` |
| `editable` | JSON pointers the reviewer may change before approving |
| `notify` | Slack webhook, email or generic webhook, with signed approve and reject links |
| `display` | Optional template rendering the item for the reviewer |
| `reasons` | Reason codes offered to the reviewer; a rejection then requires one, with optional free text |
| `autoApprove` | CEL expression; matching items skip the inbox and are recorded as approved by `rule` |
| `sampleRate` | Share of auto-approved items also sent to a person, default `0.05`, minimum `0.01` so a rule is always measured. The item is emitted at once; the sampled review measures the rule and cannot recall the item |

- **Approve** emits the payload, as edited, to `out`. **Reject** marks the delivery `filtered` with the reviewer's
  reason. Every decision records who, when, the reason and the diff of any edit.
- Reviews are made from the web inbox, `millstream inbox`, or the signed notification links.
- Metrics: decisions by outcome and reason code, time to decision, edit rate, auto-approval rate, sampled-rule
  agreement, and **intervention rate** (reviewed items over items reaching the step), per step and per pipeline.
- Review decisions feed self-improvement (section 11.5).

## 9. Storage

### 9.1 Log store

One interface, two implementations: SQLite (pure-Go driver, no cgo) for laptops, Postgres for servers (D2).

| Table | Content |
| --- | --- |
| `packages` | Package bundles by content hash; a revision references its package |
| `revisions` | Pipeline, package hash, git commit, applied_at, state (active, rolled back) |
| `runs` | Id, pipeline, revision, trigger, kind (`trigger` or `replay`), resolved vars, state, timings, cost |
| `pipelines` | Id, active revision, state (active, paused, disabled), limits |
| `items` | Envelope and payload; immutable once written, first commit wins (section 5.2) |
| `deliveries` | Pipeline, owning run, step, item, generation, state, attempt, lease owner, fencing token and expiry, budget reservation, next attempt at, last error |
| `staged_outputs` | Outputs of `commit: done` attempts awaiting `done` (section 5.2) |
| `barriers` | Run, `collect` step, state (open, blocked, closed) (section 5.6) |
| `events` | Append-only: every state change, with a sequence number assigned by the writer in commit order (section 5.9); partitioned by time |
| `reviews` | Decisions, reviewer, reason code and text, edit diff |
| `insights` | Kind, scope, window, severity, evidence, fingerprint, state (section 11.1) |
| `proposals` | Kind, base revision, patch artifact and hash, touched paths, state, validation report, fingerprint, decision and reason (section 11.2) |
| `dedupe_keys` | Step, key, first item, seen_at |
| `logs` | Worker log lines, tagged |
| `metric_rollups` | One-minute rollups per metric and label set |
| `artifacts` | Content hash, size, type, storage location, reference count |
| `audits` | Audit delivery, fallback output, agreement, cost (section 11.4) |
| `join_tokens` | Token hash, scope (pipelines, allowed labels), reusable, expiry (section 15.7) |
| `workers` | Node id, version, labels, granted scope, capacity, certificate serial, last heartbeat, state (active, draining, revoked) |

All writes go through the active engine's writer loop on one connection (section 5.9), on Postgres and SQLite alike.
Migrations are versioned and run at start-up. Before the first public release, the schema may change without
migrations (no compatibility shims before launch).

### 9.2 Artifacts

Artifacts are content-addressed (SHA-256) in a local directory or an S3-compatible bucket, under a prefix per
pipeline, and deduplicated by hash within it. Worker nodes read and write them through signed URLs. Remote nodes need
the S3-compatible store; a local directory works with one host, where the engine proxies transfers.

### 9.3 Retention and erasure

- Retention is set per stream (payloads and artifacts), and globally for events, logs and rollups. Expired payloads
  are replaced by a tombstone; envelopes and lineage stay, so counts and lineage remain correct.
- `millstream purge --key <key>` (or `--item`) erases an item, its descendants, their artifacts and logs, for GDPR
  erasure requests, and records a purge event without the erased data.

## 10. Observability

### 10.1 One source of truth

Every state change is an event in `events`. Metrics, lineage, the live view and the audit trail are projections of
that table, so they cannot disagree (D10).

### 10.2 Metrics

| Scope | Metrics |
| --- | --- |
| Step | items in, out (per output stream), filtered, failed, dead, unrouted; queue depth; oldest pending age; delivery latency (histogram); retries |
| Worker | RSS, CPU, starts, recycles, crashes |
| Fleet | nodes by state, slots used and free per runtime and label set, queue depth per label set, unschedulable deliveries, lease expiries, fencing refusals |
| Engine | role (active, standby), API latency, dispatch rate, writer batch size and latency, failovers |
| Agent | tokens in and out, cost, turns, schema-validation failures, by model |
| Review | decisions by outcome and reason code, time to decision, edit rate, auto-approval rate, intervention rate |
| Fallback | coverage, fallback rate, fallback cost, audit agreement |
| Improvement | open insights by kind, proposals by state, acceptance rate, `improve` cost |
| Run | duration, items per stream, cost, state |
| Custom | any `metric` message from an action |

Metrics are rolled up per minute in the log store and queried by the UI, so a laptop needs nothing else. The engine
also exposes `/metrics` in Prometheus format.

### 10.3 Traces and logs

- OpenTelemetry traces follow lineage: a span per run, per item, per delivery attempt, exportable over OTLP.
- Logs are structured and stored with their tags; they can also be exported over OTLP.

## 11. Self-improvement

A pipeline learns from its own runs: what is slow, what fails and why, what reviewers reject or correct, and which
agent steps have become predictable enough to replace with code. Learnings reach production only as **proposals**
that a person accepts (D13); nothing changes behind the pipeline file, so revisions and replay stay deterministic.

The loop has three parts:

1. **Insights** (section 11.1): deterministic analysis of the log store, always on, no LLM.
2. **Proposals** (section 11.2): reviewable changes drafted by the built-in `improve` pipeline and validated by the
   engine against past items.
3. **Adoption**: an accepted proposal becomes a new revision, through git or `apply`.

### 11.1 Insights

The **insights projector** reads `events`, `deliveries`, `reviews` and the metric rollups at the end of every run
and on a schedule (`insights.every`, default `15m`), and writes to the `insights` table. Each insight has a `kind`, a
scope (pipeline, step or action), the window it covers, a severity, its evidence (the figures and up to 20 sample
item ids), a fingerprint so a recurring problem updates one row instead of adding rows, and a state: `open`,
`acknowledged`, `resolved` or `muted`.

| Kind | What it detects |
| --- | --- |
| `slowStep` | The step's share of the run's critical path, split into queue wait (raise `concurrency`) and work time (the action is slow); p95 latency regressions against the previous seven days |
| `failureCluster` | Errors normalised into a fingerprint (numbers, ids and paths stripped), with count, rate, first and last seen, and the share that succeeded on retry: flaky failures need retries, deterministic ones need a fix |
| `reviewPattern` | Per review step: rejection rate by reason code, the JSON pointers reviewers edit most, time to decision |
| `cost` | Cost per output item and per accepted item, turns per delivery, schema-validation failures, by model |
| `waste` | Items an agent step paid for that a later filter or reviewer discarded; suggests moving the filter upstream |
| `drift` | A field's output distribution moving away from its baseline (fields chosen from the output schema), and fallback audit disagreements (section 11.4) |
| `distillable` | An agent step that has become a candidate for replacement by code (section 11.4) |

Every **run report** gives the critical path, the slowest steps, failures by cluster, cost, and a comparison with
the median of the last 10 runs; a running run shows an ETA computed from history. Reports come straight from the
events and are kept even when insights are off.

Insights are on by default. `insights.enabled: false` turns them off, in the pipeline file or for the whole
deployment in `millstream.yaml`; `insights.disable: [drift, waste]` turns off individual kinds.

### 11.2 Proposals

A **proposal** is a reviewable change to the pipeline's sources: a patch against the pipeline file, an action's
`prompt.md`, a lessons file, action code or evals, with its rationale, the insights it answers, the base revision
hash and a validation report.

| Kind | Changes |
| --- | --- |
| `config` | Retries, timeouts, concurrency, thresholds, `review.autoApprove` |
| `prompt` | An agent action's `prompt.md` |
| `lessons` | A step's lessons file (section 11.3) |
| `topology` | Inserting, moving or removing steps, such as moving a filter upstream |
| `distill` | Code replacing an agent step, with the agent kept as fallback (section 11.4) |

States: `drafting`, `validating`, `ready`, then `accepted`, `rejected` or `stale`. A proposal becomes `stale` when its
base revision is no longer current; it is revalidated on the current revision (the patch is rebased, and the evals and
backtest rerun) or closed.

**The `improve` pipeline** is embedded in the binary and written in the ordinary pipeline format, so it has budgets,
transcripts, replay and the UI like any pipeline (D15). It is triggered by an insight crossing
`improve.minSeverity`, by a weekly cron, or by "Propose a fix" on an insight. Its steps select insights, gather
evidence (transcripts, review diffs, sample items), draft the proposal with an agent, validate it, and publish it. It
has its own `improve.budget.dayUsd`; backtests and shadows that call agents count against it. `improve.enabled`
turns it off, and it stays off until a harness is configured, so insights work without an API key.

**Validation** is done by the engine, not by an LLM:

1. `check` on the patched pipeline.
2. The evals of every affected action, before and after.
3. **Backtest:** the changed steps are replayed on a stratified sample of past items (`improve.backtest.sample`,
   default 200, including reviewed and dead-lettered items) in a scratch store with every sink stubbed, so a backtest
   has no side effects. Unchanged upstream steps reuse their recorded outputs. A topology change that admits items
   the historical runs discarded reruns the downstream steps those items now reach, charged to the improve budget.
   The report compares, before and after: agreement with historical outputs, agreement with reviewer decisions,
   failure rate, cost and latency.
4. **Shadow**, optional and required for `distill`: the candidate runs beside the live step on live traffic, its
   outputs are compared and never emitted.
5. Acceptance uses the evals of the base revision. A proposal that changes evals is judged by the base evals, and
   its new evals are reported separately, so a proposal cannot redefine its own success.

**Adoption.** Accepting a proposal hands it to the action named by `improve.publish`. `apply` creates a revision
directly; `patch-file` writes a patch; `git-pr-gh` and `git-pr-glab` open a branch and pull request through the
`gh` and `glab` CLIs, using the credentials those CLIs already have in the action's environment. Millstream itself
holds no forge configuration (D16). Publishing follows the rules of section 11.6.

**Acceptance is conditional on the base revision** (D29):

- Accepting is one writer transaction (section 5.9) that succeeds only if the pipeline's active revision is still the
  proposal's base; otherwise the proposal becomes `stale`. The `apply` publish action creates the new revision under the
  same condition.
- In that transaction, every other open proposal that touches the same files or the same step becomes `stale`, so
  two proposals validated on the same base are never combined unvalidated.
- With the git publish actions, acceptance opens a pull request and the merge happens outside Millstream. When a
  revision is applied, the engine reads the `Millstream-Proposal` trailers of its commits. If the revision's parent is
  not the proposal's validated base, the proposal is recorded as accepted but not validated in this combination, and the
  engine runs the evals and a backtest of the new revision against the previous one, raising an insight on a regression.

**Rejection** asks for a reason, which is recorded and given to later drafts. The proposal's fingerprint is
suppressed, so the same idea comes back only when its evidence changes materially (by default, when the insight's
severity doubles).

### 11.3 Lessons

Lessons belong to a step, not to an action: an action may be locked, shared or from the catalog, while what was
learned is specific to how this pipeline uses it (D14).

- A step's lessons live in `lessons/<step>.yaml` in the package, or at the path given by the step key
  `lessons`. The file is part of the revision hash, so replay stays deterministic. It is a plain file a person may
  also edit.
- Content:

  ```yaml
  rules:
    - text: Listings without a surface area are not scored; return score 0 and reason "missingSurface".
      source: proposal/p-0142
      added: 2026-11-03
  examples:
    - input: { … }        # trimmed payload excerpt
      output: { … }       # the corrected output, such as a reviewer's edit
      why: Reviewer lowered the score: ground-floor flats on a main road.
      source: review/r-8812
  ```

  Every rule and example carries its source, so the UI links it to the reviews and insights behind it.
- The agent adapter exposes lessons to `prompt.md` as `.Lessons`. A template that does not use them gets a "Lessons
  from past runs" section appended, so lessons work with unchanged actions.
- `lessons.maxTokens` (default 2,000) is enforced by `check`, never by silent truncation. As a file nears the limit,
  `improve` drafts a `lessons` proposal that merges and prunes rules, validated like any other.
- Lessons apply to agent steps only. Code steps improve through `config`, `topology` and code changes.
- In v1 every example is included in the prompt.

### 11.4 Replacing agents with code

**Candidates.** The `distillable` insight flags an agent step that meets all of:

- at least 500 deliveries in the window (`improve.distill.minDeliveries`);
- a bounded output schema: mostly enums, booleans, bounded numbers or fields copied from the input, not free prose;
- at most two turns per delivery and no external tool calls;
- where the step is reviewed, at least 95% reviewer agreement with its outputs.

Candidates are ranked by the monthly agent cost they would save.

**The `distill` proposal.** `improve` builds input and output pairs from history, treating a reviewer's edit as the
truth where there is one, and splits them into a training set given to the drafting agent and a **holdout set it never
sees**. The split is made by time and by entity (item key) before any evidence is gathered, so no holdout item, retry of
one, or lesson example derived from one reaches the drafting agent. The agent writes a code action in
`improve.distill.language` (default Go, with the SDK), with unit tests and evals. The action may **abstain** on any item
it is unsure of (section 6.3). Validation requires agreement of at least `improve.distill.minAgreement` (default 0.98)
on the holdout items the code covers, coverage (the share not abstained) of at least `improve.distill.minCoverage`
(default 0.6), and at least 200 covered holdout items. It runs the evals, then a shadow run on live traffic that must
meet the same three thresholds before the proposal is `ready`. The patch makes the code the step's action and moves the
agent under `fallback`.

**Fallback.** `fallback` is a general step key, also useful for hand-written rules backed by an agent:

```yaml
score:
  action: ./actions/score-rules
  fallback:
    action: ./actions/score-agent
    when: [abstain]          # also: error, for non-retryable errors before any output is published
    auditRate: 0.02
```

- An abstained delivery goes to the fallback action on the same step, so output ids (`hash(step, out stream, input id,
  generation, key ?? index)`) are unchanged. The envelope records `producedBy`: `primary` or `fallback`.
- `when: error` applies only while no output of the delivery is published: with `commit: done` the staged outputs
  are discarded first; with `commit: emit`, an error after a published output goes to the dead-letter stream.
- `auditRate` also runs the fallback on a sample of the items the primary covered; only the primary's output is
  emitted. Audits are allowed only when both actions declare `effects: none` (`check` fails otherwise). Audit
  deliveries carry `audit: true`, their outputs go to `audits`, they reserve budget, are not retried, and do not
  hold up run settlement. Disagreements raise a `drift` insight, so when data drifts away from the rules, `improve`
  proposes a fix or a rollback.
- Metrics: coverage, fallback rate, fallback cost, audit agreement.

### 11.5 Learning from reviews

Each review decision records the outcome, a reason code and optional text, the diff of any edit, the time to
decision, and, through lineage, the upstream items and steps that produced the item.

**Attribution.** An edited field is attributed by walking the item's lineage upwards: the author of a value is the
nearest step whose output differs from its input on that field. Items are immutable, so the comparison is exact, and
pass-through steps (every builtin, and actions that copy a field) are never blamed. When no single step changed the
value, for example when it came from a trigger or from two parents, the edit is kept as unattributed evidence.
Lessons and prompt changes therefore target the step that made the mistake.

| Pattern | Proposal |
| --- | --- |
| Rejections predictable from fields known upstream | `topology`: a `filter` with a CEL condition, placed before the most expensive step it can precede; the backtest must show it would wrongly drop at most `improve.filter.maxFalseDrop` (default 1%) of past approvals |
| Recurring edits to the same field | `lessons` (a rule and examples taken from the edits) or `prompt`, on the attributed step |
| Near-universal approval without edits | `config`: a `review.autoApprove` rule |
| Free-text reasons no reason code covers | New codes for the step's `reasons` list, grouped by the `improve` agent |

`autoApprove` and `sampleRate` (section 8) keep people reviewing a sample of what a rule approves, so a rule that
stops being right raises an insight. The intervention rate is the headline measure of whether a pipeline is
learning.

The `improve` agent sees reason codes, reason text and edit diffs, never reviewer identities, and text goes through
the same secret redaction as transcripts.

### 11.6 Publishing safely

A proposal's patch is written by an agent that read untrusted data, so publishing it follows three rules, enforced by
the engine (D28):

1. **Paths per kind.** A patch may touch only the files its kind allows, inside the package:

   | Kind | Allowed paths |
   | --- | --- |
   | `lessons` | `lessons/<step>.yaml` |
   | `prompt` | `actions/<action>/prompt.md` |
   | `config`, `topology` | `pipeline.yaml` |
   | `distill` | a new `actions/<name>/` directory, and `pipeline.yaml` |

   Symbolic links, file-mode changes and any path outside the package (CI configuration, root build files) are
   refused when the proposal is drafted and again when it is published.
2. **Separate environments.** The publish action runs in its own container with the forge credentials and nothing
   else. It never builds, never runs candidate code, and runs git with hooks disabled (`core.hooksPath=/dev/null`).
   Candidate code runs only in the network-less sandbox (section 15.3), which never holds forge credentials.
3. **The reviewed patch is the published patch.** The publish action receives the hash of the validated patch and
   refuses any other content. Pull requests carry the validation report and a `Millstream-Proposal: <id>` trailer.

Millstream cannot control a repository's CI. The documentation tells users not to expose secrets to branches pushed
by the publish action; the path rules already keep proposals away from CI files.

## 12. API and web UI

### 12.1 HTTP API

A versioned REST API (`/api/v1`) with a published OpenAPI document. The UI and the CLI use only this API. Its JSON
follows the conventions of section 5.2.

- Read: pipelines, revisions, runs and run reports, streams, items (with CEL filtering), item lineage, deliveries,
  logs, metrics, inbox, insights, proposals with their validation reports, lessons.
- Actions: trigger a run, cancel a run, pause and resume a step or a pipeline, disable a pipeline, roll back to a
  revision, drain or revoke a worker node, replay, review decisions, apply a revision,
  acknowledge or mute an insight, request a proposal, accept or reject a proposal.
- Live data over **server-sent events** (D5):
  - `/api/v1/live/pipelines/{p}`: per-step state (in flight, throughput, error rate, p95 latency, queue depth)
    coalesced at about 4 updates per second, whatever the item volume;
  - `/api/v1/live/runs/{r}`, `/api/v1/live/items/{i}` and `/api/v1/live/logs?…`: fine-grained events for one scope.
- New insights and proposal state changes are pushed on the pipeline stream.
- Worker nodes use a separate, versioned endpoint (`/worker/v1`) authenticated by node certificates; the engine
  refuses a node with an incompatible protocol version.
- Every SSE event carries the event sequence number, so a client reconnecting with `Last-Event-ID` resumes without
  gaps.

### 12.2 Web UI

A React and TypeScript single-page application, built with Vite and embedded in the binary (`go:embed`); `millstream
run` serves it on localhost. Graphs use React Flow; time series use uPlot. The UI is localised in English and
French from the first commit and meets WCAG 2.2 AA.

## 15. Security

### 15.1 Tenancy

Single-tenant: one deployment per customer, on their infrastructure or on a dedicated VPS (D6). A deployment holds
many pipelines of that organisation, isolated as in section 4.10. Data never crosses deployments.

### 15.2 Access

- The API listens on localhost by default. Exposed, it requires a bearer token (open-source edition), or OIDC
  sessions with RBAC per pipeline and inbox (commercial edition).
- Accepting a proposal is a separate permission in the commercial RBAC.
- Worker nodes join with a join token, which may be limited to pipelines and labels (an on-premises node can be
  bound to the one pipeline whose data must stay there). A joined node gets a short-lived client certificate,
  renewed automatically and revocable (section 15.7).
- Webhook triggers each have their own token. Review notification links are signed and expire with the review.

### 15.3 Isolation

- `exec` actions run with the node's privileges, only on nodes started with `--allow-exec`, and are for trusted code
  only.
- A pipeline resolves only the secrets granted to it; secrets reach nodes inside deliveries and never touch their
  disks.
- Third-party and registry actions run as containers.
- Agents run in their sandbox (section 7.3).
- Proposed code is untrusted until accepted: backtests and shadows run it in the container sandbox with no network
  and with stub sinks. The `improve` agent has the same sandbox and budgets as any agent.

### 15.4 Prompt injection

Crawled pages and documents reach agents, so agent output is treated as untrusted data:

- it is validated against the output schema before it goes anywhere;
- an agent gets only the tools, MCP servers and network destinations its manifest declares, and no secrets beyond
  its config;
- `millstream check` warns when agent output can reach an `effects: external` step with no `review` step without
  `autoApprove` between them. A `filter` does not count: its condition says nothing about whether an effect is
  authorised. The check is advisory, not a security guarantee.

### 15.5 Supply chain

Registry actions are pinned by digest in `millstream.lock`. Catalog actions are signed with cosign; the engine verifies
signatures on pull when `registries.<name>.verify` is set.

### 15.6 Personal data

Streams may hold personal data (a seller's name and phone number in a listing). Retention per stream, erasure by
key (section 9.3) and secret redaction are in the open-source core. Encryption at rest is delegated to the database
and the disk.

### 15.7 Worker nodes

Every node request is authorised against the node's record in the engine, and holding a lease is what grants access
to that delivery's data (D27).

- **Join tokens** are stored hashed, expire, and are single-use unless created with `--reusable` (for autoscaling
  groups). A token's scope is a set of pipelines and the labels a node may advertise.
- **Certificates** carry only the node id. The scope is copied from the token into the node's record at join time and
  checked on every request, so changing a node's scope never needs a new certificate. Certificates last 24 hours and
  renew only while the record is active.
- **Labels.** A node may advertise only labels its token allows; joining fails otherwise. Placement labels can
  therefore be relied on for data residency, not only for routing.
- **Pulls** lease only deliveries of the node's granted pipelines.
- **Packages and artifacts.** A node fetches a package, or obtains a signed artifact URL, only for a delivery it
  currently holds; with no lease, it can fetch nothing.
- **Revocation** marks the record: the node's next request is refused, its certificate is not renewed, and its leases
  are expired at once, so fencing refuses anything it sends afterwards.

## 20. Prior art and positioning

| Tool | What it is | Why Millstream differs |
| --- | --- | --- |
| Temporal | Durable execution of code-first workflows | Item streams and declarative graphs fit poorly; a laptop needs the dev server; our standard would be a layer on someone else's engine (D1) |
| Airflow, Dagster, Prefect | Python data orchestration | Batch and task oriented rather than item streaming; Python-centric; no agent or human step model |
| Argo Workflows | Kubernetes-native workflows | Kubernetes only |
| n8n | Low-code automation | Visual-first, sustainable-use licence, not built for engineers' code or durable item lineage |
| Redpanda Connect (Benthos) | Declarative stream processing in Go | Stream ETL, with no agents, humans, runs or lineage; part of it is now commercially licensed |
| Inngest, Trigger.dev | Event-driven functions | Function-centric, tied to their hosted models |
| LangGraph, CrewAI | In-process agent frameworks | They orchestrate inside one agent; they can run inside a Millstream agent action |

Millstream's position: declarative item-stream pipelines that mix code, agents and people in one graph; one binary from
laptop to an engine with a hot standby and a worker fleet; many isolated pipelines per instance; lineage, evals, cost
and human-intervention rate built in; pipelines that learn from their runs and reviews through validated proposals;
an open action protocol any language can implement.

## 21. Key decisions

| Id | Decision |
| --- | --- |
| D1 | Build a Go engine rather than build on Temporal or assemble stream tools |
| D2 | A durable item log (SQLite or Postgres) is the only state; at-least-once delivery |
| D3 | Actions speak JSON lines over stdio |
| D4 | Agent actions are harness-agnostic, run by an adapter |
| D5 | Live UI data over server-sent events, not WebSocket |
| D6 | Single-tenant deployments in v1 |
| D7 | The pipeline file is the source of truth; no graphical editor in v1 |
| D8 | CEL for every expression |
| D9 | Deterministic item ids make retries idempotent downstream |
| D10 | One event table drives metrics, lineage, live view and audit |
| D11 | Open-source core includes the whole UI; the commercial edition sells identity, governance, connectors and fleet operations |
| D12 | The product is named Millstream |
| D13 | Learnings reach production only through accepted proposals |
| D14 | Lessons are versioned per step and part of the revision hash |
| D15 | Self-improvement runs as a Millstream pipeline |
| D16 | Forge integration goes through actions; Millstream holds no forge credentials |
| D17 | The package is the unit of deployment and isolation |
| D18 | Leaderless control-plane replicas over Postgres (superseded by D25) |
| D19 | Worker nodes pull deliveries under fenced leases and never touch the store |
| D20 | Target about 10,000 deliveries per second on one Postgres; the pipeline id is the partition key for later sharding |
| D21 | Outputs publish on `done` by default; streaming on `emit` is opt-in per step |
| D22 | Runs are pinned to the revision they started with |
| D23 | v1 commits to 2,000 deliveries per second, measured; 10,000 remains the design goal (refines D20) |
| D24 | Events get their public sequence from a per-pipeline publisher (superseded by D26) |
| D25 | One active engine with a hot standby, elected by a Postgres advisory lock; active-active deferred |
| D26 | A single writer loop group-commits state changes and sequences events in commit order |
| D27 | Worker nodes are authorised per request against their record; a lease grants access to its data |
| D28 | Proposal patches are confined to paths per kind and published from an isolated environment, by hash |
| D29 | Accepting a proposal is conditional on its base revision being current |
| D30 | Static schema compatibility covers a defined subset and reports what it cannot check |
| D31 | Triggers publish to reserved trigger streams; steps read only streams, through `in` |
| D32 | `collect` is one builtin emitting a single item with a JSON Lines artifact; no collect mode in the protocol |
| D33 | Routing lives in `out` for every step (first match wins); unmatched outputs go to the step's `dlq` |
| D34 | JSON keys defined by Millstream are lowerCamelCase |
| D35 | YAML keys and multi-word enum values defined by Millstream are lowerCamelCase too |
