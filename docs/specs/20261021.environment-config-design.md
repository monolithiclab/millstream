# Environment configuration: one struct, three layers, `init environment`

Status: draft for review, 2026-10-21.

## Intent

The environment file (`millstream.yaml`, platform spec section 14) is today the only way to configure where packages
run. Nothing generates it: the tutorial has readers type YAML by hand, and Compose ships a template,
`deploy/compose/millstream.yaml`, that duplicates what the code knows. Docker and systemd would rather configure a
process through environment variables, which millstream does not read (apart from a few CLI variables).

This change makes the configuration self-describing and layered, the way gomddoc does it (its D5 and architecture's
"Configuration" section):

1. **One struct is the schema.** Sections are named struct fields; every leaf carries its YAML key, its variable name,
   its default and its one-line doc as tags.
2. **Three layers over the defaults**, the last one winning: the environment file, then `MILLSTREAM_*` variables, then
   CLI flags.
3. **`millstream init environment`** writes the default file, generated from the struct: every key, commented out, at
   its default.
4. **Docs, tutorial, help, Compose and systemd use the simplest, most direct way** for each case, and never point at a
   template file.

## Goals

- The YAML file is decoded straight into the struct (`go.yaml.in/yaml/v3`, known fields only), then variables are
  applied by walking the struct, then flags. The ~600 lines of hand-written node readers in
  `internal/pipeline/environment.go` go; what they checked moves to a `Validate` pass over the decoded struct.
- Every key of section 14 is settable from a variable named `MILLSTREAM_<SECTION>_<KEY>`.
- `init environment` and the loader cannot drift: both are projections of the same tags, held by tests.
- `deploy/compose/millstream.yaml` is deleted; Compose and systemd configure the engine with variables.
- The `lab-go-app` skill states the rule for every lab Go app: file, then variables, then flags, from one tagged
  struct.

## Non-goals

- No user-level configuration (`~/.config/millstream`, XDG): ruled out.
- No presets or profiles for `init environment`: it writes the default file only.
- No change to the file format: same keys, same shapes, same strictness. No compatibility code (pre-launch rule).
- No change to the pipeline file, the action protocol or the HTTP API.
- The CLI-client variables keep their names and meaning: `MILLSTREAM_SERVER`, `MILLSTREAM_TOKEN`, `MILLSTREAM_COLOR`,
  `MILLSTREAM_SECRET_<NAME>`, `MILLSTREAM_LIVE`. They are not configuration keys.

## Anti-goals

- A second list of keys anywhere (a template, a hand-written table in Go, a docs page the tests do not hold) that can
  disagree with the struct.
- A secret value written into the environment file, or logged, or echoed in an error.
- Weaker validation than today: an unknown key, a wrong type, a bad value must still fail with the key's path.

## Design

### The struct

`pipeline.Environment` becomes a tree of named section structs, one field per top-level key of section 14:

```go
type Environment struct {
    Mode      string          `yaml:"environment" env:"ENVIRONMENT" doc:"production or development"`
    Store     StoreConfig     `yaml:"store"       env:"STORE"`
    Artifacts ArtifactsConfig `yaml:"artifacts"   env:"ARTIFACTS"`
    Listen    string          `yaml:"listen"      env:"LISTEN" doc:"..."`
    Auth      AuthConfig      `yaml:"auth"        env:"AUTH"`
    UI        UIConfig        `yaml:"ui"          env:"UI"`
    Runtime   RuntimeConfig   `yaml:"runtime"     env:"RUNTIME"`
    // ... metrics, node, registries, secrets, retention, lessons, improve, prices, agents, engine, tls
}

type UIConfig struct {
    BaseURL string `yaml:"baseUrl" env:"BASE_URL" default:"http://127.0.0.1:7070" doc:"..."`
    Listen  string `yaml:"listen"  env:"LISTEN"   default:"127.0.0.1:7070"        doc:"..."`
}
```

- **Tags.** `yaml` (the file key, unchanged), `env` (the name segment, explicit, so `IMPROVE_PATCH_FILE_DIR` is never
  guessed from camelCase), `default` (the value before any layer, in the file's syntax: `5s`, `90d`, `true`,
  `docker`), `doc` (one line, required on every leaf; a test fails without it). A key without a default has no
  `default` tag and is generated as an empty example.
- **Section names follow the file**: `UI.BaseURL` replaces `UIBaseURL`, `Agents.Image` replaces `AgentImage`,
  `Lessons.MaxTokens` replaces `LessonsMaxTokens`, and so on. Every caller is updated (about 160 references in 17
  files); no aliases are kept.
- **Defaults live only in tags.** Today's scattered defaults (`newEnvironment`, `DefaultAuthUser`,
  `DefaultGitBase`, `DefaultDistillLanguage`, the "zero means default" comments, the 5 s engine durations, the
  retention job's 1 h, `review.DefaultBaseURL`) become `default` tags; code that read "zero means default" reads the
  value. Where a constant is still needed elsewhere, it is derived from the tag or the tag cites it, and a test holds
  them equal.
- **Field types** carry their own decoding: a `Duration` type that accepts `d` (days) as today, `SecretSource`
  (`{ env }` or `{ file }`), `Price`. Each implements `yaml.Unmarshaler` and a `Set(string) error` used by the
  variable walk.
- **No one-of sections.** A setting that picks an implementation is one key whose value names it, never a choice
  inferred from which of several keys is set (see "The store" and "Artifacts" below). Two layers then cannot disagree
  about the kind: the later value wins, whole.

### Loading

`pipeline.LoadEnvironment(path, required, lookup)` (the signature may change; `lookup` is `Runtime.Env`, so tests
never touch the process environment):

1. **Defaults**: walk the struct, apply every `default` tag.
2. **File**: `--env-file` (also `MILLSTREAM_ENV_FILE`, a Kong `env` tag), else `./millstream.yaml` when it exists.
   Decode with `KnownFields(true)` into the defaulted struct. Relative paths resolve against the file's directory,
   as today. yaml.v3's errors are rewrapped so they name the key path (`ui.baseUrl: ...`), as today's do.
3. **Variables**: walk the struct; for each leaf, look up `MILLSTREAM_` + the `env` segments joined by `_`
   (`MILLSTREAM_UI_BASE_URL`, `MILLSTREAM_STORE_DSN`, `MILLSTREAM_IMPROVE_GIT_AUTHOR_EMAIL`), and when set,
   `Set` the leaf from its text. Relative paths from a variable resolve against the working directory.
   - **Maps and lists** (`registries`, `prices`, `secrets`, `improve.git.env`) take the whole value as YAML flow
     syntax: `MILLSTREAM_REGISTRIES='{ lab: ghcr.io/monolithiclab/millstream-actions }'`. No per-entry variables.
   - **Secret sources** (`auth.token`, `node.token`): a set variable means "read me": the source becomes
     `{ env: <that variable> }`.
     `MILLSTREAM_AUTH_TOKEN=<token>` is the token itself, and the struct holds the variable's name, never the value,
     so nothing changes in how secrets are resolved, logged or redacted.
   - **Strictness**: a variable whose name starts with `MILLSTREAM_<SECTION>_` for a known section (or equals a known
     top-level key) but matches no leaf is an error naming it (`MILLSTREAM_UI_BASEURL: no such key; did you mean
     MILLSTREAM_UI_BASE_URL?`). Other `MILLSTREAM_*` variables are ignored, which leaves the CLI-client variables
     alone. A test holds that no client variable falls inside a section's prefix.
4. **Flags**: a flag that sets a key overrides it only when given on the command line, never with its Kong default.
   Today that is `--db`, which sets `store.dsn`. It replaces section 14's rule that naming the store in both places
   is a usage error. Future flags for keys declare which key they set with a
   `setting:"<key path>"` tag (gomddoc's join).
5. **Validate**: the checks the node readers made today, over the final struct: the store DSN and artifacts URL,
   `host:port`,
   http(s) URLs, namespaces, pinned images, package dirs, variable names, fractions, positive ints,
   `improve.publish` needing its settings, `CheckMode`. Each error names the key path; a value a variable could not
   parse names the variable. The loader keeps no record of which layer set a value.

### The store

`store` has one key, `dsn`, whose scheme picks the implementation:

- `sqlite://<path>`: SQLite at `<path>`, everything after `sqlite://` (`sqlite://.millstream/millstream.db` relative,
  `sqlite:///var/lib/millstream/millstream.db` absolute). The default, `default:"sqlite://.millstream/millstream.db"`.
  A relative path resolves against the working directory when defaulted or set by a variable or flag, against the
  file's directory when set in the file.
- `postgres://[host][:port]/[database][?option=value...]` (or `postgresql://`): Postgres, the URI handed to pgx as
  is. Everything else follows libpq's conventions, which pgx implements: `PGUSER`, `PGPASSWORD`, `PGHOST`, `PGPORT`,
  `PGDATABASE`, `PGSSLMODE` and the rest fill what the URI leaves out, and `~/.pgpass` works. A password in the DSN
  is refused, in every layer, with a message pointing at `PGPASSWORD`: `store.dsn` is then not a secret, may be logged
  with its query string, and is no longer a secret source.
- Any other scheme, or none, is an error naming the two accepted ones.

`--db <dsn>` sets `store.dsn` (`--db sqlite://other.db`, `--db postgres://db/millstream`). A bare path given to
`--db` is an error with a hint (`want sqlite://other.db`), so the flag and the key share one syntax.

The store-path-derived defaults stay: the local artifact directory and package cache sit beside a SQLite database,
and beside `.millstream/` with Postgres (`artifacts/` under the default SQLite path's directory, as today with
`--db`'s).

### Artifacts

The same rule, applied by the spec's author (to confirm): `artifacts` has one key, `url`.

- `file://<path>` (default `artifacts` beside the database: a computed default, see the calls below) is the local
  directory, `<path>` read as `sqlite://` reads its path.
- `s3://<bucket>[/<prefix>]` is an S3-compatible bucket. Everything else follows the AWS SDK's conventions:
  `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` (else `us-east-1`, as today) and `AWS_ENDPOINT_URL`
  (else AWS's endpoint for the region). The `endpoint`, `region`, `prefix`, `accessKeyId` and `secretAccessKey` keys
  go; `internal/artifacts/s3` reads the variables through `Runtime.Env`.

With that, the only secret sources left in the file are `auth.token`, `node.token` and the pipelines' `secrets`.

### `millstream init environment`

- `millstream init environment [--dir <d>]` writes `<d>/millstream.yaml` (default: the current directory), refusing an
  existing file like `init pipeline` refuses a directory (`scaffold.ErrExists`, a usage error).
- The file is generated by walking the struct: each section a commented block, each leaf a commented line
  `# key: <default>  # <doc>`, followed by its variable's name, so the file also documents the variable layer. Maps
  get one commented example entry. A header says what the file is, that every key is commented out at its default,
  and that variables and flags override it.
- Output prints the path and the next step, like the other `init` commands.
- Tests:
  - loading the generated file gives exactly the defaults;
  - uncommenting every line of the generated file parses (every example is valid);
  - every leaf has `doc`, every `env` path is unique, and every key appears in the generated file;
  - a golden file of the output, rewritten with `-update` like the help goldens.

### Help and docs

Each place takes the simplest, most direct way for its reader:

- **CLI help**: `init environment` gets a `help:""` and a `Help()` with an example; the `--env-file` help says the
  default and that `millstream init environment` writes one. `guide.md` (the `millstream help` guide) states the
  three layers and the variable naming rule, with two examples, and points at `init environment` for the full list.
- **Tutorial** (`docs/guides/getting-started.md`, run for real): the step that writes `millstream.yaml` by hand uses
  `millstream init environment`, then shows the lines to uncomment and set (`agents.allowUnsandboxed`, `prices`). The
  builder picks whichever of that or two variables is shorter in the tutorial's flow, and reruns the tutorial.
- **`docs/guides/deployment.md`**: Compose and systemd sections set variables; the Laptop section uses
  `init environment`. Nothing links `deploy/compose/millstream.yaml`.
- **Platform spec section 14**: the YAML block stays as the shape reference; the text adds the three layers, the
  variable naming rule, the secret-source rule, the strictness rule, `store.dsn` and `artifacts.url` with their
  schemes and the libpq and AWS variables, and `--db` overriding `store.dsn`. Section 13's command
  table gets `init environment`.
- **`docs/decisions.md`**: a new entry (next free D number) records the layering, the struct-tag schema, the
  secret-by-variable rule and why no library (koanf/viper) is used, citing gomddoc's D5. Edited in place, pre-release
  rule.
- **`docs/development/testing.md`** where it describes the environment-file fixtures, if it does.

### Compose and systemd

- **Compose**: `deploy/compose/millstream.yaml` is deleted. The engines' `environment:` in `compose.yaml` declares the
  non-secret keys (`MILLSTREAM_ENVIRONMENT: production`, `MILLSTREAM_LISTEN: 0.0.0.0:7070`,
  `MILLSTREAM_ENGINE_LOCK_CHECK`, `MILLSTREAM_TLS_CERT: /etc/millstream/tls/cert.pem`, `MILLSTREAM_NODE_EMBEDDED:
  "false"`, `MILLSTREAM_REGISTRIES`, `MILLSTREAM_RETENTION_*`, `MILLSTREAM_UI_BASE_URL`, ...), and the secrets come
  from `.env` under their conventional names (`PGPASSWORD`, `MILLSTREAM_AUTH_TOKEN`, `MILLSTREAM_NODE_TOKEN`,
  and for S3 `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`). `MILLSTREAM_STORE_DSN: postgres://postgres/millstream`
  and `PGUSER: millstream` are plain settings in `compose.yaml`; the postgres service reads the same password from
  `.env` as `POSTGRES_PASSWORD: ${PGPASSWORD}`, so it is written once.
  Values shared by both engines are written once (a YAML anchor or an `x-` extension), not
  twice. `.env.example` is renamed to match; the `--env-file` argument and the mount go.
- **systemd**: the unit drops `--env-file`; `millstream.env.example` lists the variables (secrets and settings) the
  engine needs. The install steps in `deploy.md` lose the `millstream.yaml` line.
- **The soak test** (`internal/e2e/soak_test.go`) stops reading `deploy/compose/millstream.yaml`: it runs
  `compose.yaml` as is and adds its prices through its override's environment (`MILLSTREAM_PRICES`).
- `make test-deploy` (`docker compose config`, `systemd-analyze verify`) still passes; AGENTS.md's rule that a change
  to the environment file's keys updates `deploy/` and `docs/guides/deployment.md` still holds and now covers variables.

### The lab-go-app skill

In `repositories/lab-standards` (its own commit, its own repo's gate): a "Configuration" section in the `lab-go-app`
skill: one struct with named section fields carrying `yaml`, `env`, `default` and `doc` tags; load defaults, then the
file (strict), then `<APP>_<SECTION>_<KEY>` variables by walking the struct, then explicitly-given flags; an
`init`-style command generates the default file from the struct; docs and deploy files use variables or the generated
file, never a hand-kept template; tests hold the generated file, the docs tags and the variable names. Cite
millstream and gomddoc as the references.

## Testing

- Unit (in `make test`, within the budget: these are pure, no files beyond `t.TempDir`, no process environment):
  layer order (default < file < variable < flag), each field type's `Set` and `UnmarshalYAML`, secret sources from
  variables hold the name only, strict unknown keys and unknown section variables, every `Validate` rule with its key
  path (today's `environment_test.go` cases carried over), relative path resolution per layer, the `init
  environment` tests above, and the CLI command's refusal of an existing file.
- e2e: the existing serve/auth/webhook/failover tests keep their environment files; one e2e case starts `serve` with
  variables only (no file) and checks the token and listener took effect.
- Deploy: `make test-deploy` and `make soak` after the Compose change (milestone-close tier).
- `go test ./internal/cli -run Test_help -update` for the help goldens.

## Constraints

- Go standard library plus the YAML library already in `go.mod`; reflection for the walk. No new dependency.
- The environment struct stays in `internal/pipeline` (callers already import it).
- `make test` budget (docs/development/testing.md): the new tests are microseconds each; the struct walk runs once per
  command.
- Repo rules: AGENTS.md's "Constraints that look like bugs" that mention environment keys still hold; secret
  handling (`SecretSource.Value`, never logging a value) is unchanged.

## Calls made after the builder check

These were settled by the spec's author, not the product owner; each is open to review.

1. **Recording evals.** `eval` records scores when `--db` is given or `store.dsn` differs from its default.
2. **One key per choice.** Ruled by the product owner: no one-of sections (see "The store"). Setting one leaf of an
   absent pointer section (`tls`, `auth`) allocates it, and `Validate` then requires its siblings (`tls.key` with
   `tls.cert`), naming the key.
3. **`MILLSTREAM_NODE_TOKEN` keeps both roles.** It is the node command's join token and the engine's `node.token`:
   the same secret on both sides, so one variable is the simplest deployment. The client-variable test lists it as an
   intended overlap. The strict unknown-variable check runs wherever the environment is loaded (every command that
   calls `environment(rt)`), `node` included: it reads the environment for the container runtime and the agents key.
4. **Computed defaults have no `default` tag.** `agents.linuxBinary` (the running binary on Linux),
   `artifacts.url` (`file://` beside the database), `secrets` (absent means `MILLSTREAM_SECRET_<NAME>`, which an
   empty map
   does not), and any other key whose default depends on another value: the `doc` tag states the computed default, the
   generated file shows the key commented out with an empty value, and the code keeps computing it. `ui.baseUrl`'s
   default is static (`http://127.0.0.1:7070`) and moves into the tag, `review.DefaultBaseURL` following it. Behaviour
   does not change: retention keeps "unset is for ever" for `events`, `transcripts` and `rollups` (no default tag;
   section 14's `90d`/`30d`/`400d` are examples), and `every` takes `default:"1h"`. The "generated file loads as the
   defaults" test compares against the defaulted struct, computed keys unset.
5. **Conventions over keys.** Ruled by the product owner: where a client library has a convention, use it. Postgres
   credentials and connection defaults come from libpq's `PG*` variables; S3's from the AWS SDK's (applied by the
   spec's author to artifacts, to confirm).
