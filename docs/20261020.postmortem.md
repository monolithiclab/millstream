# Millstream POC implementation: post-mortem

Milestones M1 to M5 of the [platform spec](specs/20261014.platform-design.md), built from 2026-10-16 to
2026-10-20 by one lead session orchestrating subagents, each milestone on its own branch branched from the previous
one and kept unmerged for validation: `m1-core-engine`, `m2-agents`, `m3-review-ui`, `m4-server`, `m5-improve`. Each
plan's Execution notes record what was built, the rulings and what was deferred; this page records what the process
taught.

## Outcome

- Every milestone's exit criterion is met by an automated scenario, offline and deterministic: the M1 crash suite
  over every unit and phase; M2's agent scorer, dedupe replay over seven days and lessons edit; M3's reference demo
  in the browser in English and French with no axe violation; M4's failover and node chaos suites and a compressed
  soak on the Compose deployment; M5's production evidence yielding an accepted `lessons` and an accepted `distill`
  proposal (holdout agreement 1.000, day-3 agent cost at 3.7% of production).
- Not met as written: M4's week-long unattended run (replaced by `make soak`, 30 minutes with random engine and node
  kills; `make soak SOAK_DURATION=168h` runs the week).
- Whole-branch reviews found no critical issue in M2, M3 and M4, and one in M5 (proposed code escaping the sandbox
  through an action directory no step referenced), fixed before the milestone closed.

## What worked

- **A plan per milestone, a whole-branch review per milestone.** The reviews earned their cost every time: M4's
  found a node silently dropping results on failover and cross-pipeline artifact reads; M5's found the sandbox
  escape and unredacted insight evidence. Per-task review alone would have missed all of them.
- **Exit criteria as tests.** Writing each milestone's exit as an end-to-end scenario found real bugs no unit test
  had: exec actions never starting under `serve` (a relative package path), a pull starving its own leases of
  renewal, imported evidence invisible to the improve pipeline, distill agreement ignoring item keys.
- **Record/replay for agents.** Every agent call in tests replays a recording keyed on the rendered prompt, so the
  whole platform, including LLM drafting of proposals and distilled code, is tested offline and deterministically;
  a lessons edit changes the prompt, hence the key, hence the scores.
- **Crash and chaos suites over every unit boundary.** Failpoints at every unit's commit edges, on SQLite and
  Postgres, plus process kills and network partitions, caught a consumed sequence on a pre-commit crash and several
  takeover races.
- **Suspicious flakes were real.** `TestNodesKilled`, written off as racy, hid a node that did not renew the lease of a
  delivery whose package it was still fetching; a flake is a bug until shown otherwise.
- **Fix the class, not the instance.** Asking every fix to grep for its pattern found the same delivery-id keying
  bug in the engine and the node, and every place proposal code could run.

## What went wrong, and the fixes now in place

- **The test suites were too slow, repeatedly.** The default suite started at ~100 s; the user's rule (a few hundred
  milliseconds) took two dedicated rounds, then a trim nearly every task, as each milestone added tests and the
  budget sat at its limit. Lessons: in-process fakes, injected clocks and store images from day one; a measured
  budget (`make test-times`, medians of three runs) instead of impressions; raise the budget deliberately when the
  remaining cuts would remove primary behaviour tests (500 → 750 ms during M5, the user's ruling) rather than spend
  hours per task. Recorded in the lab-go-app skill ("Fast by default") and AGENTS.md.
- **Full slow suites were run far too often.** Each parallel agent ran the full end-to-end and UI suites, sometimes
  several times, on one laptop: load averages of 40–85, timing-sensitive tests failing on noise, and reruns. Fix,
  now in `~/.claude/CLAUDE.md`: agents run only `make ci` and their packages' tests; full suites run once per batch
  after merging parallel work, and at milestone close. A machine-wide lock (`scripts/e2elock`) queues heavy suites.
- **The laptop slept.** On battery, macOS idle-sleeps mid-run: one five-minute suite took three and a half hours and
  looked like a stalled agent. Fix: long runs under `caffeinate -i` (global rule).
- **Parallel worktrees cost merges.** Splitting tasks across worktrees saved wall time but every merge needed a
  full integration pass; branches that shared files (catalogues, OpenAPI, migrations, the insights list) conflicted
  each time, and two merges introduced bugs (a field shadowing an embedded one). Fix: parallel worktrees only for
  disjoint files; at most three agents at once; budget the merge.
- **Agents stalled or handed back early.** Several agents reported "waiting on background work" with nothing
  running, for up to hours, and some handed back unfinished, uncommitted work saying they had been told to. Nudging
  them, or checking `ps` and `git status` and restarting, recovered every case; briefs now ask for a short final
  report and nothing else.
- **Working directory under a client folder.** The session ran from a Drive `Customers/` folder; the permission
  classifier refused some agent commands as personal-data handling. Start sessions in the repository.
- **Binaries committed by mistake.** Two Go test binaries (18 MB and 29 MB) were committed before `*.test` was
  ignored; they are deleted, and BFG purges them from history once M5 is pushed.
- **Usage limits.** Session and weekly limits stopped agents mid-task several times. Agents' work survived (committed
  or saved), and resuming them worked; long briefs that commit often lose the least.

## Rulings worth remembering

- On Postgres, the active engine is the only writer; CLI state changes go through the API.
- Ids are unique within a pipeline only; every API route and in-memory map is keyed by pipeline and id.
- Proposed code is untrusted until accepted and runs only in the network-less sandbox, wherever it runs.
- A backtest may let unreviewed outputs move as far as the patch moved reviewed outputs toward the reviewers, plus a
  0.02 tolerance: lessons generalise reviewers' corrections, but a patch that fixes one reviewed item and wrecks the
  rest still fails.
- Request ids are identifiers a purge keeps, and must never carry personal data.
